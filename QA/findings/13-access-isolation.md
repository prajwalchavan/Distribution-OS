### NOT TESTED (with reason)
- **True access-token expiry (the `exp` clock)** — would need a 15-minute wait or the signing key (not on
  hand). Covered indirectly: the `exp` claim is present and a token with a tampered `exp` is rejected
  (signature check). Marked NOT TESTED for the literal wall-clock case.
- **`documents`, `file_objects`, `messages`, `inbound_messages` cross-tenant by real Sai id** — the Sai seed
  has no rows in these tables, so there was no genuine foreign id to point at. The IDOR sweep (random ids)
  and the generic list-filter isolation still exercised these endpoints; per-row isolation for them is
  NOT TESTED for lack of seed data.
- **Password reset end-to-end** (`forgot-password` → token → `reset-password`) — the reset token is written
  to the auth-service log out of band; it was not harvested this session. `forgot-password` always answering
  `ok` (no user enumeration) was confirmed by contract; the reset leg is NOT TESTED.
- **UI-level checks** — out of scope for this lane by charter (API/DB only).

### Observations (not filed as access findings — belong to other phases)
- **8 handler `500`s** during the vertical run, all for the *correctly authorised* role calling its own
  service with the /docs example body against a wrong-state row (e.g. `delivery.stops.arrive`,
  `pricing.priceLists.upsert`, `retailers.beats.upsert`). Body is a generic "Internal server error" (no
  stack disclosure). This is input/state robustness (Phase 13), not access control.
- **Query filters are silently scoped to the caller.** `salespersonId`, `retailerId`, `userId` filters on
  list endpoints are ignored when they name someone else — the query returns the caller's own rows, not the
  named party's. This is *safe* (it never widens access) but can mislead; noted for the API-hygiene backlog.

### DOS-270 — A revoked login keeps working on the tenant APIs until the access token expires
Category: security | Priority: P2 | Role: all staff/retailer | Platform: API

Steps (all reproduced, `QA/evidence/p12/auth.json`):
1. Sign in as a staff member; keep the access token and refresh token.
2. Cut the login off three different ways, each in its own run:
   - **logout** — `POST /auth/auth/logout` with the refresh token;
   - **deactivation** — the owner calls `POST /owner/tenancy/staff/set-status {status:"disabled"}` for that user;
   - **password change** — a second session of the user calls `POST /auth/auth/change-password`.
3. With the *already-issued access token*, call a protected tenant endpoint
   (`GET /sales/orders`, `GET /warehouse/inventory/balances`, `GET /manager/reporting/dashboard/owner`).

Expected (charter Phase 11): "logout actually invalidates access"; "deactivated users cannot continue
performing protected operations with an existing token."

Actual:
- After **logout**: `GET /auth/auth/me` → 401, but `GET /manager/reporting/dashboard/owner` → **200**.
- After **deactivation**: `set-status disabled` → 200, the refresh token → 401, but `GET /sales/orders`
  with the live access token → **200**.
- After **password change**: the other session's refresh → 401, `/auth/me` → 401, but
  `GET /warehouse/inventory/balances` → **200**.
- In every case the refresh token is revoked immediately, so no *new* access token can be minted; the
  existing one stays valid until its `exp` (15 minutes, per the token `iat`/`exp` observed).

Root cause: `TenantGuard` on the six tenant services validates only the JWT (EdDSA signature, `exp`, and the
`PERMISSIONS` matrix) with no database read — by design ("the access token (JWT) is stateless", CLAUDE.md).
Session and membership liveness are enforced only by the auth service (`/auth/me`, refresh), not by the
tenant services. This is a documented trade-off, but it fails the literal Phase 11 expectation.

Business impact: a fired or suspended employee — or someone whose session an owner has explicitly logged
out — can keep operating for up to 15 minutes: a disabled salesperson can still book orders, a disabled
delivery crew can still act on a trip, a retailer whose access was pulled can still place orders. Bounded by
the token TTL and the refresh revocation, so not a P0/P1 leak, but a real revocation-latency gap on
money/stock-moving endpoints. (Founder may choose to escalate given money can move within the window.)

Evidence: `QA/evidence/p12/auth.json` (`access-after-logout`, `deactivation`,
`password-change-other-session`).

Suggested fix (product decision — not implemented): either shorten the access-token TTL for
mutation-capable roles, or have `TenantGuard` check a cheap session/membership-liveness signal (a cached
`session_revoked_at` / `membership_status`) on mutating (non-GET) procedures so an explicit revoke bites
before the token expires.

### DOS-271 — Login response time distinguishes a real username from an unknown one
Category: security | Priority: P3 | Role: n/a (pre-auth) | Platform: API

> **Judge's note (main session, 2026-09-28): NOT CONFIRMED — do not schedule.** The stated cause is wrong: `AuthService.login`
> verifies the password against a dummy argon2id hash when the username is unknown (`auth.service.ts`, `dummy()`), so both paths hash.
> The figures here are 3 samples each. The security lane measured the same two cases with 40 and 10 samples on the production-mode
> build: median 26 ms (unknown) against 27 ms (real), `QA/evidence/p16/timing-oracle.json`. Kept for the record; counted as P3 observation, not a defect.

Steps (`QA/evidence/p12/auth.json` → `wrong-vs-unknown`):
1. `POST /auth/auth/login` with a **real** username (`raju.yadav`) and a wrong password.
2. `POST /auth/auth/login` with an **unknown** username (`ghost.user.zzz`) and any password.
3. Compare status, body and latency (3 samples each, staying under the lockout threshold).

Expected: indistinguishable responses (status, body, and timing) so an attacker cannot enumerate valid
usernames.

Actual: the **body and status are identical** — both `401 {"message":"Invalid username or password"}` —
which is correct. But the **timing differs**: median ~44 ms for a real username vs ~27 ms for an unknown one.
The real-username path runs the password hash comparison; the unknown-username path returns before hashing,
so it is measurably faster. Over many samples this is a weak username-enumeration oracle.

Business impact: low. An attacker could, with statistical effort, confirm which usernames exist, aiding
targeted password-guessing — but the 5-attempt account lockout (verified, below) sharply limits guessing.
Usernames here are also low-entropy (`first.last`), so enumeration adds little.

Evidence: `QA/evidence/p12/auth.json` (`wrong-vs-unknown`: `medianWrongMs` 44, `medianUnknownMs` 27,
identical status+message).

Suggested fix (product decision — not implemented): perform a dummy hash comparison on the
unknown-username path so both branches take constant time.

## Authentication controls that PASSED (Phase 11)

- **Account lockout**: after 5 failed passwords the account returns `423 LOCKED`
  ("Try again in 15 minutes"); the correct password is refused while locked. (`auth.json` → `lockout`.)
- **Refresh rotation + reuse detection**: refresh rotates on every use; presenting an already-rotated
  refresh token is rejected (401) and **kills the whole session family** — the legitimate child token is
  then also refused. (`auth.json` → `refresh-rotation-and-reuse`.)
- **Token integrity**: `alg:none`, a tampered `role` claim (salesperson→owner), a tampered `tid` claim, a
  token re-signed with an attacker's own ed25519 key, a tampered-`exp` token, empty and garbage tokens —
  **all rejected 401**. (`auth.json` → `tampered-tokens`.)
- **Role election**: `actAs:"owner"` for a salesperson-only login → 403 with a clear message.
  (`auth.json` → `actAs-unheld-role`.)
- **Tenant switch**: `switch-tenant` to a distributor the user has no membership in → 403.
  (`auth.json` → `switchTenant-unheld-tenant`.)
- **must-change-password** (observation per charter, tested): a staff member created with a temporary
  password has `mustChangePassword: true`, yet can sign in and call the API before changing it — a read
  (`GET /sales/orders`) returned 200, and the block on a mutation was ordinary field validation (400), not
  an auth refusal. The flag is advisory; the app is expected to force the change. Kept as an observation,
  not a defect: a salesperson cannot move money directly (orders still need approval → billing). Worth a
  ruling only if a money-desk role (accountant) is ever issued a temp password and left able to record
  receipts before changing it. (`QA/evidence/p12/auth.json`; retest logged in the session notes.)
