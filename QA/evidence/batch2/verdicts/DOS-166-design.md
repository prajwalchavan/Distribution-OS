# DOS-166 — architect design (Fable, 2026-09-13)

## Summary for the founder (three lines)
1. The offline upload door (`POST /sync/upload`) lets ANY staff phone write ANY of the twelve synced tables: a salesperson recorded money (RCPT-0708) although the online `POST /receipts` refuses it.
2. Fix: every synced table names the online procedure it stands for, and the upload checks the same permission table the online door uses; a refused op is recorded and shown on the phone as "not allowed" (never a crash, never a wedged queue). A database policy then makes "a salesperson never records a receipt" true even if code forgets.
3. Own lane, size M, started once the money lane (h1) merges. The delivery crew's receipts, stops and deliveries work exactly as before; only doors nobody legitimately uses are closed.

## Design
Single source of truth: `PERMISSIONS`. Single enforcement point: `SyncService.upload`, once per op, before the savepoint and before `vetoIfStale` (as the DOS-115 verdict sketched).
1. `contracts/src/sync.ts`: `SYNC_REJECTION_CODES.roleNotAllowed = 'role_not_allowed'` + one sentence in its doc comment. No route or shape changes (READMEs unchanged; run `docs:readme:check` anyway).
2. `sync.registry.ts`: `register(table, handler, { standsFor: readonly ProcedurePath[] })` — the option is REQUIRED, so a registration without it is a compile error; at registration `permissionFor(p) === undefined` for any entry throws, so a service naming an undeclared procedure cannot boot (fail closed, like the guard). New `mayUploadTable(table, role: ActorRole)`: `role === 'system' || standsFor.every(p => isAllowed(permissionFor(p), role))` — EVERY listed procedure must allow the role (trip_stops needs all three DOORSTEP rows; a non-membership role such as `curator` fails closed; a support session already acts as `owner` at the guard, tenant.guard.ts:229). New `uploadTables(): { table, standsFor }[]` for the pin test. `manifest().writable` becomes `mayUpload(role) && handlers.has(table) && mayUploadTable(table, role)`, so the phone never queues what the server will refuse (docs/27 §1: the manifest's `writable` is the client's authority).
3. `sync.service.ts:108-120`: after the `unknown_table` branch, `else if (!this.registry.mayUploadTable(op.table, ctx.actorRole))` → `reject(op, 'role_not_allowed', 'A <role> may not send <table> from a device', 'यह काम आपकी भूमिका के लिए नहीं है')`. It runs outside the savepoint (no DB read, no RCPT number drawn) and still falls through to the `sync_errors` + `sync_ops` inserts, so it is durable and replays as a rejection. HTTP stays 200.
4. The five module files gain `standsFor` on the twelve `register` calls (module files only — `receivables.sync.ts`, `delivery.sync.ts`, `orders.sync.ts` are untouched, which is what keeps this clear of lanes h1/h3/h5).
5. Per-handler checks: DOS-115 (b) `requirePlacer()` stays exactly as approved — defence in depth, like `requireRole` behind the guard — and NO new per-handler checks are added anywhere else. The registry check is simpler and harder to get wrong: it is one line derived from the matrix, it cannot be forgotten by the next module (the table above shows the per-handler approach forgotten twelve times), and a per-handler `requireRole` is a second tuple that drifts (core's `MONEY_COLLECTORS` copy at receivables.service.ts:156 already lives apart from the contracts one).
Client: `@dos/offline` engine.ts:737 special-cases only `stale`; every other code is stored with the server's sentence and shown in the tray — no client change. `writable` stays true for everything a field app pushes today (rep: sales_orders/lines; loader: pick_lines; crew: trip_stops, deliveries, receipts), so no field device's `schemaVersion` moves; only the desk roles' hash moves and no desk app mounts `<OfflineProvider>` (only the sales, warehouse and delivery `_layout.tsx`).

## Warehouse 500 and database defence in depth
Why 02 passed and 03 crashed: `receipts` INSERT is `staffWritePolicy` (any non-retailer, schema/receivables.ts:219) and `journal_entries` INSERT is `LEDGER_POSTING_ROLES` = STAFF minus warehouse (:49, :108). The salesperson passed both; the warehouse failed the journal with 42501, which is a `DrizzleQueryError`, not an `ORPCError`, so sync.service.ts:147 rethrew it: 500, whole batch rolled back, no `sync_ops` row, RCPT-0709 burnt inside the rolled-back savepoint.
Fix, INCLUDED (three lines in the file already open, and it is never-list #8's exact case): sync.service.ts:147 gains `else if (isPrivilegeViolation(error)) outcome = rejection('not_permitted', pgMessage(error))` using the existing helpers (platform/pg-errors.ts:19, :34). A policy refusal is a refusal of THIS device's op, never a transient; without this branch the policy below would turn every future refusal into a 500 and a wedged queue. After the fix the warehouse op never reaches the handler anyway (`role_not_allowed`, before any number is drawn).
Database defence in depth: YES, for `receipts` INSERT only. Today the database itself lets a salesperson write money: never-list #2 is application-only while #1 (cost) is a database guarantee, and this finding is precisely an application path that skipped the matrix. Shape: `columns.ts` adds `MONEY_COLLECTOR_ROLES = ['owner','manager','accountant','delivery','system']` and an optional second argument `staffWritePolicy(name, { insert?: readonly string[] })` that narrows only the insert policy's `withCheck` (update and delete stay staff-wide: deposit/bounce/reverse are MONEY_DESK, the worker writes `pdf_object_key` as `system`, nobody deletes). `schema/receivables.ts:219` → `...staffWritePolicy('receipts_write', { insert: MONEY_COLLECTOR_ROLES })`. Every INSERT path verified: createReceipt (MONEY_COLLECTORS), collections.service.ts:124/127 (MONEY_COLLECTORS), the sync handler (now crew-only), `payments.initiate` creates no receipt (:152), seed runs as `dos` (BYPASSRLS). Migrations: `pnpm db:generate` → `0045_receipts_insert_roles_expand.sql` (alters `receipts_write_insert` in place — same name, so no rename prompt) + hand-written `0046_receipts_insert_roles_guarantees.sql` ending in the DO block that fails unless `receipts` has FORCE RLS, carries no `FOR ALL` policy, and `pg_policies.with_check` for `receipts_write_insert` names neither `salesperson` nor `warehouse`. Numbers are 0045/0046 because h1-money holds 0043/0044 (c2c472f); take the next free index from `_journal.json` after h1 merges. Cost: S (one const, one helper arg, one schema line, two migrations, one rls test); it lands as the second commit of the lane.
