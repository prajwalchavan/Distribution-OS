## Amendments (binding)
(a) **The app mints `uuidv7()` per unlock call, exactly as `disable` does (users.tsx:80).** Not `meta.idempotencyKey` + `enable.reset()`: a hidden "reset on every opening" invariant in one screen is how the replay the reviewer found comes back in a refactor. The Dialog is `busy` while pending and the server's no-op guard makes a second enable harmless, so nothing is lost. The e2e replay test (lock → unlock → lock → unlock, same reason) stays as the proof.
(b) **The smoke `planFor` case returns `{ pathParams: { id }, pinned: { id } }`, as :1508 does — never `pathParams` alone.** The handler acts on the BODY id (DOS-112), and a contract example body is spread with `ctx.pinned` (smoke-endpoints.mts:2461-2467). Path-only, the body keeps the docs' active-filtered pick (examples.ts:780-791) or the sampler uuid: the pair can lock one identity and "unlock" another, or 404 → BROKEN on the uuid — the exact failure the plan claims to close.
(c) **`user.enabled` enters DOS-109's typed vocabulary.** DOS-109 lands first in this lane and binds `PLATFORM_AUDIT_ACTIONS`/`PlatformAuditAction` (its amendment (d)); `enableUser`'s insert names the action through that type, the array gains `'user.enabled'`, strings.ts gains `'word.user.enabled': 'Login unlocked'`, and DOS-109's core case 1 stays green.
(d) **The audit row is written iff the UPDATE returned a row.** `update users set status='active' … where id = :id and status = 'disabled' returning`; insert `user.enabled` only when `row` is defined. Same outcome as the `target.status` guard under the lock, but the trail can then never say "unlocked" when nothing changed.
(e) **DOS-164 is an iOS-walk dependency, not a build blocker** (this corrects the DOS-109 verdict's "only after DOS-164 merges"). Build the unlock Dialog exactly as the lock Dialog is built today (same kit component, same placement beside the Sheet, users.tsx:256-285) so DOS-164's kit fix covers both at once; if DOS-164's verdict prescribes a new screen-side pattern before the screen half is built, follow it. iOS is recorded NOT TESTED (blocked by DOS-164) and walked in the A.12 regression.
(f) **The docs' disposable pick prefers a locked identity.** examples.ts:780-791 drops `eq(users.status,'active')` and orders `(status = 'disabled') desc, created_at desc`, so on the Scalar page the enable example undoes the identity the disable example locked, and a database an interrupted run left locked is repaired by pressing Execute once. The disable note keeps its DESTRUCTIVE wording.

## Decisions
- technical: reason is mandatory, trimmed, 1-500 characters (`AdminUserEnableInput` mirrors `AdminUserDisableInput`; docs/23 §10 #14 says "the same shape as disable"); an unlock without a why is not auditable.
- technical: unlocking a login that is not locked answers 200 with the unchanged item, no UPDATE, no audit row. A stale "Locked out" list or a double press is harmless, and a console account (no membership, no idempotency row) is safe through the row lock alone. Not 409: the state the super wanted is already true.
- technical: an unlock restores `users.status` only. Ended sessions stay ended (the person signs in afresh), memberships, `platform_admins.disabled_at` and the 5-failure lock (`failed_login_count`/`locked_until`, auth.service.ts:169-186, expires by `LOCK_MINUTES` on its own, shown as its own chip at users.tsx:205-210) are untouched — clearing that from the console would let a super switch off brute-force protection on somebody else's account.
- technical: `admin.users.enable` = POST `/admin/users/{id}/enable`, declared directly after `disable` (ORDER_HINT has no admin entry, so declaration order is smoke run order), PERMISSIONS `PLATFORM`, ADMIN_LEVELS `CONSOLE_SUPER`, output `AdminUserItemOutput`; idempotency filed against the first membership's tenant like the lock.
- technical: lane **h10-console** from main, order DOS-109 → DOS-107 (both edit console.service.ts `audit()`, admin.ts, internals.ts, platform-admin.spec.ts, admin-app strings.ts; DOS-107's screen half also needs DOS-109's typed action). Line-disjoint with DOS-115 (h5), DOS-166 (h7), DOS-037/044 (h9), DOS-043 (h2) on permissions.ts/.test.ts, and with DOS-043/044 on examples.ts and smoke-endpoints.mts: merge in lane order, no swap needed. DOS-112 (P2) must add `admin.users.enable` to its path-vs-body sweep.
- docs/22: no new product rule (the 2026-09-12 row already says only a super locks or unlocks). Record the three technical specifics above as a dated §8 precision to that row plus a §11 change-log row, re-render, republish.
- No FOUNDER DEFAULT.
