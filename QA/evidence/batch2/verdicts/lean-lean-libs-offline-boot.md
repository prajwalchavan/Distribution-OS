## DOS-046 — design-ready

### Design

DECISION (protocol): a user's "Try it again" is a NEW operation. It goes out under a fresh opId (= idempotencyKey) on the same intent; the server is not touched. Reasons: (1) ADR 0007 / never-list #8 make every outcome durable and a replay of a known opId returns the stored outcome — a rejection is such an outcome, and `backend/libs/core/src/modules/sync/sync.service.ts:117-131` + `:226-229` answer a replayed rejection as `replayed:1, rejected:[stored]`, which is exactly the evidence in the finding; letting the server re-run a known opId would make one opId carry two outcomes over time and break the one invariant that makes lost-response recovery safe. (2) The user pressing the button at a later time against new server state IS a new intent; the audit stays honest (opId A rejected picklist_closed, opId B accepted). (3) The automatic re-send paths (killed mid-flight, network/5xx backoff, upgradeRequired re-queue) keep the SAME opId — nothing changes there. (4) Zero backend rows or code on the hot path.

ROOT CAUSE, three places in `frontend/libs/offline/src/engine.ts`: `retry()` :793-813 re-queues the row under the same op_id ("deliberately kept") so the server replays the stored rejection for ever; it also DELETEs the `_sync_errors` row (:806) while the server still lists that opId as unresolved, so `pullErrors()` :383-424 re-inserts it on the next sync (only `discarded_at` rows are skipped, :406-415) — and `sync()` runs manifest → pull → pullErrors independently of `flush()`, so on a reconnect the pull can run BEFORE the re-send and resurrect the old rejection beside the retried op. Third, the test double lies: `frontend/libs/offline/src/test-support.ts` `upload` answers a replayed op with `replayed += 1` and NO rejection (it stores `applied.set(opId, 0)`), so the engine acks a replayed rejection in tests — which is why the gate never saw this. The existing test 'lets a rejected op be sent again with the SAME opId…' (engine.test.ts:534) only exercises discard.

THE CHANGE.
1. `test-support.ts` FakeServer: store the rejection as the op's outcome; a replay of a rejected opId answers `replayed += 1` AND pushes the stored rejection into `rejected`, exactly like sync.service.ts. A replay of an applied op stays `replayed` only.
2. `sql.ts` (memory engine): add exactly `ALTER TABLE t ADD [COLUMN] c TYPE` — appends the column, existing rows get NULL, a duplicate column name throws `SqlError('duplicate column name: c')` like SQLite. Document it in the grammar comment at the head.
3. `schema.ts`: base `SYSTEM_TABLE_STATEMENTS` unchanged. Add `SYSTEM_SCHEMA_UPGRADES: [{ version: 2, statements: ['ALTER TABLE _sync_errors ADD COLUMN retried_as TEXT'] }]` and run them in `createSystemTables` after the CREATEs: read `_sync_state.systemSchema` (absent = 1), apply each upgrade with version > current, write `systemSchema` after each. Every store — fresh memory, fresh SQLite, an existing device DB — takes the same path, so no PRAGMA probe and no try/catch.
4. `types.ts`: `LocalSyncError.retriedAs: string | null` ("the opId the user sent it again under; the old rejection stays as history").
5. `engine.ts`:
   - `retry(opId): Promise<string | null>` — select the outbox row; if none, return null and change nothing. Else `next = uuidv7()`; in ONE store.transaction: `UPDATE _outbox SET op_id = ?, idempotency_key = ?, status = 'queued', sent_at = NULL, acked_at = NULL, rejection_code = NULL, rejection_message = NULL WHERE op_id = ?` (seq, created_at, tbl, row_id, op, data, base_updated_at, attempts untouched); `UPDATE _sync_errors SET retried_as = ? WHERE op_id = ?`; setPending(row, 'queued'). Then refreshCounts, emit [table, OUTBOX_CHANNEL, ERRORS_CHANNEL], emitStatus, `void this.flush()`, return next. Rewrite the doc comment: the opId is deliberately NEW; docs/27 §4.
   - `needsAttention()`: `WHERE discarded_at IS NULL AND retried_as IS NULL`; map `retriedAs`.
   - `pullErrors()`: the skip set becomes `SELECT op_id FROM _sync_errors WHERE discarded_at IS NOT NULL OR retried_as IS NOT NULL`; the mirror INSERT OR REPLACE statements (:417, :766) list `retried_as` explicitly as NULL only for NEW rows — use INSERT OR REPLACE with `retried_as` = NULL in settle() (a fresh rejection under a new opId), and in pullErrors keep INSERT OR REPLACE but it can only hit rows not in the skip set, so NULL is correct there too.
   - `settle()` unchanged: a re-rejected retry lands as a new `_sync_errors` row under the new opId, so the chain old → new → newer stays readable.
   - `start()` comment (:147-152) stays true — that path still re-sends the same opId.
6. `react.tsx`: `OutboxApi.retry: (opId: string) => Promise<string | null>`; the hook returns `engine?.retry(opId) ?? null`.
7. `frontend/warehouse-app/app/pick/attention.tsx`: render the retry Button only when `entry.op !== null` (the delivery tray already does this, delivery-app/app/attention.tsx:137-160); no new string — "Throw it away" stays for a server-pulled row this install no longer holds.
8. `docs/27-offline-sync-client.md`: §3 `_sync_errors` gains `retried_as`; `_sync_state` gains `systemSchema` and the sentence "system tables change expand-only through versioned ALTERs"; §4 line 71 becomes: automatic re-sends (a batch that never reached a service, an op `sending` when the app was killed, a lost response) reuse opId and idempotencyKey and the server's `sync_ops` replays the stored outcome — a rejection included; a user's retry from the tray is a NEW op: fresh opId = idempotencyKey on the same intent (same seq, row, data, baseUpdatedAt), the old rejection stays durable on the server and is marked `retried_as` on the device (QA DOS-046, 2026-09-13); §6 add the bullet "'Try it again' re-queues the row under a new opId; the old `_sync_errors` row is kept, marked, and never resurrected by the errors pull"; §11 `retry(opId) → Promise<newOpId | null>` (null when this install no longer holds the op; screens offer only discard then); §13 add test 12; §14 'App killed mid-upload' row unchanged.

### Binding amendments

- (a) Only `retry()` mints a new opId. `release()`, the sending→queued revert in `start()`, network/5xx backoff and the upgradeRequired re-queue keep the SAME opId; engine.test.ts describe 7 (:560 're-sends with the same opId', :591) must pass unchanged.
- (b) No backend change: `sync.service.ts`, the `sync` contract and PERMISSIONS are untouched; a replay still returns the stored outcome, rejection included (ADR 0007, docs/22 never-list #8). The FakeServer is corrected to match the server, never the reverse.
- (c) The retried op keeps its outbox row: same seq (FIFO place, an order still precedes its lines), created_at (the pick's own time, informational per docs/27 §14), tbl, row_id, op, data, base_updated_at; attempts keeps counting. Only op_id, idempotency_key (= the new opId), status, sent_at, acked_at and rejection_* change. No second outbox row; `applyLocally` is not re-run.
- (d) The old `_sync_errors` row is never deleted and never given `discarded_at`; it is marked `retried_as = <newOpId>`. `needsAttention` hides rows with either marker; `pullErrors` skips both. A retry refused again lands as a fresh row under the new opId.
- (e) `retried_as` is added expand-only: base DDL unchanged, one versioned step keyed by `_sync_state.systemSchema` (absent = 1 → 2), applied in `createSystemTables` before any statement touches the table, the same path for memory, fresh SQLite and an existing device DB. The memory engine learns exactly `ALTER TABLE t ADD [COLUMN] c TYPE` (NULL on existing rows; a duplicate column throws like SQLite). No try/catch around the upgrade, no PRAGMA probing, no other DDL change.
- (f) `retry()` on an opId with no outbox row (a tray row pulled from the server after a reinstall or a cleared browser) returns null and changes nothing — no marker, no emit, no upload. The warehouse tray does not render the retry button when `entry.op === null` (no new string; 'Throw it away' stays). Sales and delivery trays are not edited in this item (delivery already hides it; sales gets null harmlessly).
- (g) `stale` is out of scope: a retry of a stale edit resends the same baseUpdatedAt and is expected to be refused `stale` again under the new opId (docs/27 §7: the client never resolves a conflict alone). Do not rebase baseUpdatedAt here.
- (h) Screens keep importing only `@dos/ui` and `@dos/offline/react`; the `retry` signature change is additive (`Promise<string | null>`), so every `void outbox.retry(...)` call site compiles unchanged.
- (i) Files outside the group's list are limited to `frontend/libs/offline/src/{schema,sql,types,test-support}.ts` and `sql.test.ts` — verified against lean-groups.json that no other lean group owns them, and the change cannot be made without them. docs/22 is not lane-owned: the builder tells the main session to add a §8 row 'Correction (architect, QA DOS-046): a user's retry from the tray is a new operation under a new opId; automatic re-sends keep theirs; the server still replays stored outcomes' and a §11 change-log line correcting the 2026-09-06 'same opId on retry' wording.

### Notes

Design-ready: this is a protocol/technical choice inside the architect's own binding doc (docs/27), consistent with ADR 0007 and never-list #8; no docs/22 §8 founder decision is contradicted (the 2026-09-06 §11 change-log wording 'same opId on retry' conflated the automatic re-send with the user's retry and is corrected by amendment (i)). h11-syncpull is merged (be5c40f on main), so the engine.ts read here is current and the group's wait on it is satisfied. Observed in passing, NOT in scope — candidates for the S-list: (1) `sync_errors.resolved_at` is never written by anything on the server (discard and retry both leave the server row unresolved; `sync.errors.list unresolvedOnly, limit 50` will eventually fill with dealt-with rows and the desk's support triage sees them as open) — a later item could resolve the old row server-side via an optional `supersedesOpId` on the wire op, but it still needs the local marker built here because the pull can run before the re-send; (2) `clock_skew` (sync.service.ts:107-115) compares clientTime = capture time, so any op queued over 10 min warns; harmless because the engine ignores `warnings`; (3) the FakeServer lied about replayed rejections, which is why the offline gate missed this — fixed here; (4) sales tray (sales-app/app/orders/attention.tsx:88-95) still offers Try it again on a row with op === null; one-line parity with delivery if the sales lane wants it.
