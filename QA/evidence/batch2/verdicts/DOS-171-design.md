## Root cause

Confirmed on main 10c2464 (no backend or frontend file has changed since 331f4d0, where Fable read it). This matches S-28's executed probe and the skeptic's re-run:

1. THE WRONG FIELD. `frontend/delivery-app/app/stop/[id]/van-sale.tsx:193` reads `quote.data?.totals.netPaise`, which is documented "Before GST." at `backend/libs/contracts/src/pricing.ts:354-355`. Line :217 prints it under `d6.total` = 'Sale total' (`src/strings.ts:283`). Each line (:263) prints `lineNetPaise`, which is also before GST. The header comment (:13-15) promises the bill's figure "to the paisa". DOS-096 added `totals.totalPaise` ("What the shop pays", pricing.ts:360-361, computed with the bill's own `roundToRupee` at `quote.service.ts:158-166`) but never touched this screen.
2. THE BILL IS RIGHT. `vansales.service.ts:97-104` bills through `BillingService.issueFromLocation`. `invoices.service.ts:1548-1559` adds taxable + CGST + SGST + IGST + cess and rounds once. The order, the invoice, `retailer_outstanding_summary` and the `VanSaleInvoiced` event all carry 24 800. Collecting the 22 140 shown leaves 2 660 due and the bill `partially_paid`.
3. THE MONEY SCREEN HAS NO FALLBACK. D5 (`collect.tsx:100`) prints `stop.planned_collection_paise ?? dues.outstanding_paise` as "Owed on the bills here". That column is `notNull().default(0)` (`schema/delivery.ts:257`), so the `??` never falls through. A stop planned with no bills is written as 0 (`trips.service.ts:1139-1140` sums an empty list), and a stop created by the sale is written as 0 (`vansales.service.ts:256`). Nothing adds the van-sale bill afterwards, so D5 reads Rs 0.00 at that door. D3's bills-panel meta (:313), D1's "to collect today" sum (`index.tsx:111`) and `day.tsx:170` read the same column.
4. THE TOAST IS LOST. D6 sets the "Bill INV/…" toast and calls `router.replace` in the same tick (:183-184), the DOS-149 pattern. The crew never sees a figure taken from the bill itself.

Cess and the intra-state split are known leftovers, not the cause. `QuotedLine.taxPaise` excludes cess (pricing.ts:331; DOS-079, a P2 in lean-sales-orders-pricing). `splitGst` rounds each CGST/SGST half separately (`domain/src/gst.ts:22-24`), so an intra-state line's bill tax can sit one paisa under the quote's (S-28: 2 656 against 2 657, both totals 24 800).

## Design

Paths are relative to /Users/prajwalchavan/Desktop/Distribution OS. Work test-first: every step names its test; write it, see it fail, then make it pass. No contract, schema, migration, PERMISSIONS or README change; `pnpm smoke` is unaffected.

THE SHAPE: before billing, the crew reads the quote's PAYABLE figure. After billing, they read the BILL's figure. The money screen counts the van-sale bill. That is three small pieces, one for each screen state.

STEP 1 — the pure figure (frontend/delivery-app/src/lib/van-sale.ts, new).
`export interface SaleFigures { billPaise, beforeGstPaise, gstPaise, roundOffPaise, cashDiscountPaise: number }`. `saleFigures(quote: Quote | undefined): SaleFigures | null` (type `Quote` from `@dos/contracts`) returns `{ billPaise: totals.totalPaise, beforeGstPaise: totals.netPaise, gstPaise: totals.taxPaise, roundOffPaise: totals.roundOffPaise, cashDiscountPaise }`, or null when there is no quote. `lineFigure(quote, lineId): number | null` returns that line's `lineTotalPaise`. No React, no network. The screen reads money fields only through these two functions.

STEP 2 — D6 before billing (van-sale.tsx).
2a. Bottom bar: the label `d6.total`, reworded 'Bill total', over `<Money value={figures?.billPaise ?? null} size="moneyL" testID="d6-total" />`. The testID stays the same, so the S-28 assertion can be re-run on the screen.
2b. "This sale" panel: meta `d6.quote` is reworded 'Priced by the office rules, GST included'. Each `ListRow` gets `trailingMoney={lineFigure(quote.data, line.variantId)}`, and the free-goods chip stays. The `Group` gets a `footer` (GroupProps.footer, types.ts:210) of rows built from `Row`/`Txt`/`Money` inside the screen: `d6.beforeGst` 'Before GST' (testID d6-before-gst), `d6.gst` 'GST' (d6-gst), and `d6.roundOff` 'Round-off' (d6-round-off, only when it is not 0). When cashDiscountPaise > 0, one extra moss `Txt` line `d6.cashDiscount` reads 'Paid now, {amount} comes off the bill' (d6-cash-discount).
2c. Rewrite the header comment (:13-15): the quote's `totalPaise` is the bill's payable figure for every item that carries only GST. Cess (DOS-079) and the one-paisa CGST/SGST rounding are why the bill is shown again after it is issued.

STEP 3 — D6 after billing (van-sale.tsx).
3a. New state `billed: { no: string; totalPaise: number } | null`. `onSuccess` sets it from `result.invoice` (`invoiceNo ?? id.slice(0, 8)`, `totalPaise`), calls `haptics.success()`, and calls `void engine?.sync('van-sale')`, where `engine = useSyncEngine()` (`@dos/offline/react`, public, react.tsx:216, already used by `settings.tsx:52`). `onSuccess` does no `router.replace` and shows no toast.
3b. While `billed !== null`, the stock panel and the lines panel are hidden. A `Panel` (testID d6-billed) prints `d6.billed` 'Bill {no} issued', then `<Money value={billed.totalPaise} size="moneyL" testID="d6-billed-total" />`, then `d6.billedNext` 'Take the money on the stop screen'. The bottom bar becomes one `Button` `d6.back` 'Back to the stop' (testID d6-back) that calls `router.replace('/stop/<id>')`. The 'Bill it and hand it over' button is not rendered in this state, so a second tap cannot issue a second bill.

STEP 4 — the money screen counts the bill (backend/libs/core/src/modules/delivery/vansales.service.ts).
Once `issueFromLocation` returns and `invoice` is loaded (:112), in the same transaction: `tx.update(tripStops).set({ plannedCollectionPaise: sql\`${tripStops.plannedCollectionPaise} + ${invoice.totalPaise}\`, updatedAt: new Date() }).where(and(eq(tripStops.tenantId, ctx.tenantId), eq(tripStops.id, stop.id)))`. This is an increment, never a read-then-write. It applies to the caller's stop, to the shop's open stop, and to a stop `stopFor` has just created (its 0 becomes the bill). `lockTrip` (:63) already serialises van sales on one trip, and `idempotent()` makes a replay add nothing. Moving `updated_at` is what puts the row into the device's next delta pull (`sync.service.ts:358`). `walkStop` (:169) never sets this column, so it cannot overwrite the sum. The column keeps its meaning, "the bills at this door plus agreed old dues" (contracts/delivery.ts:340), and a van sale is a bill at this door. `collect.tsx` is NOT edited: `planned_collection_paise` is now correct there, and D3's meta, D1's sum and `day.tsx` read the same column.

STEP 5 — strings (frontend/delivery-app/src/strings.ts, d6 block only): reword `d6.total` and `d6.quote`; add `d6.beforeGst`, `d6.gst`, `d6.roundOff`, `d6.cashDiscount`, `d6.billed`, `d6.billedNext` and `d6.back`. `d6.collectNow` (unused) is left alone.

WHAT THIS DOES NOT DO: no bill-and-collect in one tap (the screen still does not use the API's `collect` block; that is a Phase-2 line, not a fix); no cess in the quote (DOS-079); no change to D5's own cash-discount arithmetic; no offline van sale.

## Binding amendments

- (a) The headline is `totals.totalPaise` under the words 'Bill total', the same field the retailer order screen prints as 'You pay' (DOS-096). 'Sale total' is retired. Only `saleFigures`/`lineFigure` read the quote's money fields.
- (b) The breakdown under the lines is Before GST, GST and Round-off (only when not 0), from `netPaise`, `taxPaise` and `roundOffPaise`. On the phone GST is one word; CGST/SGST or IGST is the bill's business. Lines show `lineTotalPaise`, GST included, which is the bill's own line total.
- (c) Schemes, bargains and order-level rules are already inside `lineNetPaise` (`priceOrder()` spreads order-level rules into the lines, schemes.ts:334-348), so the lines add up to Before GST. Free goods keep their chip and carry no value. Cash discount is reported (ADR 0004) and never deducted from Bill total.
- (d) The crew TAKES the bill's figure: after issue, D6 stays on screen with `result.invoice.invoiceNo` and `totalPaise` and offers only 'Back to the stop'. No toast followed by an immediate redirect (DOS-149's pattern).
- (e) `onSuccess` calls the public `useSyncEngine()?.sync('van-sale')`, with no change to the engine or react.tsx. If a pull is already running the call does nothing and the next poll catches up; the billed state carries the figure either way.
- (f) `VanSalesService.create` increments `trip_stops.planned_collection_paise` by `invoice.totalPaise` and bumps `updated_at`, inside the transaction, as a SQL increment. No contract, schema, migration or PERMISSIONS change; the retailer mapper still answers null (`delivery.mappers.ts:174`).
- (g) IGST: an inter-state shop gets the same rate and the same total. Intra-state, the two halves round separately, so quote and bill can differ by one paisa per line and, rarely, by ₹1 after rounding to the rupee; the bill wins and is shown (d). Handed to the DOS-079 design: when the quote's GST path is extended to cess, compute its tax with `splitGst(seller state, place of supply)` so the quote equals the bill to the paisa.
- (h) Cess: `QuoteOutput` excludes it until DOS-079. Until then, D6's Bill total for a cess item is short by the cess. D5, D3 and D1 are right because they read the bill. DOS-171 does not add cess to the quote: without DOS-079's order columns, the sales and retailer apps' quotes would stop matching the orders they place.
- (i) Backend tests go in a NEW `vansales.spec.ts`, so `delivery.spec.ts` (owned by groups 2, 14 and 18, and reworked by DOS-172) merges untouched.
- (j) Screens import only `@dos/ui`, `@dos/offline/react`, `@dos/api-client/react`, `@dos/domain`, `@dos/contracts` (types) and expo-router. The money rows are built in the screen from `Row`/`Txt`/`Money`. No kit change; `src/lib/ui.tsx` (owned by group 5) is not edited.
- (k) Files outside the list are not edited. docs/22 gets a §8 row and a §11 line only (no §4 node changes: the D6 node there is Collect, and its wording still holds). The main session writes them in its single docs pass after the money, DOS-171 and DOS-172 merges. docs/23 needs nothing, because D6 makes the same calls.
- (l) FIXTURES THAT SURVIVE DOS-172 RULE C (critic overlap 1, gap loadsheet-fixtures). `vansales.spec.ts` never departs a trip that carries a packed bill. Its trips use S-28's fixture: stops with `invoiceIds: []`; the planned starting figure given as the stop's own `plannedCollectionPaise` (agreed old dues, contracts/delivery.ts:676); van stock on a sheet the manager creates and confirms before depart. Such a trip departs 200 on main today, and under Rule C with either founder answer ("has none and van sales on departs as before"). If a later edit ever needs a planned bill here, the bill goes in the sheet's `orderIds` and is confirmed before depart; depart never dispatches it. DOS-172 merges last and runs the whole core suite, this file included. It may swap in its shared load-out helper without changing any assertion.
- (m) `MoneyProps.value` is `number | null` (types.ts:89): every figure is passed with `?? null`, so a missing quote shows the em dash, never ₹0.00.
- (n) LOCK ORDER. The increment runs after `lockTrip` (:63), in the same trip-then-stop order that `walkStop` (:169), `deliveries.record` (:103/:109) and `collections.record` (:89/:112) already use, so it adds no new order. `startStopInTx` (trips.service.ts:822-823) and its arrive/fail siblings take the stop first and the trip second, which is the reverse. That is pre-existing, and this slice widens it only to stops already finished, where a start or arrive is a replay. Handed on as an S-item for the main session: a start on the same stop racing a van sale can end in a 40P01 deadlock, and one request is refused.
- (o) Settlement is untouched. `planned_collection_paise` is display only: `settlement.service.ts`, `performance.ts` and reporting never read it, so money's receipt count (DOS-169) and this figure cannot disagree. D6 sends no `collect`, and a settlement takes the trip row before anything else, so it cannot cross the stop-row update.
