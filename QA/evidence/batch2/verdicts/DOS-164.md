# DOS-164 — architect verdict (Fable, 2026-09-13)
**Verdict:** APPROVE WITH AMENDMENTS

Root cause holds and is complete for kit overlays. On main `Sheet` (native/feedback.tsx:139) and `Dialog` (:226) are two sibling `<Modal>`s. RN 0.86.3 presents a modal from `[self reactViewController]` (RCTModalHostViewComponentView.mm:150-156), which walks `nextResponder` to the first UIViewController (UIView+React.m:282-292): a sibling Dialog reaches the screen's controller, whose presenter already presents the Sheet, and UIKit refuses (the logged "already presenting"). `ensurePresentedOnlyIfNeeded` sets `_isPresented = YES` before the present call (:165-182), nothing clears it on refusal, `updateProps` only re-runs the gated check (:300-301), and only `prepareForRecycle` resets it (:271-278) — hence "dead until unmount or relaunch". A host view that is a DESCENDANT of the presented modal's content resolves to that modal's controller instead, which is why rendering the second overlay INSIDE the first Modal is the right direction. No second cause in scope: 0 POST proves no server path; web stacks divs; Android stacks dialog windows (android-manager-results.json:7, :243, :269 PASS). Two adjacent non-kit presenters (RupeeInput's pad Modal money.tsx:415, expo print/share) are outside the store — see findings. Contract, permissions, schema, money, ledgers, sync: untouched; `SheetProps`/`DialogProps` (types.ts:376-395) unchanged; screens unchanged; web/feedback.tsx unchanged. The design is minimal for a shared kit: one store, one outlet, two panels extracted.

## Amendments (binding)
(a) A layer is a `<View style={absoluteFill} accessibilityViewIsModal>` inside the host's Modal, never a nested `<Modal>`. A nested Modal is a second (chained) UIKit presentation; it is refused while the host is still animating in and then sticks at :165-182 — the same failure class. Rule: one `presentViewController` per kit overlay stack, ever. The native-overlays guard also asserts the `OverlayOutlet` body contains no `<Modal`.
(b) Store invariants after every `flush()`, both asserted by the exhaustive spec over every open/close/unmount order of two Sheets and two Dialogs: (i) `presentedRoots().length <= 1`; (ii) every overlay whose last intent was open is a root, or a layer whose `hostOf` is a presented root — the finding's actual invariant ("never open but unseen"). The store repairs, it never throws.
(c) `setLayer(id, render)` emits only when the value changes (`null → null` is a no-op) and `request(id, open)` with an unchanged `open` records nothing, so a root Sheet's re-render (every field-app screen, every keystroke) bumps no version and re-renders no outlet.
(d) The interim commit (an `open` flip before its flush) renders a root's `<Modal visible={false}>` and never unmounts a Modal that has been presented; a root's Modal stays mounted with `visible={false}` after close so the iOS dismissal animates; a layer's Modal is never mounted. `useLayerContent` calls `setLayer` from a layout effect only, never during render.
(e) D7 fallback pre-authorised. e2e check (h) and verify step 5 walk the owner backward swap on the PRE-FIX main Metros first. If the backward swap fails there too, the builder applies "layer on coincidence" (D7 b) ONLY to a close and an open in the same flush (the retained root hosts the opener), (h) then expects the panel to reappear with no refusal, and the verifier records which branch shipped. No return trip to me.

## Risks for the builder
- A layer renders at its HOST's tree position: same `<Screen>` in all 22 files, app providers above; never read route hooks in a Dialog/Sheet body (the README rule is the only fence).
- Controlled TextInput in a layer: the outlet must update only from the store; any context consumer between outlet and layer element that re-renders on its own would push a stale `value` and jump the caret. Keep the wrapper a bare `View`.
- Retention unmounts `SheetPanel` (children lose local state) exactly as Modal.js does today (`isRendered`, :267-283); do not try to keep the panel mounted.
- Rule 6 promotion and D7 (a) both present a fresh Modal while another's dismissal may animate — the one UIKit race left; forward is proven (ios-results.json:369-375). If a walk shows it, (e)'s coincidence rule is the fix, not a retry loop.
- The `covered` panel needs BOTH `accessibilityElementsHidden` and `importantForAccessibility="no-hide-descendants"`; `accessibilityViewIsModal` hides only siblings. Whether XCUITest drops the covered Close from `labels` is unproven — assert dialog labels present, not Close absent.
- Non-kit presenters are unchanged: a kit overlay opened while expo-print/share/picker is up can still be refused and stick; out of scope, do not add a retry.
- Expo Go only: no native code, no `FullWindowOverlay`, no reanimated dependency.
- Rebase note for L19/L20/DOS-158: edit inside `SheetPanel`/`DialogPanel`; the guard fails a raw `<Modal visible={open}>`.
