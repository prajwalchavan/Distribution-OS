# DOS-117 — architect verdict (Fable, 2026-09-13)
**Verdict:** APPROVE WITH AMENDMENTS

Root cause confirmed in code and dos_qa: only postings (`refreshOutstandingFor`, outstanding.ts:321) and the owner's `rebuildAgeing` (receivables.service.ts:1435) write `retailer_outstanding_summary`; `computeOutstanding` ages against `asOf` (outstanding.ts:235-237); worker/main.ts and jobs/reporting.ts register no ageing queue (`pgboss.schedule` has 10 rows, none ageing). No second cause: `checkCredit` ages live from `oldestDueDate` (credit.ts:73-75); the 09:00 sweep, `loadOutstanding`, `listOutstanding`, the synced rows and `owner_summary` all read the same stale table and are cured by the same re-date. The precedence change in rollup.ts:203-211 is required, not adjacent: tarsun `daily_tenant_stats` 09-11 = 472821900/266970000 and 09-12 = 442437400/268691700, exactly those days' snapshot sums, so a nightly snapshot would freeze today's point at 00:20. The design is minimal: no contract, permission or schema change; money stays integer paise; both writers are upserts; the worker runs as each tenant's system actor under `withTenant` (rollup.ts:45-49 pattern); `ageing-rebuild.ts` is exported only through `receivables/worker.ts`, never `index.ts`. Fan-out per tenant on a `stately` queue keyed tenant+day is right (plans.js:675 index; dos_qa queues are all `standard`, so the plan's warning is real). Run-time `businessDate()` in the job is the correct guard against a late retry re-dating backwards.

## Amendments (binding)
(a) `createQueue(RECEIVABLES_AGEING_REBUILD, { policy: 'stately', retryLimit: 3, retryDelay: 300, retryBackoff: true, expireInSeconds: 3600 })`. Stately allows one created plus one active job per key; a job that passes the 900 s default expiry is re-fetched while its first handler is still paging, doubling a large tenant's pass. The catch-up queue keeps the default expiry.
(b) `rebuildTenantAgeing` takes its page lock with `select retailer_id from retailer_outstanding_summary where tenant_id = $t and retailer_id in (…) order by retailer_id for update` INSIDE the same `withTenant` transaction as `rebuildAgeingPage`, and locks nothing else (no invoices, receipts or allocations rows). Every posting path locks exactly one summary row last in its transaction (receivables.service.ts:424/470/505/573/1818, invoices.service.ts:682/840, receivables.sync.ts:154, integrations/commit.ts:367-371), so this order is deadlock-free; adding any other lock breaks that proof.
(c) Because DOS-117 lands on h1 after DOS-007, it MAY edit `backend/worker/src/main.ts:80-82` to name the two ageing queues in the start-up line; `receivables/worker.ts` and the `./receivables` export in `backend/libs/core/package.json` are appended to, never recreated.
(d) The three worker tests must reach the queues through `registerReportingJobs` and the stored handlers (the plan's wiring-test shape), and the fake boss must throw on a send to an uncreated queue; if `vi.mock('@dos/core/reporting')` does not intercept under the worker preset, give `scheduleAgeingRebuilds`/`finalizeRollups` an optional `tenants` override parameter (default `activeTenantIds`) instead of a global — never a real 2 000-tenant probe of the dev database in a spec.
(e) `rollup.ts` dues precedence is exactly: `isToday` → live summary sums; else an existing `daily_tenant_stats` row → keep; else the day's snapshot when `rows > 0`; else 0. `refreshOwnerSummary(tx, tenantId, day, liveRow)` at :267 is untouched. Rewrite the :180 comment and property 4 (:34-35) to say so.
(f) Record in docs/18 (build log) and QA/13 that docs/plans/receivables.md §7's 00:30 `receivables.ageing_snapshot` job is realised as the 00:20 finalize's per-tenant `receivables.ageing.rebuild` fan-out plus a start-up `receivables.ageing.catchup`, run as each tenant's system actor. docs/22 does not change (no founder decision).

## Decisions
- technical: per-tenant pg-boss job, not an inline loop in the finalize (rollup.ts property 2, docs/20 rule 5, 900 s expiry).
- technical: catch-up criterion = any dues row dated before today, OR dues rows exist and no `ageing_snapshots` row for today; a shop with no summary row never makes a tenant stale. Served by the summary PK prefix and `ageing_snapshots_as_of_idx`; no migration.
- technical: the rebuild job ages to `businessDate()` at RUN time; the payload's `day` feeds only the singleton key and the log.
- technical: each rebuild sends its tenant's today rollup (`reporting-rollup:<tenant>:<today>`) after the pages commit — that is my "before the owner rollup", per tenant.
- technical: snapshots are written for every retailer of the tenant (same as the owner's rebuild today); bounding growth is a separate finding, not this fix.
- technical: the owner's `receivables.ageing.rebuild` keeps its input, output, OWNER_ONLY role, single transaction and idempotency key; only the page body moves to `rebuildAgeingPage`.
- technical: DOS-015 stays a separate P3 (button sends no request); its severity note is QA bookkeeping and this fix leaves that endpoint unchanged.
- FOUNDER DEFAULT: none — the visible change (overdue rises on quiet mornings) is the documented behaviour of docs/plans/receivables.md §7 and contracts receivables.ts:711/727.
