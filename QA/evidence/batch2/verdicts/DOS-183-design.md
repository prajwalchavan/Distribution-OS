# DOS-183 — architect design (Fable, 2026-09-20)

P1 on the DOS-167 P0 path; the one clause of founder answer A (2026-09-14) that still fails: "unsent changes go FIRST at that person's next sign-in". Measured on a real browser (QA/findings/12 §DOS-183): sign-in over a kept file pulled first and uploaded at +60 753 ms; a page that booted offline made no call for 49.5 s after the `online` event. Read on main: engine.ts, react.tsx, connection.ts, docs/27 §4/§5/§12/§14, identity.test.ts, test-support.ts. Frontend-only; no contract, server, kit or app-screen change.

## Root cause (confirmed by reading)

1. `engine.ts:452-488` `start()` runs `sync('start')` and never a flush. The only pre-pull flush is `applyManifest`'s stale branch (`:1088-1097`), reached only when the file has no `schemaVersion` — i.e. only after `end()`'s `dropReadSet`. A `stop()` (forced 401, provider re-mount), a crash, a closed tab or a sign-out from another tab leaves the manifest in the file, so the next start is "not stale" and pulls a delta; the queue waits for the 60 s poll, and the poll itself (`:1876-1886`) pulls before it flushes.
2. `setNetworkHint(true)` (`:1012-1023`) computes `was = this.radio()`, and `radio()` falls back to `navigator.onLine` when no hint was ever given — already `true` inside the `online` handler — so a page that booted offline (`radioOn === null`) returns early and never drains. Native apps pass no hint at all (only react.tsx's window events; DOS-068 is the NetInfo item), so this is a web gap today and a native one the day NetInfo is wired.
3. Latent, on the same path: `flush()` (`:1397`) builds `flushChain` with `.then` only, so one thrown `claim`/`settle` (a store error) leaves the chain rejected and every later flush of that engine dead. Today nothing awaits it at start; the fix below does, so it must be closed with it.

## Design — three rules, one private entry point

R1 — THE QUEUE GOES BEFORE THE HANDSHAKE, ON EVERY PATH THE ENGINE SCHEDULES ITSELF. One private `drain(reason)`: `await this.flush({ pullAfter: false }).catch((e) => this.note(e, \`flush(${reason})\`))` then `await this.sync(reason)`. Callers: `start()` (replacing the bare `sync('start')`, after `bringUp` and its `sending→queued` revert, so the flush sees the recovered rows), `setNetworkHint(true)`, and the poll tick (today `sync` then `flush`; becomes `drain('poll')`). `flush()` gains `{ pullAfter?: boolean }` (default true, unchanged for `enqueueMany`, `retry`, the retry timer, `sendNow`): `flushInternal` runs `sync('after-upload')` only when `pullAfter`. The `applyManifest` stale-branch flush stays as a guard (it now finds `pending === 0` on every scheduled path; it still matters for a screen's own `engine.sync(...)`). Order at a start over a queue: `upload → manifest → pull` — the upload precedes the handshake, not only the pull; `sync.upload` needs no manifest (protocol is a constant, the server validates tables and role and answers 2xx with `sync_errors`), and this is already what the stale branch did before the drop.
What must NOT change: the pull still runs after the flush on every path (a flush that sent nothing, failed, or hit `upgradeRequired` falls through to `sync`); the outbox stays FIFO by `seq` in ≤50-op/4 MiB batches with the original `opId = idempotencyKey` (`claim`/`settle`/`release` untouched); the identity claim at open still precedes everything (a foreign queue is wiped before any flush); `end()`'s `settled()` still awaits `flushChain`; screens still never call `sync.*`.

R2 — A RECONNECT IS NEVER SWALLOWED, AND NO POLL IS ADDED. `setNetworkHint(true)` decides on what the ENGINE knew, never on `navigator.onLine`: `const believed = this.radioOn === true && this.reachable`; then set `radioOn`, `reachable = true`, reset the backoff, emit; `if (!online || believed || !this.started) return`; clear the retry timer (the reconnect IS the retry); `void this.drain('reconnect')`. `radio()` is unchanged for `status().online`. Consequences: a page that booted offline (`radioOn` null, `reachable` false after the failed start) drains on the first `online` event; a spurious `online` (interface change) on a page that never gave a hint costs one drain — a probe, which docs/27 §10 already calls the honest thing; a page whose calls failed without an `offline` event drains too (`reachable` false). `sync()` still returns early while a pull is in flight, so a reconnect landing under a hung manifest call (20 s deadline) defers to the poll — acceptable; optional one-liner: a `syncAgain` flag re-run once at the end of the in-flight sync.

R3 — A FLUSH THAT FAILS BLOCKS NOTHING. `flush()` links as `const link = this.flushChain.then(run, run); this.flushChain = link.catch(() => undefined); return link`: the caller still sees the rejection, the chain never carries it forward. `drain` catches and notes it (`lastError` carries the sentence for the strip); the pull follows at once. Worst case before the first pull: one request deadline (20 s), then the retry timer owns the queue at 1 → 2 → 4 … 60 s.

## The order guarantee, as a test asserts it

Clock: the transport's CALL ORDER (the `order[]` a recording transport keeps; on a browser the network log's request-start times), never wall-clock and never the poll interval. Statement: for an engine whose outbox holds ≥1 `queued` or recovered `sending` op when `start()` finishes opening, its first `sync.upload` call is recorded before its first `sync.manifest` and first `sync.pull` call, and that pull carries the file's cursor if the read set was kept (delta) or none if it was dropped; when the upload fails (network, 5xx, thrown) the manifest and pull still follow in the same start, with no timer between; when the queue is empty no upload is made and manifest → pull run as today. On reconnect: an `upload` is recorded after `setNetworkHint(true)` before any `pull`, with no timer between. On the poll: `upload` precedes that tick's `manifest`/`pull`. Every op appears in exactly one upload call (the FakeServer's `applied` map).

## Risks, answered

- Thundering flush on a cold start: one engine per identity (provider deps unchanged), one chain, ceil(N/50) serial requests before the first pull — the same requests the device made a minute later before; the strip says "N waiting" then "Updated" honestly. Across lakhs of devices the request count is unchanged.
- Flush racing a pull: `drain` serialises the scheduled paths; a screen's `engine.sync('order placed')` may still overlap a flush as today — safe: one transaction per page, and a pull never overwrites a `_pending` row (§5 rule 3).
- An op sent twice: the chain serialises; `claim` marks `sending` before the request; the recovery revert runs before the first flush; the retry timer is cleared on reconnect; a lost reply replays by `opId`.
- A stale manifest over fresh local rows: the upload lands before the handshake, so a stale manifest drops tables with `pending === 0` in the common case; when the upload failed, today's rule holds — the outbox row survives the drop (a system table) and goes on the retry, only its local `_pending` marker goes with the table (§14 row 3, unchanged).
- A second tab: OPFS access handles are exclusive, so the second tab's open answers an announced memory store (ruling 3 (cc)) with an empty outbox; the rule is vacuous there and the tab holding the file follows it. Nothing cross-tab is added; a file closed with a queue waits for the next open, which R1 covers.
- A 401 in the start flush (token died while offline): the api-client refreshes once; a dead refresh clears the session, the provider stops the engine, the file keeps the queue (§14). Unchanged.
