# Offline sync design

> **Superseded 2026-09-05 (founder, docs/22 §8 / docs/26 §5):** offline sync is built in-house — the existing `/sync/upload` path plus a per-table delta pull keyed on `(tenant_id, updated_at)` into SQLite on the device. PowerSync is not used. The rules below (upload never 4xx, `sync_ops`, GPS outside the queue, LWW with backend veto) still apply; the transport paragraphs about PowerSync Cloud, logical replication and residency do not. **The live design is §0 "Our own sync" immediately below; §7.1–§7.6 are kept for the rules they still carry and for the history of what was rejected.**

## 0. Our own sync (2026-09-05)

> **Client side (device):** the binding design for `@dos/offline` is `docs/27-offline-sync-client.md` (2026-09-06). This section is the server side.

No vendor, no logical replication, no second database process: the device keeps SQLite and talks to four procedures of the `sync` contract (`backend/libs/contracts/src/sync.ts`), all over the same access token and the same permission matrix as every other endpoint. `SYNC_PROTOCOL_VERSION` is the wire version; a batch that carries a different one is answered `upgradeRequired` with every op rejected, never 4xx.

**Who syncs.** The five staff apps (owner, manager, sales, warehouse, delivery) hold the read set AND the write queue. The retailer app holds the READ half only — `sync.manifest` and `sync.pull` are `ANY_MEMBER`, so the shop keeps its own bills, orders and dues on the phone and opens them in a dead spot, while `sync.upload` and `sync.errors.list` stay `STAFF`: a shop places an order online through `orders.*` and never carries a device queue. That is a widening of the read path only; RLS narrows every pulled table to the shop's own rows, and no table a shop can hold has a cost column.

**Manifest — `GET /sync/manifest`.** Asked once per app start and after a role or distributor switch. It answers, for the actor's role, every table the device should hold with its `primaryKey`, its `columns` (name + the JSON type the column arrives as + nullability) and `writable` (false for the download-only tables — prices, schemes, catalog). Two fields make it a schema contract rather than documentation:

- `schemaVersion` — a hash of the protocol version and the table list. The device stores it. Send it back as `knownSchemaVersion`; when it differs the local tables are stale: drop them, re-create from `tables`, and re-snapshot with a `pull` that carries no `since`. `changed: false` means keep the rows and pull a delta.
- `role` — the role the manifest was built for, so a phone that signed in as somebody else notices it holds the wrong read set even when the hash matches.

A column a pull spec strips (a scheme's funding source, anything carrying cost) is absent from the manifest as well, so the device has nowhere to put it.

**Pull cursor — `GET /sync/pull`.** Rows changed since an opaque cursor, across the tables registered for the role in `SyncRegistry` (or the subset the device names in `tables`; the cap is above the longest read set, so a device may always name every table it holds and catch one table up without re-reading the rest). The cursor is base64url `{v:1,t:<iso>}` and is issued at the server clock **minus a 5 s overlap**, so a row committed by a transaction that started before the read is still caught next time — the device upserts by primary key, so seeing a row twice is free. `limit` is shared across the tables in the call; `hasMore` means at least one table filled its share, and the device repeats the call **with the cursor the last response gave**, not with the one it sent, until `hasMore` is false. The cursor advances even mid-page — to the earliest point every table has finished, ties completed — because one that stood still handed a device that had fallen behind the same page for ever; see the client contract below. `asOf` is what the "updated at" line on the screen shows. Ordering inside a table is `updated_at, id`, which is why every synced table carries the `(tenant_id, updated_at)` index (migration 0012).

**Tombstones.** A row that is deleted, or that leaves the actor's read set without being deleted (a beat reassigned to another rep, a trip closed, a shop unlinked), comes back as its id in that table's `deleted` array; the device deletes it locally. The owning module's pull spec is what reports them — RLS makes such a row simply invisible on the next pull, which is silent, so a module whose rows can leave a scope must return the ids rather than rely on absence. A device offline past the tombstone retention re-snapshots instead: that is the second job of `schemaVersion` and of a `pull` with no `since`.

**LWW with a backend veto.** A device op that edits an existing row carries `baseUpdatedAt` — the `updated_at` the device's copy had when the user changed it, exactly as `pull` delivered it. The server applies the write only if the row has not moved on since; if it has, the op is rejected with code `stale` (`SYNC_REJECTION_CODES.stale`), a `sync_errors` row lands in the "Needs attention" tray, and the response is still 2xx — the queue is never wedged, and the device re-reads the row before offering the edit again. Inserts and insert-only tables (a receipt, a visit, a delivery, a trip count) carry no `baseUpdatedAt` and cannot be vetoed this way; protected columns and the per-entity rules in §7.3 are unchanged, and so is the idempotency contract of §7.4 (`sync_ops` by `(tenant_id, device_id, op_id)` for ≥ 180 days, plus `UNIQUE(tenant_id, idempotency_key)` on both ledgers).

**The read set, as built (2026-09-06).** Thirty-seven tables are pull-able; `SYNC_PULL_TABLES` in `@dos/db` is the list and `SyncRegistry.registerPull` in the owning module is the server side of it, so the two are compared directly, per role, in `libs/core/src/modules/sync/sync.coverage.spec.ts`. A role receives the tables `sync-tables.ts` names for it plus, for the desk (owner, manager, accountant), everything: a rep holds 21, the crew 19, the godown 13, a shop 18. Three shapes are served by one generic reader: ordinary tenant tables keyed by `id`; the two with no `id` at all (`stock_balances` keyed `lot_id, location_id`, `retailer_outstanding_summary` keyed `retailer_id` — that key is what the manifest publishes and what a tombstone carries, joined by `:`); and the four global curated catalog tables, which have no `tenant_id` and whose tombstones are filed under the sentinel `'*'`. Each module also bounds its own rows by age — 90 days of bills, orders and receipts, 30 days of godown paperwork, 14 days of the road — so a first sync is bounded work on a budget phone (docs/20).

**The client contract for a pull response, in order.**

1. **Apply `deleted` BEFORE `rows`.** A row that both moved and is still visible to this reader arrives in both lists (a soft hide is per-reader: the shop that left rep A's beat joined rep B's, and both devices pull the same tombstone; the server subtracts only the ids the CALLER can still see). Applying them the other way round deletes a row the same response just delivered.
2. **Upsert by the manifest's `primaryKey`**, not by `id`: two tables have no `id` column.
3. **Repeat while `hasMore`, always sending back the cursor the LAST response gave.** The cursor advances even mid-page — to the earliest point every table has finished — so a device that fell behind finishes its read set. It is microsecond-precise on purpose: a millisecond-truncated bound re-reads its own boundary rows for ever.
4. **A pull with no `since` is a full snapshot** and carries no tombstones — there is nothing on the device to delete yet. That is also the recovery path when `schemaVersion` changes or a device has been away longer than the 180-day tombstone retention (`SYNC_TOMBSTONE_RETENTION_DAYS`, swept hourly by the worker).

**The veto, as built.** `SyncService.upload` calls `vetoIfStale` for EVERY op of every table before the owning module's handler runs, so no module can forget it: an op carrying a `baseUpdatedAt` older than the server's row is rejected `stale`, a `sync_errors` row lands in the tray, the response is 2xx, and the handler never ran. An insert carries no base and cannot be vetoed.

**What a shop's device gets, exactly (2026-09-06, independent gate).** Eighteen tables, and three rules that RLS alone does not give:

1. **`retailer_links` and the price lists are narrowed by the module, not by the database.** `retailer_links_read` is `tenant_id = … OR user_id = …` (the OR is the switch-distributor screen) and `price_lists` / `price_list_items` are `tenantReadPolicy` because the pricing engine runs on the rep's phone — so for a signed-in shopkeeper the tenant half of both is true of every row in the distributorship. `pricing.priceLists.list` is `STAFF` in the matrix, which is what used to stand in the way; a pull has to say it itself. A shop therefore receives the links of its OWN shops and the price lists the engine would resolve for it (the default list plus the one matching its tier) — never another customer's login, never the slab the shop down the road is on (never-list 9).
2. **Nothing in a shop's manifest is `writable`.** `writable` answers "may THIS role send this table back", not "does a handler exist": `sync.upload` is `STAFF`, so a table advertised writable to a shopkeeper would have the app build a queue whose every flush is a 403 — the 4xx that wedges a queue for good.
3. **A column published as `integer` or `number` arrives as a JSON number.** Paise are `bigint` in Postgres and node-postgres hands a bigint back as a string; the pull narrows exactly the columns the manifest published as numeric (never one that merely looks numeric — a shop code, a phone, a GSTIN, an HSN stay strings, and so does `numeric`), guarded by `Number.isSafeInteger`.

**Unchanged from the PowerSync design:** the upload never answers 4xx (§7.3), GPS points bypass the queue (§7.5), and the sync UX is a status dot rather than a "sync now" button (§7.6).

### 7.1 Engine and residency

PowerSync over Postgres logical replication (R07 §3): server-authoritative, per-user partial sync via Sync Streams keyed on JWT claims, FIFO upload queue, per-field LWW with backend veto, attachment queue, `@powersync/react-native` 2.2 with op-sqlite. ElectricSQL (no write path, cloud winding down), WatermelonDB (dormant), Replicache (maintenance) and Zero (rejects offline writes) are ruled out. RDS: `rds.logical_replication = 1`, a `powersync` publication limited to synced tables (never `FOR ALL TABLES`), replication role, TLS, security group restricted to PowerSync egress IPs, `max_slot_wal_keep_size` set with a slot-lag alarm (R07 §3.2 rule 8).

**Residency (resolved).** Week 1: verify whether PowerSync Cloud offers an India region. If yes, use it. If not, proceed on Cloud for the pilot with the fact recorded in the security note (DPDP does not mandate residency today, R08 §6.1) and keep the self-hosted Open Edition on ECS Mumbai as the exit, taken only when a paying tenant or brand partner demands residency — the Open Edition has no dashboard and no custom write checkpoints (R07 §3.2 rule 9) and is real ops load for one person. `frontend/libs/offline` is the only PowerSync-touching code. Cloud Free at pilot, Pro ($49) at ~10 tenants; C's self-host-by-10 for cost is rejected.

**Auth spike (resolved).** Better Auth over R07's Supabase Auth, because the `jwt` plugin's JWKS keeps issuance in the API. Week 1 includes a one-day spike proving a Better Auth JWT with `{sub, tenant_id, role, beat_ids}` drives `auth.parameter()` and the per-beat parameter query; fallback is a tiny token-exchange endpoint minting PowerSync JWTs from the Better Auth session.

### 7.3 Write path and conflict rules

The client writes domain rows locally; `/sync/upload` (protocol v1) maps each CRUD transaction's table set to a **command** (`PlaceOrder`, `RecordVisit`, `RecordReceipt`, `CompleteDelivery`, `ConfirmPack`, `RequestBargain`, `EditRetailerProfile`, `RecordTripCounts`) and dispatches it inside one DB transaction with tenant/actor settings from the JWT.

| Entity                    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sales order (create)      | Insert-only from devices with `quoted_unit_price`, `applied_rules`, `price_version`, `priced_at`. Server **recomputes at the same version**; unequal at the same version = tampering or engine bug → `sync_errors` + alert. If `pricing_date_mode = 'order'`, the quoted version is honoured even after a month-end scheme change (B's approval-on-every-mismatch rejected: it floods approvals). If `'delivery'`, reprice at the current version and open an approval only above the owner-set tolerance (default ₹0, adjustable) — A's rule. Business rejections return 2xx with `sync_errors(tenant_id, user_id, device_id, op_id, table, row_id, code, message_hi, message_en)` synced back to the device's "Needs attention" tray; 4xx is never returned to the uploader (it wedges the queue, R07 §3.2 rule 5). Server-owned fields flow back through the download stream.

### 7.4 Idempotency (resolved; Judge 3)

`sync_ops(tenant_id, device_id, op_id, outcome)` unique, retained ≥ 180 days; replay returns the stored outcome. `stock_ledger` and `journal_lines` carry `UNIQUE(tenant_id, idempotency_key)` so a replay after days offline cannot double-post even if `sync_ops` were pruned. Online oRPC mutations use `idempotencyKey` with Stripe semantics and 24-hour retention — the only place 24 hours applies. PowerSync does not advance a checkpoint while local mutations are unacknowledged (R07 §3.2 rule 6). CI replays a recorded upload log twice and asserts identical ledger state.

### 7.5 GPS points (the shared gap, resolved)

`trip_points` do **not** travel through the PowerSync queue: a device offline for hours would replay hundreds of GPS rows ahead of a cash receipt. The location task buffers points in a device-local table outside PowerSync and posts batches (30 s / 50 m, or on reconnect) to `POST /gps/points` with `(trip_id, device_id, ts)` for dedupe; the server drops points outside the trip window, upserts `vehicle_positions` and inserts `trip_points`. `device_id` is in every key — two-person crews carry two phones (C's `(trip_id, device_ts)` key rejected). Raw points pruned after 90 days by `dpdp.gps_retention`. The owner phone syncs `vehicle_positions`; the console reads an SSE feed of the same rows; latency ~30 s. **No WebSocket** (all judges): one fewer transport with sticky sessions behind an ALB.

### 7.6 Attachments and sync UX

Photos go through the attachment queue to S3 via pre-signed PUT; metadata rows sync normally; thumbnails cached locally. No "sync now" button: a status dot (synced / pending n / offline) and "last synced"; sync on connectivity change and app foreground; `expo-background-task` flushes on its ≥ 15-minute schedule when the app is closed.
