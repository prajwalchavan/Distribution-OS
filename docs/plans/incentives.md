## 1. Purpose and boundaries

Incentives turns a target the owner sets for one salesperson or delivery crew member — a metric (order value, pieces, lines, distinct outlets billed, visits, or cash+UPI collected), an optional brand scope, a period, and a slab table of payouts — into a live achievement percentage the rep can watch, and a computed (never paid) statement at period end. It **owns** `targets`, `achievements`, `computed_payouts` — no other module writes them. It is explicitly **compute only**: it never posts a journal entry, never touches `receipts`/`payroll`, and nothing it writes is a legal or accounting document (no series, no GST, no invoice/credit-note reference anywhere in its output).
It **reads** (never writes) rows owned by other modules to compute achievement: `sales_orders` / `sales_order_lines` (orders — value/pieces/lines/outlets), `visits` (retailers — visits), `receipts` (receivables — collections), and `product_variants` → `products` → `brands` (catalog — brand scoping). None of those modules has shipped a service surface incentives can call yet (`orders` exists but exports nothing achievement-shaped; `receivables`/`retailers`'s visit rollups don't either), so — exactly like `modules/orders/credit.ts` already does for `invoices`/`allocations` before billing exists — the read lives as a plain, commented, read-only SQL join in `incentives.internals.ts` and in the worker job, not behind a fabricated service call. `daily_tenant_stats` / `daily_rep_stats` (reporting) are **not** the source of truth here: they carry no brand dimension and no distinct-outlet count, both of which a target needs, so incentives aggregates its own numbers rather than depending on a module (reporting) that hasn't shipped either.
It **calls out** to nothing that writes. Membership-role validation at `targets.upsert` (a target's `userId` must be an active salesperson or delivery member) is the one exception worth naming: it is a single-row read of `memberships`, owned by `tenancy`, done the same `credit.ts`-style way.
It **emits** `IncentiveStatementComputed` and `IncentiveStatementApproved` outbox events (notifications, reporting); nothing consumes an incentives event to change state elsewhere — this module is a leaf, the last one in the downstream chain (CLAUDE.md's module order ends `... → reporting → integrations → incentives`).
Retailers never appear anywhere in this module — it is entirely internal staff performance data. Warehouse staff are out of scope too (module scope is explicitly salesperson/delivery, per the founder's brief); a warehouse-role actor gets the same 403 as a retailer.

## 2. Endpoints

Contract file `backend/libs/contracts/src/incentives.ts`, exported as `incentivesContract`, mounted as `incentives: incentivesContract`. `IsoDate = z.iso.date()`. Every mutation extends `MutationBase` except `targets.whatIf` (a pure computation with no side effect, exactly like `pricing.quote` — no `idempotencyKey`, nothing written). GET inputs use `QueryBoolSchema`/`QueryIntSchema`; lists cap `limit` at 200 and page on the last row's `id`. Roles below are literal role lists for `backend/libs/contracts/src/permissions.ts` (values are role lists, `'public'` or `'authenticated'`) and are also the `requireRole([...])` tuple in the service — this module declares its own tuples (`INCENTIVE_OWNER = ['owner','system']`, matching today's `targets_write`/RLS exactly; `BACK_OFFICE` from `platform/authz.ts` for read/compute paths; `INCENTIVE_READERS = [...BACK_OFFICE, 'salesperson', 'delivery']`) rather than inventing new ones that drift from the RLS they sit in front of.

## 3. Schema changes needed

Everything else the module needs already exists in `backend/libs/database/src/schema/incentives.ts` (`targets`, `achievements`, `computed_payouts`, all three RLS-enabled). One new hand-written, expand-only migration `backend/libs/database/migrations/0006_incentives_guards.sql`, appended to `migrations/meta/_journal.json`:

1. `ALTER TYPE "public"."target_metric" ADD VALUE 'visits';` (own statement, first in the file, exactly like migration `0004`'s `ADD VALUE 'warehouse'`) — the founder's brief for this module names value/lines/**visits**/collections as the four slab dimensions, but today's enum has `outlets` where `visits` is missing entirely. Both stay (outlets = distinct shops billed; visits = beat calls made — different, both useful).
2. `ALTER TABLE targets ADD COLUMN name text;` — a short label ("Diwali Push — Campa") so a target reads as something on a list row instead of an anonymous `(user, brand, metric, period)` tuple; every list/leaderboard/console screen needs one.
3. `ALTER TABLE targets ADD COLUMN created_by text REFERENCES users(id);` — who assigned it, shown on the owner's target list; matches the audit convention already used elsewhere (`approvals.requestedBy`, `trip_settlements.approvedBy`).
4. `CREATE INDEX targets_tenant_period_idx ON targets (tenant_id, period_from, period_to);` — the only existing index (`targets_user_period_idx`) leads with `user_id`, so `progress.team` and an un-filtered `targets.list` (both tenant-wide, no `userId`) would seq-scan.
5. **RLS fix**: split `computed_payouts_back_office` (today `for: 'all'`, BACK_OFFICE only) into `computed_payouts_read` (`for: 'select'`, BACK_OFFICE **or** `user_id = current actor`) and `computed_payouts_write` (`for: 'insert'/'update'/'delete'`, BACK_OFFICE only). As written today, a salesperson or delivery actor cannot read their **own** `computed_payouts` row at all — which breaks the one screen this table exists for (docs/06's "computed incentive" on the rep's own Performance tab).

No new tables. `achievements` and `targets`' read policies are already correct (own row or back office) and need no change.

**Not a migration, but worth calling out**: `incentives.internals.ts` reads `memberships` (tenancy) and `sales_order_lines` → `product_variants` → `products` → `brands` (orders, catalog) as plain read-only joins, not through an exported service, because neither `orders` nor `catalog` exports anything achievement-shaped — the same accepted pattern as `modules/orders/credit.ts` reading `invoices`/`allocations` before billing existed. Nothing in this module writes any table it does not own.

## 4. Domain rules and edge cases

1. **`targetValue` is metric-typed, not always money.** The column is `paise()` (bigint) for historical reasons shared with every other metric — for `metric='value'` it is paise; for `pieces`/`lines`/`outlets`/`visits` it is a plain integer count stored unscaled in the same column. Never format a non-`value` target as currency. `achievements.achieved_value` follows the identical convention; `achievements.achieved_pieces` is filled **in addition**, from total pieces sold in the window, regardless of the target's own metric — a nicer progress-bar caption ("target 5,000 pcs of Campa, 3,120 pcs so far") even on a `value`-metric target.
2. **Metric → source table.** `value` = `Σ sales_order_lines.line_total_paise`; `pieces` = `Σ sales_order_lines.qty_pcs`; `lines` = `count(sales_order_lines.*)`; `outlets` = `count(distinct sales_orders.retailer_id)`; `visits` = `count(visits.*)`; `collections` = `Σ receipts.amount_paise` where `receipts.status IN ('collected','deposited')`. For `value`/`pieces`/`lines`/`outlets`, the join is `sales_order_lines → sales_orders` filtered to `sales_orders.salesperson_id = target.user_id AND sales_orders.state NOT IN ('draft','submitted','cancelled')` and, when `brandId` is set, `sales_order_lines.variant_id → product_variants → products.brand_id = target.brand_id`. `visits` reads `visits.user_id = target.user_id`; **`brandId` is meaningless for `visits`/`collections`** and is refused at `upsert` for `collections` (§2); a brand-scoped `visits` target is refused the same way (a visit isn't to one brand).
3. **Visits and outlets are salesperson metrics.** A delivery crew member does not run a beat; `upsert`/`bulkAssign` refuse (400) `metric IN ('visits','outlets')` when the target user's membership role is `delivery`. `value`/`pieces`/`lines`/`collections` apply to both roles — for delivery, `value`/`pieces`/`lines` are read from **van-sale** orders (`sales_orders.source = 'van_sale'`) attributed the same way, via `salesperson_id`; `collections` is identical for both roles (any staff member's `receipts.received_by`).
4. **IST windows.** `periodFrom`/`periodTo` are IST business dates (`businessDate()` from `@dos/domain`); the aggregation window is `[periodFrom 00:00:00+05:30, periodTo 23:59:59.999+05:30]` on the source rows' own date column (`sales_orders.created_at`, `visits.started_at`, `receipts.received_at`) — copy the `istStart`/`istEnd` helpers from `orders.internals.ts` rather than reimplementing.
5. **`payoutBps` only means anything for `metric='value'`** (basis points of `targetValue` paise); every other metric may only use `flatPaise` per slab. `upsert` refuses (400) a `payoutBps` slab on a non-`value` target.
6. **Slab evaluation is highest-achieved-slab-only**, not cumulative/compounding — the same convention `docs/17` §B fixes for pricing scheme slabs, applied here for consistency rather than because the founder specified it (flagged in §8). The matching slab is the one whose `[fromPct, toPct)` contains `achievedPct` (bps, uncapped — over-achievement can exceed `10000`); a slab with no `toPct` is open-ended (the top tier); `achievedPct` below every slab's `fromPct` pays `0`; slabs must not overlap (`upsert` does not validate this — a founder-console UI concern, not a server one) but if they do, the **highest `fromPct`** match wins.
7. **`achievedPct`** is always `round(achievedValue * 10000 / targetValue)` using `@dos/domain` integer helpers — never a float. `targetValue` is constrained `> 0` at `upsert` precisely so this is never a division by zero.
8. **Manager sees, never sets.** `targets_write` RLS is owner (+ `system`) only, unchanged by this slice — assigning a rep's incentive plan is money promised to staff, an owner decision. A manager's and accountant's role in this module is entirely read (`targets.get/list`, `progress.team`, `statements.get/list`) plus running the numbers (`statements.compute`, `targets.refresh`, `targets.whatIf`) — never creating a target or approving a payout.
9. **One statement per (user, period), summed across every target of that user in that period.** `statements.compute` refuses a `userId` with zero targets whose period exactly equals the input; it does **not** partially aggregate a target whose period only overlaps the requested window — periods must match exactly, by design (§8.7).
10. **Statements are immutable once approved**, mirroring the invoice-immutability convention elsewhere: `compute` 409s once `approved_by IS NOT NULL`; only `reopen` (owner) clears it. Nothing else about a `computed_payouts` row (its `id`, `user_id`, `period_from/to`) ever changes after creation.
11. **`achievements` is a worker-only cache**, never written from an `app_rw` request (§3's RLS is unchanged and stays `system`-only for writes) — `targets.refresh` enqueues a job rather than writing directly (§2, §7). Reads of it (`targets.get`, `progress.*`) may be up to one sweep interval stale (≤ 1 hour, §7); `statements.compute` reads the same cache and is therefore only as fresh as the last sweep or an explicit `refresh` — acceptable because it is called rarely (period end), not on every screen open.
12. **Bounded work** (docs/20): `payoutRule ≤ 10` slabs, `bulkAssign` userIds `≤ 50`, every list `limit ≤ 200`, the worker sweep batches `≤ 5,000` targets per run via a `(tenant_id, id)` cursor so one large tenant never holds the batch. No endpoint aggregates a tenant's whole order/receipt history — every achievement query is scoped to one target's `(userId, brandId?, metric, period)`.
13. **Never**: a purchase cost, margin, GST field, document number, or any receivable/journal write in this module; a target for anyone other than an active `salesperson`/`delivery` member; `payoutBps` on a non-`value` metric; a `computed_payouts` write from any role but the app-level owner-approve/owner-reopen paths and the BACK_OFFICE compute path; a retailer- or warehouse-role caller reaching any procedure (both are simply absent from every role list — no dead 403 branch to maintain).

## 5. DB-backed spec list

`backend/libs/core/src/modules/incentives/incentives.spec.ts`, `describeDb`, `bootTestApp([IncentivesModule])` (no other module is needed at boot — fixtures for `sales_orders`/`visits`/`receipts` are inserted directly with `@dos/db`, not through the orders/delivery/receivables APIs), keyed by a unique `run` suffix: one tenant, one owner, one manager, one accountant, one salesperson, one delivery member, one retailer, one warehouse member, two brands, a handful of confirmed orders (some tagged to each brand), some visits, some receipts.

1. `upsert creates a target and refuses a non-rep userId` → owner target for the salesperson succeeds; the same call with the owner's own id, or the retailer's id, is 400.
2. `upsert refuses visits/outlets for a delivery user, and payoutBps for a non-value metric` → both 400.
3. `upsert refuses an overlapping (user, brand, metric) target` → second call with an intersecting period is 409; a different brand or a non-intersecting period succeeds.
4. `bulkAssign creates one target per user in one transaction` → 3 users, one failing row (a retailer id among them) aborts all three (409, zero rows written).
5. `worker sweep computes achievedValue/achievedPieces/achievedPct correctly` → a tenant-wide value target and a brand-scoped value target for the same rep, seeded orders across two brands, sweep produces two distinct `achievements` rows matching a hand-computed sum.
6. `visits and collections metrics aggregate from the right table` → a visits target matches `count(visits)`, a collections target matches `Σ receipts.amount_paise` excluding a seeded `bounced` receipt.
7. `targets.refresh enqueues a job and writes nothing itself` → after the call, `achievements.computed_at` for that target is unchanged until the job runs.
8. `progress.mine returns only the caller's own targets` → rep A never sees rep B's row even when both exist in the same tenant.
9. `progress.team ranks by achievedPct desc for one metric` → three reps' value targets, ranks in the expected order; a `metric` mismatch is excluded, not zero-filled.
10. `statements.compute sums two targets of different brands into one statement` → `amountPaise` equals the hand-computed sum of both slabs, `breakdown` has two entries.
11. `statements.compute is refused once approved, and reopen re-enables it` → compute → approve → compute again is 409; reopen → compute again succeeds and changes `amountPaise`.
12. `whatIf writes nothing` → call it, then assert no new row in `achievements` or `computed_payouts` for the tenant.
13. `targets.remove is refused once a covering statement exists` → 409 after `statements.compute` for that user/period; succeeds before it.
14. **RLS/role — salesperson**: `targets.upsert`, `bulkAssign`, `remove`, `statements.approve`, `statements.reopen` are all 403; `progress.team` is 403; a direct `withTenant` select as `salesperson` on another rep's `targets`/`achievements`/`computed_payouts` row returns 0 rows.
15. **RLS/role — delivery**: same refusals as salesperson; `progress.mine` returns only the delivery member's own rows.
16. **RLS/role — manager**: `targets.upsert`/`bulkAssign`/`remove`/`statements.approve`/`statements.reopen` are 403 (owner only); `statements.compute` and `progress.team` succeed.
17. **RLS/role — accountant**: identical to manager (may compute and read, may not assign a target or approve a statement).
18. **RLS/role — retailer and warehouse**: every procedure is 403 (undeclared role on every path — `permissionFor` returns `undefined`, treated as a refusal).
19. **tenant isolation**: a target created in tenant A is `NOT_FOUND` on `targets.get` and absent from `targets.list`/`progress.team` for an owner of tenant B; a direct select as tenant B's role returns 0 rows.
20. `401 without context` on any GET.
21. Extend `backend/libs/database/src/rls.test.ts`: a `salesperson`/`delivery`-role session can `SELECT` its own `targets`/`achievements`/`computed_payouts` rows and zero of another rep's; its `INSERT`/`UPDATE` on `targets` and `computed_payouts` is rejected by the write policies; a non-`system` `app.actor_role` cannot `INSERT` into `achievements` at all (RLS, not just the app-level 403).

3. **`achievements` rows for every this-month target**, computed for real from the 14 working days of orders/visits/receipts `seedSales`/`seedReporting`/`seedDelivery` already inserted — expect `achievedPct` well under `10000` (mid-month against a full-month target), which is the realistic "in progress" state the Performance tab should render.

## 7. Worker jobs / outbox events

**Outbox events** (written by `statements.compute`/`approve` in the same transaction, relayed by the existing worker relay):

| event | aggregate | payload | consumers |
| --- | --- | --- | --- |
| `IncentiveStatementComputed` | `computed_payout` / statement id | `{computedPayoutId, userId, periodFrom, periodTo, amountPaise}` | notifications ("your estimated incentive for Feb is ₹X, pending approval"), reporting |
| `IncentiveStatementApproved` | `computed_payout` / statement id | `{computedPayoutId, userId, periodFrom, periodTo, amountPaise, approvedBy}` | notifications ("approved: ₹X"), reporting |

**pg-boss jobs** (registered in `backend/worker`):

- `incentives.achievements.sweep` — hourly, `withSystem()` (`app_worker`, BYPASSRLS, cross-tenant): recomputes `achievements` for every target whose `[period_from, period_to]` contains today, batched `≤ 5,000` targets per run via a `(tenant_id, id)` cursor (docs/20 rule 3 — never one unbounded scan). Read-only against `sales_orders`/`sales_order_lines`/`product_variants`/`products`/`brands`/`visits`/`receipts`; one `INSERT ... ON CONFLICT (achievements_target_idx) DO UPDATE` per target.
- `incentives.achievement.recompute` — on-demand, enqueued by `targets.refresh`, payload `{tenantId, targetId}`; the identical single-target computation, for a fast path when the owner just changed a target and wants the number now rather than waiting up to an hour.

**Sync handlers**: none. Every write in this module is a back-office/owner-console action done online (`targets.*`, `statements.*`); the rep-facing endpoints (`progress.mine`, `targets.get/list`, `statements.get/list`) are reads. Nothing here needs `SyncRegistry`.

## 8. Founder questions this brief had to assume an answer for

1. **Achievement basis before billing/delivery ship.** Assumed order-**booked** value (`sales_orders`, `state` past `confirmed`, excluding `cancelled`), not invoiced or collected-net-of-returns value — `billing`/`delivery` don't exist yet and this brief's own schema scope (reporting/orders/receivables, not billing) points the same way. Revisit once billing ships: a return or a cancelled-after-dispatch order would then silently keep counting toward achievement under this v1 rule.
2. **Delivery attribution for van sales.** Assumed van-sale order value/pieces/lines are credited via `sales_orders.salesperson_id`, and that whichever slice builds `delivery.vanSales.create` sets `salesperson_id = createdBy` for a delivery-role actor's van sale (today's generic `OrdersService.create` doesn't special-case this — flagged for that slice, not fixed here).
3. **Who may assign a target.** Assumed owner only (matches today's `targets_write` RLS verbatim); a manager can see the whole team's progress but cannot create or edit a target. If the founder wants managers to propose targets subject to owner approval, that is a new `status` column and a real product decision, not a role-list tweak.
4. **Slab evaluation style.** Assumed highest-achieved-slab-only (not cumulative), for consistency with `docs/17` §B's pricing-scheme convention — the founder specified slabs for incentives but not this evaluation rule specifically.
5. **No cap above the top slab, no payout below the lowest.** Assumed an over-achieving rep is paid exactly the top slab's amount (not extrapolated further), and a rep below the lowest slab's `fromPct` earns `0` — both common in FMCG incentive schemes but not stated by the founder.
6. **Payment stays entirely outside the system.** "Compute only, no payroll" was taken literally: `approve` is the last thing this module ever does to a statement; there is no export, no journal posting, no marking-as-paid. If the founder wants a later "mark disbursed" flag for reconciliation, that is a new column on `computed_payouts`, easy to add without disturbing this brief.
7. **Multiple simultaneous targets per rep.** Assumed allowed across different `(brand, metric)` combinations and refused only when identical and overlapping; a statement sums every target whose period **exactly** equals the requested window (no partial-overlap aggregation).
8. **Statement visibility before approval.** Assumed a rep can see a `computed`-but-not-yet-`approved` statement immediately (`approvedBy: null` in the response, not a hidden row) — matches docs/06's "computed incentive" reading like a live figure on the Performance tab rather than a payslip revealed only at month-end. If Tarsun's reps should not see a number until the owner signs off, `statements.get/list`'s RLS needs narrowing to `approved_by IS NOT NULL` for the rep-role branch — a one-line change to the migration in §3 if the founder disagrees.
