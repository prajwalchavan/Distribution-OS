## 1. Purpose and boundaries

Outbound fulfilment: it turns confirmed sales orders into picked, packed, invoiced and loaded goods, and it is the only module that writes `picklists`, `pick_lines`, `pack_confirmations`, `load_sheets` and `delivery_challans` (its five tables — nothing else may write them).
It calls **out** through exported services only: `OrdersService` (queue reads, order lines, `confirmed → picking → packed → dispatched` transitions, picked-quantity write-back), `InventoryService` (FEFO lot suggestion, `sale` rows at pack, `transfer_out`/`transfer_in` at load-out, reservation release), `BillingService.issueForPack` (the invoice at pack — optional injection so this module ships before billing), and `nextDocumentNumber` from `src/platform` for the `PICK` and `DC` series.
It never reads `sales_orders`, `sales_order_lines`, `invoices`, `reservations`, `stock_balances` or `trips` directly, and never touches `tenant_product_costs` — a picker must never be able to back a purchase rate out of a screen.
It publishes `outbox_events` (`PicklistStarted`, `OrderPacked` is emitted by orders, `LoadSheetConfirmed`, `DeliveryChallanIssued`) which the delivery, notifications and reporting modules consume; it consumes nothing.
Cycle counts, adjustments, transfers between godowns and the ledger itself stay in `inventory`; trips, stops, ePOD and collections stay in `delivery`; the invoice document, its numbering and its GST split stay in `billing`.

## 2. Endpoints

Role names below are the permission constants declared in `backend/libs/contracts/src/permissions.ts`. Two new local groups are needed there:

```ts
/** The godown floor and the desk above it. A rep or a shopkeeper is never here. */
const WAREHOUSE_DESK = ['owner', 'manager', 'warehouse'] as const satisfies readonly MembershipRole[]
/** Reads a crew needs on the road, plus the accountant who reconciles the paperwork. */
const FULFILMENT_READERS = ['owner', 'manager', 'accountant', 'warehouse', 'delivery'] as const satisfies readonly MembershipRole[]
```

`BACK_OFFICE` = `ROLE_GROUPS.BACK_OFFICE` (`owner, manager, accountant`); where a step needs the manager's PIN the list is `['owner', 'manager']` (the existing `ONBOARDERS`-shaped pair — declare it inline as `PIN_HOLDERS`).

Every mutation input extends `MutationBase` (`idempotencyKey`) and carries its own client-generated UUIDv7 `id`; every GET input uses `QueryBoolSchema`/`QueryIntSchema`; every list is `{ items, nextCursor }` with `limit` capped at 200 and `cursor` = the last row's UUIDv7 id (descending). No output in this module carries a purchase cost, a landed cost or a margin.

**Offline sync** (`warehouse.sync.ts`, registered on `onModuleInit` through `SyncRegistry`, exactly like `orders.sync.ts`):

- `pick_lines` — accepts `PUT` only. The device sends `{ picklist_id, order_line_id, lot_id, picked_qty_pcs, short_reason }`; the handler re-validates against the server's picklist and applies the same rules as `picklists.pick`. Every business fault is a `SyncRejection` (2xx + `sync_errors`), never a 4xx.
- `picklists`, `pack_confirmations`, `load_sheets`, `delivery_challans` — **not** registered. Packing issues a numbered legal invoice and loading issues a numbered challan; both allocate server-side numbers under a row lock (ADR 0001, docs/20 rule 13) and stay online-only procedures.

  ```ts
  fulfilmentQueue(tx: Db, filter: { locationId?: string; beatId?: string; state?: OrderState; expectedDeliveryDate?: string; limit: number; cursor?: string }): Promise<FulfilmentOrder[]>
  fulfilmentLines(tx: Db, orderIds: string[]): Promise<FulfilmentLine[]>   // { orderId, orderLineId, lineNo, variantId, qtyPcs, freeQtyPcs, pickedQtyPcs, sellCaseSize } — no rates
  applyFulfilmentEvent(tx: Db, orderId: string, event: 'start_picking' | 'pack' | 'dispatch', deviceId: string | null, reason: string | null): Promise<OrderRow>
  recordPick(tx: Db, orderId: string, picked: { orderLineId: string; pickedQtyPcs: number }[]): Promise<void>
  ```
  `applyFulfilmentEvent` uses `orderMachine.next()` via the existing `transition()`, writes `recordTransition`, and extends `emitOrderEvent`'s union with `'OrderPicking' | 'OrderPacked' | 'OrderDispatched'`.
- `BillingService` is injected `@Optional()`; its contract is `issueForPack(tx, { orderId, packConfirmationId, lines: { orderLineId, lotId, qtyPcs, freeQtyPcs }[], issuedBy }): Promise<{ id, invoiceNo, totalPaise }>`. When billing has not landed, `invoice_id` stays null, the response's `invoice` is `null`, and `packs.list?invoiced=false` shows the backlog.

## 4. Domain rules and edge cases

1. **Pieces are the only quantity that is stored.** `requested_qty_pcs`, `picked_qty_pcs`, `free_qty_pcs`, `qtyPcs` on every wire shape are integer pieces (`PiecesSchema`). Cases are display only, computed at the edge with `toCasesAndPieces(qty, caseSize)` / `formatQty()` from `@dos/domain`.
2. **Two different case sizes, and the picklist uses the lot's.** Sell-side pack = `coalesce(tenant_products.case_size_override, product_variants.default_case_size)` and is what the order was entered in; the **lot's** `stock_lots.case_size` is what the picker sees on the shelf (promo packs, docs/17 A2). `pick_lines.case_size` freezes the lot's value at picklist creation; when the lot has none, fall back to the sell-side pack.
3. **FEFO warns, it never blocks.** Lots are suggested `ORDER BY expiry_date ASC NULLS LAST, lot_id ASC` from `sellable_stock` at the order's location. A picker taking a later-expiry lot sets `fefo_override = true` and gets a warning in the response — the pick is still recorded (docs/design/R03: "warn, don't block" is right for a two-person warehouse).
4. **Nothing leaves stock before pack.** `picklists.pick` writes paper only. The `sale` ledger rows and the reservation close happen exactly once, inside `packs.confirm`, so a half-picked wave abandoned at 6 pm leaves the ledger untouched.
5. **The order state machine is the only way a state changes.** Use `OrdersService.applyFulfilmentEvent` — never write `sales_orders.state`. Legal moves here are `confirmed → picking` (`start_picking`), `picking → packed` (`pack`), `packed → dispatched` (`dispatch`). There is no `picking → confirmed`, which is why `picklists.cancel` is restricted to `status = 'open'`.
6. **A short pick is a smaller invoice, not a credit note.** The invoice is issued at pack from packed quantities (§4.4) and is immutable afterwards. Credit notes belong to the doorstep (delivery module). `sales_order_lines` are never edited to match a short pack — `pack_confirmations.short_packed` and the pick lines carry the fact.
7. **One pack confirmation per order, for all time.** Enforced by `UNIQUE(tenant_id, order_id)`. `dispatched → return_undelivered → packed` (an undelivered load coming back) re-uses the same confirmation and the same invoice; it never issues a second number.
8. **Numbers are allocated at issue, never at draft** (docs/17 B, numbering). `picklist_no` from `PICK` at create (internal, no legal weight); `challan_no` from `DC` only inside `loadSheets.confirm`; the invoice number is billing's, taken inside the same transaction as the pack. `financialYear()` and the business date come from `@dos/domain/calendar` and are pinned to `Asia/Kolkata`; never `new Date().toISOString().slice(0,10)`.
9. **Money is integer paise and appears in exactly two places**: `load_sheets.load_value_paise` and `delivery_challans.value_paise` / `lines[].taxableValuePaise`. Both are **sale** values (invoice totals for packed orders, `stock_lots.mrp_paise × qtyPcs` for van stock). No purchase cost, landed cost, PTD or margin may appear in any warehouse output — the CI role-dump test asserts it.
10. **The e-way bill is a hard gate.** When `load_value_paise >= tenant_settings['ewb_intra_state_threshold']` (default 10 000 000 paise), `loadSheets.confirm` refuses with 400 `ewb_required` until an `ewbNo` is recorded. This is checked on the sheet, not per invoice (a mixed load crosses ₹1 lakh even when no single bill does — docs/17 A8, COMPLETENESS 24).
11. **Load-out posts `transfer_out` + `transfer_in`, in one transaction, both keyed.** `load:<sheetId>:<lotId>:out` and `:in`. `UNIQUE(tenant_id, idempotency_key)` on `stock_ledger` makes a retried confirm a no-op. `van_load` / `van_unload` are left to the delivery module for van-sale stock issued and returned on route (see §8).
12. **A vehicle location may not go negative and neither may the godown.** `stock_balances_on_hand_nonneg` is the guarantee; `InventoryService` turns it into a readable 400. Never set `negative_allowed` on a vehicle location to work around a bad count.
13. **The counted package check is the crew's blind count.** `countedPackages ≠ expected_packages` requires a `varianceNote` and records `pin_verified_by = actor` — the manager's PIN in the app is exactly "the caller holds an owner/manager token". Never auto-accept a variance.
14. **Every mutation is idempotent by construction** (docs/20 rule 4): `idempotent(tx, input.idempotencyKey, input, fn)` around every write, client UUIDv7 ids on every created row, and ledger-level keys underneath. A replay with the same key and payload returns the stored response; a different payload is a 409.
15. **Bounded work per request** (docs/20 rule 3): `orderIds ≤ 200`, `pick lines ≤ 500`, `vanStock ≤ 200`, `limit ≤ 200`. Never load a whole tenant's picklists; every list is cursor-paginated on the UUIDv7 id descending and every index leads with `tenant_id`.
16. **No cross-module table reads.** `sales_orders`, `sales_order_lines`, `invoices`, `reservations`, `stock_balances`, `trips` are reached only through the exported services listed in §3. `eslint-plugin-boundaries` will fail the build otherwise.
17. **What must never happen:** a second invoice number for one order; stock leaving the godown twice for one load sheet; a picker (or any token) reading `tenant_product_costs`; a `retailer`-role token reading a picklist, a load sheet or a challan; a state column written by hand; a device uploading a pack confirmation or a challan; a `4xx` from `/sync/upload`.

## 8. Founder questions this brief had to assume an answer for

1. **Which ledger reason a van load uses.** `stock_reason` has both `transfer_out`/`transfer_in` and `van_load`/`van_unload`. **Assumed:** load-out from the godown to a vehicle posts `transfer_out` + `transfer_in` (docs/06 and ADR 0013 both say so), and `van_load`/`van_unload` are reserved for the delivery module's on-route van-sale movements and the check-in count.
