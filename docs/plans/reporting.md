## 1. Purpose and boundaries

Reporting is the read-model layer behind every owner/manager dashboard tile and every register screen in the six apps: daily sales, collections, outstanding/ageing, scheme spend, stock value (cost, back office only), fill rate, salesperson productivity (visits, orders, strike rate, per beat), delivery performance, and the two GST registers (GSTR-1-shaped sales register, GSTR-2-shaped purchase register), each as JSON with an optional CSV export.

It **owns** exactly four tables, already in `backend/libs/database/src/schema/reporting.ts` — `daily_tenant_stats`, `daily_rep_stats`, `retailer_behaviour`, `owner_summary` — the pre-aggregated surfaces so phones and the owner dashboard never scan a ledger (docs/20 rule 9). Nothing else. Every register beyond those four tables is a **live, bounded, grouped read of another module's tables, reached only through that module's exported service** (docs/20 rule 12) — reporting itself never owns an invoice, receipt, trip, stock or supplier-invoice row, and never joins into one of those tables directly.

It **calls out** to: `OrdersService` (`fillRateLines`, new — §3) for `sales_order_lines`; `InventoryService` (`valuationByLocation`, new — §3) for `stock_balances`/`stock_lots`; `TenantCatalogService` (`costs`, already exported) for `tenant_product_costs`; a new `RegistersService` inside `modules/billing` exporting `gstSummary`, `salesRegister` (the same functions `billing.registers.*` calls — docs/plans/billing.md §2 — plus a new `schemeSpend`) for `invoice_lines`/`credit_notes`; `ReceivablesService` (`collectionsRegister`, new; `outstandingList`, reused only for the CSV path — §8) for `receipts`/`retailer_outstanding_summary`; `SupplierInvoiceService` (`purchaseRegister`, new — §3) for `supplier_invoices`/`supplier_invoice_lines`; `RetailersService` (`beatAssignmentsFor`, new — §3) for beat/rep mapping; `DeliveryService` (`performanceRows` — not yet buildable, §8 item 8) for trip/stop rows; and the new minimal `ExportJobsService` inside `modules/integrations` (§8 item 2) for `export_jobs`.

It **is called by** nobody — reporting is a leaf module, consumed only by app UIs. It never reacts to outbox events (§7): every materialised row is a periodic recompute, not an event-sourced counter incremented on the request path (docs/20 rule 13), so a missed or duplicated event can never leave a tile wrong.

It **emits** one outbox event, `ReportExportReady` (§7), consumed by notifications.

**Never**: writes a business record (an invoice, a receipt, a stock row, an order); computes an incentive payout (that is `modules/incentives`'s job — reporting's `repProductivity` register stops at visits/orders/strike-rate, never a rupee of payout); serves purchase cost, landed cost or margin to any role outside `owner`/`manager`/`accountant`; serves anything at all to the `retailer` role — `retailer-service` does not mount this module (docs/06's retailer-app flows never open a report screen), and the RLS tightening in §3 means a retailer-role session gets zero rows from this module's own tables even if it somehow reached them.

**Does not duplicate two registers that already have a home** (a real overlap the task's scope creates with two already-briefed sibling modules, resolved here rather than left silent): the GSTR-1 sales register's arithmetic lives in `billing.registers.gstSummary`/`salesRegister` (docs/plans/billing.md §2) and the outstanding/ageing register's arithmetic lives in `receivables.outstanding.list`/`.get` (docs/plans/receivables.md §2). Reporting's `gstSalesRegister` is a thin wrapper that calls billing's own function (so the tax math exists in exactly one place); reporting does **not** add a standalone `registers.outstanding` JSON procedure at all — the JSON screen is `receivables.outstanding.list`, and reporting supplies only the CSV-export path for it through the generic exporter (§2, §8 item 1).

## 3. Schema changes needed

One new hand-written, expand-only migration `backend/libs/database/migrations/0006_reporting_guards.sql`, appended to `migrations/meta/_journal.json`, plus the matching Drizzle edits in `schema/reporting.ts`:

1. **RLS tightening on two of the four owned tables.** `daily_tenant_stats` and `retailer_behaviour` today carry plain `tenantPolicy` (any tenant member, `retailer` role included, per `columns.ts`'s definition) — the same gap docs/plans/delivery.md §3 item 8 found and fixed on `trips`/`vehicles`/`trip_expenses`. A retailer-role session can currently `SELECT` every row of both tables: the tenant's whole day's revenue, and every *other* retailer's basket, lapsed-risk score and payment habits. Drop `daily_tenant_stats_tenant` and `retailer_behaviour_tenant`; replace both with `tenantRolePolicy(name, STAFF_ROLES)` (`STAFF_ROLES` from `columns.ts`, which — unlike `platform/authz.ts`'s `STAFF` — already includes `warehouse`). `daily_rep_stats` and `owner_summary` already carry a correct role-scoped policy (read above) and need no change.
2. **`index('daily_rep_stats_day_idx').on(tenantId, day)`.** The existing primary key is `(tenant_id, user_id, day)`, which is wrong-leading for "every rep on day X" scans (`repProductivity`'s per-beat rollup, `dashboard.rep`'s cross-rep back-office queries) — those would otherwise need an index-only scan per user. New index, additive.
3. **`DATABASE_REPLICA_URL` support — not a migration, a platform edit** (docs/20 rule 10, the first module to need it): `platform/config.ts`'s `EnvSchema` gains `DATABASE_REPLICA_URL: z.string().optional()`; `platform/db.module.ts` gains a second provider `DB_REPLICA` (symbol) built from `createPool(env.DATABASE_REPLICA_URL)`/`createDb(...)` when set, `null` otherwise. `ReportingService`/`RegistersService` inject both `DB` and `DB_REPLICA` and read through `db.replica ?? db.primary` for every GET; every write (the worker's rollup) always uses the primary pool. This is genuinely optional today (the founder's Mac runs one Postgres instance) — see §8 item 4.
4. **New exported read methods this slice needs on modules it does not own** (code changes in those modules' files, not reporting's — same category as docs/plans/billing.md §2's `nextDocumentNumber` widen and docs/plans/delivery.md §3 item 10's `ensureVehicleLocation`): `OrdersService.fillRateLines(tx,{from,to,locationId?,salespersonId?})`; `InventoryService.valuationByLocation(tx,{locationId?,brandId?})`; a new `RegistersService` file inside `modules/billing` exporting `gstSummary`, `salesRegister` (moved out of wherever `billing.registers.*` currently implements them, so both the contract procedure and this module call the same function) and a new `schemeSpend(tx,{from,to,...})`; `ReceivablesService.collectionsRegister(tx,{from,to,groupBy})`; `SupplierInvoiceService.purchaseRegister(tx,{from,to})`; `RetailersService.beatAssignmentsFor(tx,{beatId?,userId?,from,to})`.
5. **`export_jobs` gains no columns** — the existing shape (`kind`, `params`, `status`, `objectKey`, `rowCount`, `error`, timestamps) already anticipates this exact use (its own comment lists `sales_register_xlsx | outstanding_xlsx`, §1/§8 item 2).

No new tables. No column changes to any table this module does not own beyond the read-only additions above.

## 4. Domain rules and edge cases

1. **Money is integer paise, quantities integer pieces, percentages basis points.** This module never introduces a float: `avgCostPaise`, `valuePaise`, every register total. `strikeRate`/`fillRate`/`onTimeRate`/`podCoverageRate` are the only non-integer numbers this module ever returns, and they are ratios (0..1 or 0..∞ for `fillRate` when free/short quirks push it past 1), never money.
2. **Dates are IST.** Every `from`/`to`, every `day` column and the worker's own notion of "today" go through `businessDate()`/`financialYear()` (`backend/libs/domain/src/calendar.ts`). A rollup that runs at 00:05 IST computes the row for the *new* business date, not the one that just ended (that is `reporting.rollup.finalize`'s job, §7).
3. **Materialisation, not live aggregation, for the four owned tables.** `daily_tenant_stats`, `daily_rep_stats`, `owner_summary` are refreshed every 15 minutes; `retailer_behaviour` once daily. Every other register in §2 is a live, bounded, grouped query with a capped date window (≤ 31 or ≤ 92 days depending on how expensive the join is) — never an unbounded scan of another module's ledger (docs/20 rule 3). No register endpoint in this module ever loads a whole tenant's history.
4. **Idempotent by upsert, not by idempotency key.** The rollup job's every write is `INSERT ... ON CONFLICT (tenant_id, day[, user_id]) DO UPDATE` — a crash, a retry or a redeploy mid-run reproduces the same numbers, never doubles them. This is deliberately different from `idempotent()` (which guards *online mutations*; the rollup is a background recompute with no client-supplied key to replay against).
5. **Per-tenant fairness on the rollup** (docs/20 rule 5). The scheduler fans out one pg-boss job per tenant rather than looping tenants inside one job, with bounded worker concurrency — one distributor with an unusually large order book never delays another's dashboard refresh.
6. **Read-replica aware, primary-write-only.** Every GET in §2 prefers `DATABASE_REPLICA_URL` when set (§3); the worker's rollup and `reporting.export.render`'s read of `export_jobs` for status updates always use the primary (docs/20 rule 10: writes and any `SELECT ... FOR UPDATE` stay on the primary — the rollup does no locking reads, but its own write half is on the primary by construction).
7. **Cost visibility is a hard boundary, not a filter.** `stockValue` is the only register carrying `avgCostPaise`/`valuePaise`; it is the only procedure in this module `requireRole`'d to `BACK_OFFICE` and the only one never mounted on `sales-service`/`warehouse-service`/`delivery-service` (§2) — the same "the fact of the endpoint's existence never reaches that app" pattern the tenant-catalog cost endpoints already use.
8. **Scheme spend never collapses funding source.** `company`-funded and `distributor`-funded scheme redemptions are always reported separately (`totals.companyFundedPaise`/`distributorFundedPaise`) as well as summed — a distributor-funded scheme is a margin hit today; a company-funded one is a receivable from the brand that the (future) claims module should be chasing. Conflating them would make a fully-recoverable scheme look like a loss.
9. **Fill rate degrades gracefully before warehouse exists.** `pick_lines`/`picklists` (schema present, no owning module, no seed data yet — §6) would give a per-line short reason; until that module lands, `fillRate` is computed from `sales_order_lines.picked_qty_pcs` alone (already written by whatever currently advances an order past `confirmed`), with `shortPcs` reported and no reason. The contract's output shape gains an optional `shortReasons` breakdown later without a breaking change (`items[].shortReasons?`).
10. **Delivery performance degrades to a stub, never an error, before delivery exists.** `DeliveryService.performanceRows` returns `{items:[], note:'delivery module not yet built'}` until docs/plans/delivery.md ships; the contract shape is frozen now so the six apps' generated docs already show the final response, and nothing about the endpoint's signature changes when delivery lands.
11. **Bounded work everywhere** (docs/20 rule 3): every list `limit ≤ 200`; every date window capped (31 days for the heavier per-line joins — `fillRate`, `deliveryPerformance`, `collections`, `repProductivity` — 92 days for the lighter grouped-column reads — `dailyStats.*`, `schemeSpend`, both GST registers); `reporting.export.render` refuses (marks the job `failed`, `error: 'window too large'`) a request whose filters exceed the same cap its live GET would enforce, rather than ever rendering an unbounded file.
12. **CSV export is always async, even for a small window** (docs/20 rule 3 and rule 15 by analogy: nothing streams inline). `reporting.exports.request` only ever returns `queued`; the file is always fetched by URL from `reporting.exports.get`, matching `billing.invoices.pdf`'s pattern exactly rather than inventing a second convention for text files.
13. **Every export is audited.** `reporting.exports.request` writes one `audit_log` row per request (`action='report.export.request'`) — a CSV of the sales register or the ageing book leaving the system is exactly the kind of bulk extract docs/17 A12 wants a trace of, the same principle that makes `delivery.gps.trace`/`vehicle-positions` write one.
14. **`retailer` role never reaches this module.** `retailer-service` does not mount `ReportingModule` at all (§2) — a forged or misrouted call 403s at `TenantGuard` before any handler runs; and even a direct database session as `retailer` now gets zero rows from every one of this module's own tables after the §3 RLS tightening, so there is no path — application or database — by which a shopkeeper's session ever sees another shop's numbers or the distributor's own revenue.
15. **This module never computes an incentive.** `repProductivity` stops at visits/orders/strike-rate; `modules/incentives` (schema already present: `targets`, `achievements`, `computed_payouts`) owns turning those into a rupee payout. Reporting's rollup does not read or write any `incentives` table.
16. **Never**: a purchase cost, landed cost or margin in any output shape except `stockValue`, and never on a service that does not `requireRole(BACK_OFFICE)`; a write to any table this module does not own (`invoices`, `receipts`, `sales_orders`, `stock_ledger`, `trips`, `export_jobs` included — that last one goes through `ExportJobsService`, §1); an unbounded date window; a synchronous CSV response body.

## 7. Worker jobs / outbox events

**Outbox events**: reporting emits exactly one, `ReportExportReady` (`aggregate_type = 'export_jobs'`), written by `reporting.export.render` in the same transaction as marking the job `succeeded`, payload `{jobId, register, format, tenantId, requestedBy}`, consumed by notifications (a WhatsApp/push "your report is ready" to whoever requested it). Reporting consumes **no** outbox events itself — every materialised row is a periodic recompute (§4 rule 3), never an event-driven increment.

**pg-boss jobs** (`backend/worker/src/jobs/reporting-rollup.ts`, `reporting-export.ts`, registered in `backend/worker/src/main.ts` alongside the existing outbox relay and retention sweep):

| job | schedule | role | does |
| --- | --- | --- | --- |
| `reporting.rollup.schedule` | every 15 min (`*/15 * * * *`) | `withSystem()` (BYPASSRLS, cross-tenant) | Lists `tenants` where `status='active'`; enqueues one `reporting.rollup.tenant` job per tenant with `{tenantId, businessDate: businessDate()}`, `singletonKey: reporting-rollup:<tenantId>:<businessDate>` so an overlapping run is never doubled up. |
| `reporting.rollup.tenant` | on demand, bounded concurrency (`teamSize: 20`) | `withSystem()` | Recomputes and `ON CONFLICT DO UPDATE`s that tenant's `daily_tenant_stats` and `daily_rep_stats` rows for `businessDate` (grouped queries over `sales_orders`, `invoices`, `receipts`, `trip_stops` for the window) and the single `owner_summary` row (today + MTD + margin + stock value + near-expiry + pending `approvals` count + active `trips` count). Every write idempotent by upsert (§4 rule 4); read-only against every source table. |
| `reporting.rollup.finalize` | once daily, `50 18 * * *` UTC = 00:20 IST | `withSystem()` | Re-runs `reporting.rollup.tenant` for **yesterday's** `businessDate` (closes out any device that synced after midnight) and recomputes every tenant's `retailer_behaviour` rows for a 30-day rolling window — the one heavier, whole-retailer-table scan, deliberately not run every 15 minutes. |
| `reporting.export.render` | on demand, triggered by `reporting.exports.request` | tenant-scoped (loads the `export_jobs` row's `tenant_id`, then `withTenant` for the actual register read so RLS still applies to the data being exported) | Loads the job, calls the named register's data source with the stored `filters` (its own service method, or the owning module's exported read — §1/§3), renders CSV (or passes JSON through), uploads to object storage (§8 item 3), sets `objectKey`/`rowCount`/`status='succeeded'` — or `status='failed'` + `error` on any exception, including the oversized-window refusal (§4 rule 11) — and writes `ReportExportReady`. |

Explicitly **not** reporting's: rendering PDFs (billing/receivables/delivery's own worker jobs); the GPS retention sweep or trip-points partitioning (delivery); computing incentive payouts (incentives, once built) off the `daily_rep_stats` rows this module produces.

## 8. Founder questions this brief had to assume an answer for

1. **Overlap with billing's and receivables' own registers.** The task scope hands reporting "GST registers" and "outstanding/ageing," but both already have a home in already-briefed sibling modules (docs/plans/billing.md's `billing.registers.*`, docs/plans/receivables.md's `receivables.outstanding.*`). Assumed reporting must never reimplement that arithmetic: it wraps billing's function for the sales-side GST register (`gstSalesRegister`, §1/§2) and adds no standalone JSON procedure for outstanding at all, only a CSV path through the generic exporter. If the founder instead wants one visually consistent "Registers" screen whose JSON shape is identical regardless of which module computes it, an umbrella `reporting.registers.list(kind, from, to)` procedure is a small addition on top of this design, not a rewrite of it.
2. **`export_jobs` ownership.** No `modules/integrations` exists yet — only the schema file, itself already commented for exactly this use. Assumed this slice builds the minimal `modules/integrations/{export-jobs.service.ts,integrations.module.ts,index.ts}` (create/get/markRunning/markSucceeded/markFailed) rather than writing to the table directly or blocking on the real Tally/imports module, the same call docs/plans/billing.md §8 item 7 made for receivables before it existed.
3. **Object storage.** `reporting.export.render`, billing's `invoice.pdf.render` and delivery's `delivery.pdf.pod` (docs/plans/billing.md §7, docs/plans/delivery.md §7) all assume an S3-compatible bucket + pre-signed-URL helper that none of the three has actually built yet (a grep of `backend/libs/core/src` and `backend/worker/src` today turns up nothing). Assumed whichever of the three modules lands first builds the shared `objectStorage.ts` helper in `@dos/core/platform`, and the other two just call it — flagged here so it is not accidentally built three times.
4. **Read replica is optional today, not a new requirement.** The founder's Mac runs one Postgres 17 instance on :5439 (CLAUDE.md); `DATABASE_REPLICA_URL` is declared but unset. Assumed this slice only needs to *honour* the env var per docs/20 rule 10 ("a missing replica URL falls back to the primary"), not stand up an actual replica — the platform edit in §3 is correctness-neutral until the founder adds one.
5. **Rollup cadence — a number, not a decision.** Assumed 15 minutes for the "today" tiles and once daily (00:20 IST) for `retailer_behaviour` (§7), because the behaviour scan touches every retailer in the tenant while the tenant/rep rollup is a handful of grouped aggregates. Shrinking the 15-minute job to 5 minutes for sub-minute-feeling freshness on the owner's phone is a schedule-string change, not a design change, so it is left for the founder to tune once real usage shows whether it matters.
6. **A field role's own-scope filters are always forced, never merely accepted.** `dashboard.rep`, `repProductivity` and `fillRate`'s `userId`/`salespersonId`, and `deliveryPerformance`'s `driverId`, are always overridden to the caller's own id for `salesperson`/`delivery` roles regardless of what the client sent (§2, §4 rule — mirrors docs/plans/delivery.md §2's `trips.list` "mine" force). The alternative — refusing a mismatched filter with 403 instead of silently substituting — was rejected because it is one more error path a flaky offline client has to handle for no security benefit (RLS is still the real guarantee).
7. **Fill rate ships ahead of the warehouse pick/pack module.** `pick_lines`/`picklists` exist in schema only. Assumed the register works today off `sales_order_lines.picked_qty_pcs` alone and gains a `shortReasons` breakdown as a strictly additive field once warehouse lands, rather than deferring this whole register until then.
8. **Delivery performance ships ahead of the delivery module.** docs/plans/delivery.md is itself unimplemented (build-log status `⏳`). Assumed `reporting.registers.deliveryPerformance`'s contract shape should be frozen and shipped now with a stubbed, always-200 service method (§4 rule 10) rather than waiting for delivery to land first or omitting the endpoint — so the generated `/docs` for all five apps already show the final surface, and delivery's own slice only has to fill in one function body.
