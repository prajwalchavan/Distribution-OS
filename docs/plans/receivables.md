## 1. Purpose and boundaries

Receivables is the money ledger (ADR 0004): it owns `accounts`, `journal_entries`, `journal_lines`, `receipts`, `allocations`, `ageing_snapshots`, `cash_discount_conditions`, plus two new tables `write_offs` and `retailer_outstanding_summary`. Every rupee that enters or leaves the AR position is posted here; nothing else in the codebase may write a journal row.

It is **called by**: `billing` (`postInvoiceIssued`, `postCreditNoteIssued` inside billing's own transaction), `orders` (`creditVerdict` — this replaces the raw SQL in `backend/libs/core/src/modules/orders/credit.ts`, which is deleted and re-exported from here), `delivery` (`recordReceipt` at the doorstep; `collections` rows point at `receipts.id`), `integrations`/imports (`postOpeningBalance`). It **calls** `RetailersService` for credit terms and `BillingService.setInvoicePaymentState()` for the derived `invoices.state` cache.

It **reads but does not own** `invoices`, `credit_notes`, `retailers`. Until `BillingModule` exists, receivables writes `invoices.state` directly with a `// TODO(billing): move behind BillingService.setInvoicePaymentState` comment — the same explicit exception `orders/credit.ts` carries today. Everything else it needs from other modules arrives through outbox events (`InvoiceIssued`, `CreditNoteIssued`, `TripSettled`) or through the exported service, never an ad-hoc join.

Services that mount it: owner (:3001), manager+accountant (:3002), sales (:3003), delivery (:3005), retailer (:3006). **Not** warehouse (:3004) — the warehouse role never touches money.

## 3. Schema changes needed

All in `backend/libs/database/src/schema/receivables.ts` unless noted, plus one new hand-written migration (`00NN_receivables_expand.sql`) appended to `migrations/meta/_journal.json`. Policy replacement is `DROP POLICY … ; CREATE POLICY …` — no data movement, safe under expand-only.

**3.1 New columns on `receipts`**

| column                                            | why                                                                                                                          |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `device_id text`                                  | docs/07 §7.3 requires `UNIQUE(tenant_id, device_id, client_receipt_no)` for offline receipts; neither column exists today.    |
| `client_receipt_no text`                          | the crew's paper receipt number, the offline dedupe key.                                                                      |
| `reverses_receipt_id text references receipts(id)` | corrections are a reversing receipt, never an edit.                                                                           |
| `deposited_at timestamptz`, `deposit_ref text`, `deposit_account_id text references accounts(id)` | cheque/cash banking.                                                     |
| `bounced_at timestamptz`, `bounce_reason text`    | cheque return.                                                                                                               |
| `bank_charges_paise bigint not null default 0`    | bounce charges, posted to `BANK_CHARGES`.                                                                                    |

New index: `uniqueIndex('receipts_device_client_no_idx').on(tenantId, deviceId, clientReceiptNo).where(sql\`client_receipt_no IS NOT NULL\`)`, and `index('receipts_status_idx').on(tenantId, status, receivedAt)`.

**3.2 Constraint replacements (reversals need negative amounts)**

- `receipts_amount_positive` (`amount_paise > 0`) → `receipts_amount_nonzero` (`amount_paise <> 0`).
- `allocations_amount_positive` (`amount_paise > 0`) → `allocations_amount_nonzero` (`amount_paise <> 0`).
- `allocations_one_source` (`(receipt_id IS NOT NULL) <> (credit_note_id IS NOT NULL)`) → exactly one of three:
  `((receipt_id IS NOT NULL)::int + (credit_note_id IS NOT NULL)::int + (write_off_id IS NOT NULL)::int) = 1`.

Existing demo/seed rows are all positive, so both drops are inert.

**3.3 New table `write_offs`**

```
write_offs(id, tenant_id, invoice_id -> invoices.id, retailer_id -> retailers.id,
           amount_paise, reason text, note text, approved_by -> users.id,
           journal_entry_id -> journal_entries.id, idempotency_key text not null,
           created_at, updated_at)
  uniqueIndex write_offs_idempotency_idx (tenant_id, idempotency_key)
  index write_offs_invoice_idx (tenant_id, invoice_id)
  check write_offs_amount_positive (amount_paise > 0)

```

Add `allocations.write_off_id text references write_offs(id)` + `index('allocations_write_off_idx').on(tenantId, writeOffId)`.

**3.4 New table `retailer_outstanding_summary`** (docs/06 and docs/07 §7.2 `rep_scope` both name it; it does not exist. It must be a **table**, not a view: PowerSync stream queries allow no `GROUP BY`, and scale rule 9 makes rollups the read surface.)

```
retailer_outstanding_summary(
  tenant_id, retailer_id -> retailers.id,
  outstanding_paise bigint not null default 0,
  overdue_paise bigint not null default 0,
  unallocated_credit_paise bigint not null default 0,
  open_bills integer not null default 0,
  oldest_due_date date,
  oldest_invoice_date date,
  last_receipt_at timestamptz,
  last_receipt_paise bigint,
  bucket_0_7_paise, bucket_8_15_paise, bucket_16_30_paise,
  bucket_31_60_paise, bucket_61_90_paise, bucket_90_plus_paise  (all bigint not null default 0),
  as_of date not null,
  updated_at timestamptz not null default now(),
```

Deliberately carries **no** credit-limit column: credit terms belong to `retailers` (module boundary), the reader joins them.

**3.5 New columns on `ageing_snapshots`**

`bucket_61_90_paise` and `bucket_90_plus_paise` (bigint, default 0) — docs/01 promises the owner 0-30 / 31-60 / 61-90 / 90+ but the table stops at `bucket_60_plus_paise`. Keep `bucket_60_plus_paise` as the sum of the two new ones (a spec asserts the identity). Also add `overdue_paise` and `unallocated_credit_paise` and `computed_at timestamptz not null default now()`.

**3.6 RLS fixes — required, these are current leaks**

| table                      | today                            | change                                                                                                                                                                                            |
| -------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `journal_entries`          | `tenantPolicy` (every role)      | `SELECT` for `BACK_OFFICE_ROLES`; `INSERT` for `STAFF_ROLES` + `warehouse` excluded (a delivery/sales actor must be able to post a receipt but never read the book); `UPDATE` back office; no `DELETE` (trigger already rejects). |
| `journal_lines`            | `tenantPolicy` (every role)      | same split. **This is the ADR 0002 cost guarantee**: `PURCHASES`, `STOCK` and GRN postings are readable through the journal today by a salesperson, delivery crew and even a retailer.               |
| `accounts`                 | `tenantPolicy` (every role)      | `SELECT` for `STAFF_ROLES` (no amounts live here, and posting needs the code→id lookup); writes `BACK_OFFICE_ROLES`. The `retailer` role loses read access.                                          |
| `allocations`              | `tenantPolicy` (every role)      | `SELECT` scoped through the invoice, exactly like `invoice_lines_read`: `tenant matches AND (actor_role <> 'retailer' OR EXISTS (SELECT 1 FROM invoices i WHERE i.id = allocations.invoice_id))`; `...staffWritePolicy('allocations_write')`. |

## 4. Domain rules and edge cases

1. **Money is integer paise, always.** Use `@dos/domain`: `paise()`, `add`, `subtract`, `sum`, `percentOf`, `allocate`, `roundToRupee`. No float ever reaches a journal line. Basis points for the cash-discount rate (`discount_bps`).
2. **Sign convention.** `journal_lines.amount_paise` is **debit positive, credit negative**; every entry sums to exactly 0, checked by the service before insert and again by the deferred constraint trigger `journal_lines_balanced` at COMMIT. `journal_lines` and `journal_entries` are append-only (`dos_reject_mutation` triggers) — a mistake is corrected only by a reversing entry with `reversed_by_entry_id` set on the original.
3. **The five postings** (account codes from `CHART_OF_ACCOUNTS`; `party_type='retailer'`, `party_id=retailerId` on every AR line):
   - *Invoice issued* (`ref_type='invoice'`): DR `AR` `total_paise`; DR `DISCOUNTS` `discount_paise`; CR `SALES` `subtotal_paise`; CR `OUTPUT_CGST`/`OUTPUT_SGST`/`OUTPUT_IGST`/`OUTPUT_CESS`; `ROUND_OFF` line = `-round_off_paise`. Balances because `total = subtotal − discount + taxes + roundOff`.
   - *Credit note issued* (`ref_type='credit_note'`): DR `SALES_RETURNS` taxable; DR the output-tax accounts; CR `AR` total; `ROUND_OFF` mirror.
   - *Receipt* (`ref_type='receipt'`): DR `CASH` | `CASH_VAN` | `UPI` | `BANK` | `CHEQUES` by mode; DR `CASH_DISCOUNT` when realised; CR `AR` `-(amount + cashDiscount)`.
   - *Deposit* (`ref_type='deposit'`): DR `BANK`; CR `CASH`/`CHEQUES`.
   - *Write-off* (`ref_type='writeoff'`): DR `BAD_DEBTS`; CR `AR`.
4. **Cash in transit.** `mode = 'cash'` **and** `trip_id IS NOT NULL` posts to `CASH_VAN`, not `CASH`; the `TripSettled` event (delivery module) moves DR `CASH` / CR `CASH_VAN` for the handed-over amount. This is what makes the owner's "cash in transit" tile real.
5. **FIFO allocation order:** open invoices (`state IN ('issued','partially_paid')`) ordered `due_date ASC NULLS LAST, invoice_date ASC, invoice_no ASC`. An explicit allocation always wins. Never allocate more than `total_paise − Σ allocations` for an invoice; never allocate to `draft`, `cancelled` or another retailer's invoice; the remainder stays on the receipt as on-account credit and shows in `unallocated_credit_paise`.
6. **Cash discount is a conditional realised at receipt (ADR 0004)**, never deducted on the invoice — unless `tenant_brands.cash_discount_mode = 'on_invoice'` for that brand (docs/17 A1), in which case no `cash_discount_conditions` row is created and no `CASH_DISCOUNT` posting happens at receipt. Realisation requires all three: the row is `open`, `businessDate(receivedAt) <= pay_by`, and the allocation settles the invoice in full. Otherwise the row lapses (nightly job) and the shop owes the full amount.
7. **Invoice payment state is a derived cache**, moved only through `invoiceMachine.next()` from `backend/libs/domain/src/state-machines/invoice.ts` (`issue`, `receive_partial`, `receive_full`, `write_off`). Recompute after every allocation change: `openPaise === 0 → paid`, `0 < allocated < total → partially_paid`, `allocated === 0 → issued`. Never assign a state string by hand; never touch any other column of an issued invoice (immutability trigger).
8. **Receipts are append-only and immutable.** The only column the service may ever update on an existing receipt is `status` (→ `deposited`, `bounced`, `cancelled`) plus the deposit/bounce metadata. Amount, mode, retailer, `received_at` are frozen. Corrections are a reversing receipt.
9. **A bounced cheque must restore AR exactly**, including any cash discount that had been realised against it: the mirror entry re-debits `AR` for `amount + cashDiscount` and credits `CASH_DISCOUNT`, and the `cash_discount_conditions` row returns to `open` if `pay_by` is still in the future, otherwise `lapsed`.
10. **Idempotency, three layers.** Every mutation runs inside `idempotent(tx, input.idempotencyKey, input, fn)`; `receipts` and `journal_entries` each carry `UNIQUE(tenant_id, idempotency_key)` so a replay after days offline cannot double-post even if `idempotency_keys` has been pruned; offline receipts add `UNIQUE(tenant_id, device_id, client_receipt_no)`. The journal entry's key is derived, not the caller's: `` `journal:receipt:${receiptId}` ``, `` `journal:invoice:${invoiceId}` ``, `` `journal:writeoff:${writeOffId}` `` — matching the demo seed's existing convention.
11. **Numbering.** `receipts.receipt_no` comes from `nextDocumentNumber(tx, 'RCPT')` at create (a receipt has no draft state, so the number is allocated immediately). Write-offs, allocations, journal entries and statements take no series. Van/device-allocated receipt numbers use `client_receipt_no`, which is the crew's paper book and is never the legal number.
12. **IST everywhere.** `businessDate()` for `journal_entries.entry_date`, `ageing_snapshots.as_of`, `cash_discount_conditions.pay_by` comparisons and every age-in-days calculation; `financialYear()` for the series. `daysBetween(fromIso, toIso)` from `@dos/domain/calendar` for bucket assignment. A device clock more than 10 minutes skewed produces a `sync_errors` warning, never a rejection.
13. **Ageing buckets** are keyed on `due_date` (falling back to `invoice_date + retailers.credit_days` when the invoice has none), measured against `asOf`: 0-7, 8-15, 16-30, 31-60, 61-90, 90+. `overdue_paise` = the open value of bills whose `due_date < asOf`. `bucket_60_plus_paise` (legacy column) = `bucket_61_90 + bucket_90_plus`.
14. **Credit verdict.** `breached = creditMode IN ('strict','stop') AND (outstanding + orderTotal > creditLimitPaise OR (creditLimitBills > 0 AND openBills >= creditLimitBills) OR (creditDays > 0 AND oldestDueDate < businessDate() − creditDays))`. `indicate` annotates only, never blocks. `stop` and `strict` both raise the same `credit_limit` approval in orders; the difference is what the owner may do with it.
15. **Bounded work (scale rules 3, 9, 13).** Every list caps at 200; `ledger.get` caps its window at 400 days; `statements.send` caps at 200 retailers and does the work in the worker; `ageing.rebuild` processes 500 retailers per statement; no procedure ever scans `journal_lines` for a dashboard number — the summary table is the read surface.
16. **What must never happen.** A journal row outside `withTenant`. A cost or margin value in any output of a procedure a salesperson, delivery or retailer role can reach (the journal RLS change in §3.6 is that guarantee). An allocation across tenants or across retailers. A mutated issued invoice (only `state`). A receipt row edited. A `paid` invoice re-allocated. A `retailer` role creating, allocating or reversing money. Two journal entries for one receipt.

## 8. Founder questions this brief had to assume an answer for

1. **Cash-discount mode per brand (docs/17 §C item 3).** *Assumed:* realised at receipt (ADR 0004) for every brand; `tenant_brands.cash_discount_mode = 'on_invoice'` is honoured where set — in that case receivables creates **no** `cash_discount_conditions` row and posts no `CASH_DISCOUNT` line, because the discount was already netted into the invoice by pricing. Confirm with Tarsun's CA before the pilot's first Too Yumm bill.
2. **May a salesperson collect money?** *Assumed:* yes — `receipts.create` allows `salesperson` (docs/01's "pending-bills file on his phone" implies rep-side collection). If Tarsun wants cash handled by the delivery crew and the desk only, drop `salesperson` from that one procedure's role list; nothing else changes.
3. **Write-off authority.** *Assumed:* owner only, with no rupee threshold and no second approval. If the CA wants the accountant to raise and the owner to approve, this becomes an `approvals` row of kind `write_off` in the orders module's queue rather than a direct mutation.
4. **Opening balances from TradeEzee (docs/17 §C item 6).** *Assumed:* they arrive bill-by-bill as synthetic `invoices` with `source='import'` and series `OPEN`, so bill-to-bill allocation and ageing work from day one, each backed by a `ref_type='opening'` journal entry against `OPENING` equity. A single lump-sum-per-retailer opening balance would break FIFO allocation and the ageing buckets, so this shape is the recommendation to put to the founder.
5. **FIFO tie-break.** *Assumed:* `due_date`, then `invoice_date`, then `invoice_no`. Tarsun's physical file is ordered by bill number, so this matches the paper.
6. **Ageing bucket presentation.** *Assumed:* the schema keeps the fine buckets (0-7/8-15/16-30/31-60) **and** gains 61-90/90+ so the owner screen in docs/01 (0-30/31-60/61-90/90+) can be rendered by summing, without a second snapshot table.
7. **Cash in transit.** *Assumed:* cash collected on a trip sits in `CASH_VAN` until the trip settlement hands it over, rather than hitting `CASH` immediately. This is what makes the owner's "cash in transit" tile and the settlement variance meaningful.
8. **Bank charges on a bounced cheque.** *Assumed:* posted to a new `BANK_CHARGES` expense account (added to the seeded chart), not netted against the retailer. If Tarsun recovers charges from the shop, it becomes a debit note instead — a billing-module change, not a receivables one.
9. **Statement channel and period.** *Assumed:* WhatsApp PDF, default window = last 90 days, generated in the worker and delivered through the notifications module; the desk can also request a plain PDF link.
10. **Retailer visibility of the journal.** *Assumed:* a shop sees its own bills, receipts, credit notes and running balance, but never the double-entry journal or the chart of accounts — hence the two code paths in `ledger.get`.
