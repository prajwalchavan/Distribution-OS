## 1. Purpose and boundaries

The delivery module owns the physical last mile: `vehicles`, `trips`, `trip_stops`, `deliveries`, `delivery_lines`, `pod_evidence`, `collections`, `trip_expenses`, `trip_settlements`, `trip_points`, `vehicle_positions` (schema file `backend/libs/database/src/schema/delivery.ts`) — and nothing else.
It calls **out** through exported services only: `OrdersService` (order state moves `dispatch` / `deliver_all` / `deliver_partial` / `return_undelivered`, and van-sale draft→confirm), `InventoryService` (`post()` for `sale_return_saleable` / `sale_return_damaged` / `van_unload` / `transfer_in` / `cycle_count` rows; `reserve()` / `postReservationAsSale()` at the vehicle location; a new `ensureVehicleLocation()`), `InvoicingService` + `CreditNotesService` (billing: van-sale invoice, doorstep shortfall/return credit note at the original rate), `ReceiptsService` (receivables: receipt + allocations + journal entry for a doorstep collection), `LoadSheetsService` (warehouse: read-only "is the load confirmed for this trip").
It is called **in** by nobody directly; other modules react to its `outbox_events` (§7). It never reads or writes `invoices`, `receipts`, `journal_*`, `sales_orders`, `stock_ledger`, `load_sheets` tables itself (`eslint-plugin-boundaries`); the only foreign columns it touches are `sales_order_lines.delivered_qty_pcs` and `receipts.trip_id`, both through the owning module's service.
A vehicle **is** a stock location (ADR 0013): pre-sold pieces left the ledger at pick (`sale` at the warehouse), free van stock arrives at the vehicle as `van_load`/`transfer_in` from the warehouse load sheet, doorstep returns come back **into the vehicle**, and check-in moves the counted remainder back to the warehouse.

## 2. Endpoints

Roles are membership roles; every service-level `requireRole([...])` array also carries `'system'`. Every mutation input additionally carries `idempotencyKey` (`MutationBase`) and the client-generated UUIDv7 `id` of the row it creates. Every GET uses `QueryBoolSchema`/`QueryIntSchema`; every list is `{ items, nextCursor }` with `limit` (`min 1, max 200, default 50`) + `cursor` (last row's `id`).

## 3. Schema changes needed

All in one new hand-written, expand-only migration (`0005_delivery_policies.sql`) plus the matching edits to `backend/libs/database/src/schema/delivery.ts`. Every new table/column gets its FORCE-RLS line; every new index leads with `tenant_id`.

1. **`trip_points.device_id text NOT NULL`** (default `''` for the backfill, then drop the default) — ADR 0012 keys points on `(trip_id, device_id, ts)` because a two-person crew carries two phones; the column is missing today.
2. **`uniqueIndex('trip_points_dedupe_idx').on(tenantId, tripId, deviceId, recordedAt)`** — the dedupe that replaces per-batch idempotency rows.
3. **`ALTER TYPE approval_kind ADD VALUE 'trip_settlement'`** — the owner approval for a red settlement (`ADD VALUE` is expand-only and must run outside a transaction block, so put it in its own statement/file section).
4. **`trip_settlements.approved_by text references users(id)`, `trip_settlements.approved_at timestamptz`** — who cleared the variance, separate from `settled_by`.
5. **`uniqueIndex('deliveries_stop_invoice_idx').on(tenantId, stopId, invoiceId)`** — one invoice is delivered at most once per stop.
6. **`deliveries.retailer_id text NOT NULL references retailers(id)`** (denormalised from the stop) + `index('deliveries_retailer_idx').on(tenantId, retailerId, deliveredAt)` — needed for the retailer RLS policy below and for the retailer's POD list.
7. **`deliveries.device_id text`** — which phone recorded the doorstep write (audit + the "where is my order" answer).
8. **RLS tightening — today these tables carry plain `tenantPolicy`, which lets a *retailer-role* actor read every row in the tenant:**
   - `deliveries`: drop `deliveries_tenant`; add `tenantOrOwnRetailerPolicy('deliveries_read', 'retailer_id')` + `...staffWritePolicy('deliveries_write')`.
   - `delivery_lines`, `pod_evidence`: drop the tenant policy; add the `invoice_lines`-style read policy (`role <> 'retailer' OR EXISTS (SELECT 1 FROM deliveries d WHERE d.id = <table>.delivery_id)`, which leans on `deliveries`' own RLS) + `staffWritePolicy`. **Never** join `retailer_identities` from these policies (42P17 infinite recursion).
   - `vehicles`, `trips`, `trip_expenses`: `tenantRolePolicy(name, STAFF_ROLES)` — a retailer has no business in the trip plan.
   - `collections`, `trip_settlements`: `tenantRolePolicy(name, ['owner', 'manager', 'accountant', 'delivery', 'system'])` — money on the trip is not a salesperson's or a retailer's row.
   - `vehicle_positions`: `tenantRolePolicy('vehicle_positions_map', ['owner', 'manager', 'delivery', 'system'])` — the live map is owner/manager (docs/07 `owner_scope`), and the delivery actor needs write for the GPS upsert.
9. **`tenant_settings` read policy**: today `tenantRolePolicy('tenant_settings_owner', OWNER_ROLES)` means a manager/accountant/delivery actor reads **nothing** — the settlement tolerance and POD policy would silently read as absent. Add `pgPolicy('tenant_settings_member_read', { for: 'select', to: appRw, using: tenant_id matches AND actor_role IN STAFF_ROLES })`, keeping writes owner-only.
10. **Not a migration, but required platform edits** (call them out in the PR): `NUMBERING_SERIES`/`nextDocumentNumber` must accept a runtime per-vehicle series code — widen the `seriesCode` parameter from the `SeriesCode` union to `SeriesCode | (string & {})` with a fallback prefix, so `VAN-MH05EF9012` works without a schema change; and `InventoryService` gains `ensureVehicleLocation(tx, {vehicleId, name})` (exported from `modules/inventory/index.ts`) because `locations` is inventory's table.
11. New `tenant_settings` keys used (rows, not schema): `delivery.settlement_tolerance_paise` (default 10_000 = ₹100), `delivery.pod_required` (`always | credit_only | never`, default `credit_only`), `delivery.geofence_metres` (default 150, evidence only), `dpdp.gps_retention_days` (default 90).

## 4. Domain rules and edge cases

1. **Money is integer paise** (`paise()` = bigint) everywhere: `planned_collection_paise`, `amount_paise`, `expected_cash_paise`, `handed_over_cash_paise`, `cash_variance_paise`, `upi_collected_paise`, `expenses_paise`, `opening_cash_paise`. No float, no rupee string, no rounding except `roundToRupee()` where billing already does it. Use `@dos/domain` `allocate()` when splitting a header amount across lines.
2. **Quantities are integer pieces.** `delivered_qty_pcs`, `returned_qty_pcs`, `expectedPcs`, `countedPcs` are pieces. Cases are display only: the check-in screen shows cases using the **lot's own** `stock_lots.case_size` (docs/17 A2, promo packs differ per batch), falling back to the sell-side pack (`tenant_products.case_size_override` else `product_variants.default_case_size`). Never use the buy-side `supplier_pack_configs` here.
3. **Dates are IST.** `trips.trip_date` and every `from`/`to` filter go through `businessDate()` / `financialYear()` from `backend/libs/domain/src/calendar.ts`; the IST day boundary helpers are `new Date(`${d}T00:00:00.000+05:30`)` / `T23:59:59.999+05:30` (copy `istStart`/`istEnd` from `orders.internals.ts`).
4. **State machines only.** `tripMachine` and `stopMachine` from `backend/libs/domain/src/state-machines/delivery.ts`; order moves go through `OrdersService` (which owns `orderMachine`). Wrap `TransitionError` into `ORPCError('CONFLICT')` exactly as `orders.internals.ts#transition` does. Never assign `trips.state` / `trip_stops.state` / `sales_orders.state` by hand.
5. **An issued invoice is immutable** (§4.4). A short delivery, a doorstep return or a failed stop never edits `invoices` or `invoice_lines`; the correction is a credit note at the **original rate** from `CreditNotesService`. The only invoice field that ever changes is the derived payment state, and receivables owns that.
6. **Ledger direction is fixed by ADR 0013.** Pre-sold pieces already left the warehouse as `sale` at pick, so a doorstep return posts `sale_return_saleable` **into the vehicle location** (or `sale_return_damaged` into the `damaged` location), and check-in moves the counted remainder vehicle → warehouse as `van_unload` + `transfer_in`. Van-sale pieces leave the **vehicle** as `sale`. Every ledger row carries a deterministic `idempotency_key` (`delivery:<id>:<lineId>:ret`, `settle:<tripId>:<lotId>:out|in|count`, `vansale:<orderId>:<lineId>`) so a replay after days offline is a no-op — `UNIQUE(tenant_id, idempotency_key)` is the guarantee.
7. **The vehicle location may never go negative.** `locations.negative_allowed = false` for `kind = 'vehicle'`; a van sale that exceeds van stock is a 400 with the shortfall, never a negative balance. The `damaged` bin is the only location allowed to go negative.
8. **Delivery outcome is derived, never accepted from the device.** `delivered` = every line full; `partial` = at least one short; `failed` = all zero. `deliveredQtyPcs + returnedQtyPcs` must equal `qty_pcs + free_qty_pcs` of the invoice line; free pieces are delivered and returned like any other piece.
9. **Stops are monotonic but forgiving.** `pending → started → arrived → delivered|partial|failed`. An offline batch that arrives out of order is accepted when the device timestamps form a valid sequence: a transition whose `occurredAt` is older than the stored timestamp for a state already passed is a no-op returning the current row. An impossible move from a device is a `SyncRejection` (2xx + `sync_errors`), from an online call a 409.
10. **Geofence is evidence, never a block** (docs/06). `distanceM` is reported; the app shows amber. A missing GPS fix does not stop a delivery.
11. **GPS is trip-scoped and consented.** `depart` requires a `granted` `location_consents` row for the driver; raw `trip_points` are pruned after `dpdp.gps_retention_days` (90); stop coordinates and POD stay with the invoice forever; the retailer gets an ETA only, never a coordinate. Every trace/live-map read writes an `audit_log` row (docs/17 A12). GPS points never travel through `/sync/upload`.
12. **`/gps/points` and `/sync/upload` never answer 4xx for business reasons.** Out-of-window points, unknown device, stale clock → 2xx with counters. Only a genuinely transient fault is 5xx, so devices back off instead of hot-looping (docs/20 rule 6).
13. **Cash vs UPI.** Only `mode = 'cash'` counts toward `expected_cash_paise`; UPI and cheque are reported separately (`upi_collected_paise`, and cheques as `CHEQUES_IN_HAND`). Expenses reduce expected cash and hit the journal once, at settlement.
14. **Cash discount is realised at receipt** (ADR 0004), inside its window, by `ReceiptsService` — the delivery module never computes a discount.
15. **Allocation is oldest invoice first** unless the crew tagged specific bills; surplus stays unallocated on the receipt (on-account), never refused.
16. **A red settlement cannot close the trip without the owner.** Variance outside `delivery.settlement_tolerance_paise`, or any non-zero stock variance, forces `settled_with_variance` and an owner decision; a manager/accountant attempt is a 409 that files an `approvals` row.
17. **No cost, no margin, ever.** No delivery output carries `tenant_product_costs`, `purchase_rate`, `landed_cost`, `ptd` or a derived margin — the delivery role is one of the roles the ADR 0002 CI test dumps and greps.
18. **Nothing binary through the service.** POD photos and expense proofs are S3 object keys obtained from signed URLs; the API stores `object_key` only (docs/20 rule 15).
19. **Bounded work.** Every list caps at 200 (`limit`), `points ≤ 500`, `lines ≤ 200`, `counted ≤ 500`, `stops ≤ 80`. No endpoint loads a trip's whole history.
20. **Never**: write `receipts`/`invoices`/`credit_notes`/`journal_lines`/`stock_ledger`/`load_sheets` directly; re-number a trip or an invoice; delete a `trip_point`, a `pod_evidence` row or a ledger row (corrections are compensating rows); let a delivery actor read or mutate a trip they are not crew on; let a retailer see another shop's stop, delivery or collection; hold state in process memory (settlement totals are recomputed from the tables on every call — docs/20 rule 1).

## 7. Worker jobs / outbox events

**Outbox events** (`outbox_events`, inserted in the same transaction as the state change; `aggregate_type` = `trip` \| `delivery` \| `collection`):

| event | payload | consumers |
| --- | --- | --- |
| `TripPlanned` / `TripLoading` / `TripDeparted` / `TripReturned` / `TripCancelled` | `{tripId, tripNo, vehicleId, driverId, state, plannedStops}` | reporting (`owner_summary.active_trips`), notifications (crew push) |
| `StopFailed` | `{tripId, stopId, retailerId, failureReason, invoiceIds}` | notifications (WhatsApp "delivery attempt failed"), reporting |
| `DeliveryRecorded` | `{deliveryId, tripId, invoiceId, orderId, retailerId, outcome, shortPcs, creditNoteId}` | notifications (POD + credit-note template to the retailer), reporting (`daily_tenant_stats`), incentives |
| `CollectionRecorded` | `{collectionId, receiptId, tripId, retailerId, mode, amountPaise}` | notifications (receipt template), reporting (`daily_rep_stats.collected_paise`, `owner_summary.today_collected_paise`) |
| `VanSaleInvoiced` | `{orderId, invoiceId, invoiceNo, tripId, retailerId, totalPaise}` | notifications (WhatsApp slip PDF), reporting, integrations (Tally) |
| `TripSettled` / `TripSettlementVariance` | `{tripId, expectedCashPaise, handedOverCashPaise, cashVariancePaise, hasVariance, stockVariance}` | notifications (owner alert on variance), reporting, incentives |

**pg-boss jobs** in `backend/worker`:

1. `delivery.gps.retention` — daily at 02:30 IST, `withSystem()` (app_worker, BYPASSRLS): delete `trip_points` older than each tenant's `dpdp.gps_retention_days` (default 90) in batches of 10,000 with a `LIMIT`ed `ctid` delete so the table is never locked long. Stop coordinates and POD are **not** touched.
2. `delivery.trips.stale` — every 15 minutes: trips still `active` more than 14 hours after `started_at`, and vehicles whose `vehicle_positions.recorded_at` is older than 30 minutes during an active trip, raise a notification to the owner ("trip still open" / "location unavailable"). Read-only apart from the notification row.
3. `delivery.pdf.pod` — on `DeliveryRecorded`: render the POD/credit-note PDF in headless Chromium and put it in S3, then hand the object key to notifications. Long work never runs on the request path (docs/20 rule 3).

**Sync handlers** registered on `onModuleInit` through `SyncRegistry` (the delivery app is offline-first): `trip_stops`, `deliveries`, `delivery_lines`, `pod_evidence`, `collections`, `trip_expenses`. Each maps the device op onto the matching service method and throws `SyncRejection` (2xx + `sync_errors`, bilingual message) for business faults — an impossible stop transition, a delivered quantity above the invoice, a collection on a settled trip, an unknown trip. `trip_points` is deliberately **not** registered: it has its own endpoint (ADR 0012).

## 8. Founder questions this brief had to assume an answer for

1. **Van slips (docs/17 §C.2)** — assumed **tax invoices from a per-vehicle series** (`V3/0001…`, `numbering_series.allocation_mode = 'device'`, docs/17 A5), not a consolidated daily B2C memo. If the CA prefers the memo, `vanSales.create` collapses to one daily invoice per vehicle and the per-vehicle series row goes away.
2. **Cash discount mode (docs/17 §C.3)** — assumed **realised at receipt** (ADR 0004), so `collections.record` lets `ReceiptsService` close the `cash_discount_conditions` row; nothing in delivery prints or deducts a discount.
3. **Return/damage policy (docs/17 §C.7)** — assumed **every doorstep shortfall or return becomes a credit note at the original rate**, saleable pieces back onto the vehicle, damaged pieces into the `damaged` bin, and the brand claim (if any) is raised later by the claims module from those credit notes.
4. **Settlement tolerance** — assumed **₹100 (10,000 paise)** as the default `delivery.settlement_tolerance_paise`, and that **any** non-zero stock variance is red regardless of value.
5. **Who may settle** — assumed **manager or accountant within tolerance, owner only outside it**; the crew can see the cockpit (`settlementPreview`) but never post the settlement.
6. **POD policy** — assumed **photo required for credit shops** (`payment_terms = 'POST_FULFILLMENT'`), optional otherwise, and **OTP off for the pilot** (`delivery.pod_required = 'credit_only'`).
7. **GPS consent** — assumed **`depart` requires a granted `location_consents` row for the driver**, while a denied OS permission on the phone never blocks the trip (the owner simply sees "location unavailable").
8. **On-spot shops** — assumed a van sale is only ever to a **retailer that already exists in this tenant**; the delivery app cannot onboard a new shop (that stays a salesperson/back-office action, docs/17 item 27).
9. **Who bills a van sale** — assumed **billing's `InvoicingService.issueFromLocation`** does it, so the invoice/GST/numbering rules live in exactly one module; delivery only supplies the order, the vehicle location and the series.
10. **Load sheet ownership** — assumed the **warehouse** module owns `load_sheets` and posts the `van_load`/`transfer_in` rows; delivery only reads "is the load confirmed" and never posts the load itself.
