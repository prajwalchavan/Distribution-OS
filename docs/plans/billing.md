## 1. Purpose and boundaries

Billing turns a packed sales order into an immutable GST tax invoice (numbering, GST split by place of supply, `applied_rules` and entered units copied from the order line, UPI QR, FSSAI, e-invoice/e-way fields), issues van-sale invoices from vehicle stock, commits brand-DMS invoices without ever creating a second legal document, cancels an invoice before dispatch keeping its number, and raises credit notes (short delivery, returns, rate difference) at the original rate.
It **owns** `invoices`, `invoice_lines`, `credit_notes`, `credit_note_lines` — no other module writes them.
It **calls out** to: `OrdersService` (`lockOrder(tx,id)`, `detail(tx,order)`, plus one new `markPacked(tx, order, deviceId)` added by this slice) for the order aggregate; `InventoryService` (`reserve`, `releaseReservation`, `postReservationAsSale`, `post`) for every stock movement; `LedgerService` from `modules/receivables` (`postEntry`, `openCashDiscountCondition`, `allocateCreditNote`, `invoiceOutstandingPaise`) for all money-ledger rows — billing never inserts `journal_entries`, `journal_lines`, `allocations`, `cash_discount_conditions`, `receipts`; `nextDocumentNumber` from `src/platform/numbering.ts` for `INV`/`CN`/van series.
It **emits** `InvoiceIssued`, `InvoiceCancelled`, `CreditNoteIssued` outbox events (notifications, reporting, warehouse's `pack_confirmations.invoice_id`, integrations/Tally consume them); it never reads `pack_confirmations`, `deliveries`, `trips`, `messages` or any receivables table directly.

## 3. Schema changes needed

Everything the module needs already exists in `backend/libs/database/src/schema/billing.ts` (`invoices`, `invoice_lines`, `credit_notes`, `credit_note_lines` with `applied_rules`, `entered_qty`/`entered_unit`/`pack_size_at_entry`, `case_size`, IRN/EWB/UPI columns), `platform.ts` (`numbering_series` with `allocation_mode`/`device_id`/`starting_no`) and `receivables.ts`. FORCE RLS and the immutability triggers for all four tables are already in migration `0003`. Only **four guards/indexes** are missing — one new hand-written, expand-only migration `backend/libs/database/migrations/0006_billing_guards.sql`, appended to `migrations/meta/_journal.json` (next tag after `0005_auth_guarantees`), with the matching Drizzle index declarations added to `schema/billing.ts`:

1. `CREATE UNIQUE INDEX invoices_order_active_idx ON invoices (tenant_id, order_id) WHERE order_id IS NOT NULL AND state <> 'cancelled';` — one live invoice per order; a cancelled invoice keeps its number and lets the order be re-billed.
2. `CREATE UNIQUE INDEX invoices_external_no_idx ON invoices (tenant_id, external_invoice_no) WHERE external_invoice_no IS NOT NULL;` — a brand-DMS invoice can never be imported twice (docs/17 item 1).
3. `CREATE INDEX invoices_source_date_idx ON invoices (tenant_id, source, invoice_date);` — register filters and the per-source Tally split.
4. `CREATE INDEX credit_notes_retailer_idx ON credit_notes (tenant_id, retailer_id, note_date);` — the retailer's credits tab and the ageing recompute (today only `credit_notes_invoice_idx` exists).

No new tables, columns, enums or policies. Notably **do not** add a `restock_location_id` column to `credit_notes`: the location lives on the `stock_ledger` rows (`ref_type = 'credit_note'`, `ref_id = <cnId>`), which is the ledger of record.

## 4. Domain rules and edge cases

1. **Money is integer paise, quantities integer pieces.** Use `@dos/domain` only: `paise()`, `multiply()`, `percentOf()`, `allocate()`, `roundToRupee()`, `splitGst()`. Never a float, never a per-line rupee rounding.
2. **GST split.** `splitGst(taxable, gstBps, tenants.state_code, invoices.place_of_supply_state)`. `place_of_supply_state` = `retailers.state_code` (a registered buyer's GSTIN prefix must agree; when it does not, trust the GSTIN prefix and record it). `is_inter_state = sellerState !== placeOfSupply`; inter-state fills only `igst_paise`, intra-state fills `cgst_paise = sgst_paise` (`percentOf(taxable, gstBps/2)` twice, so the halves are exact). Cess is always a separate `percentOf(taxable, cessBps)`, never halved.
3. **Dated HSN rates.** Billing needs its own `loadHsnRates(tx, codes, onDate) → Map<code,{gstBps,cessBps}>` in `billing.internals.ts` (the orders copy lives in `modules/orders/pricing-lines.ts`, which `eslint-plugin-boundaries` forbids importing). Rate dated to `invoice_date`; a missing rate is a 400 naming the HSN, never a silent 0.
4. **The invoice never re-prices.** `rate_paise`, `discount_bps`, `applied_rules`, `entered_unit`, `pack_size_at_entry` are copied verbatim from `sales_order_lines`; `priceOrder()` is not run again at pack. Only quantity and tax are recomputed.
5. **Short pack.** When the packed qty is less than the ordered qty, the line's `discount_paise` scales with `allocate(orderLineDiscount, [packedQty, orderedQty − packedQty])[0]` (largest remainder, no paisa lost); `entered_qty` is recomputed as `packed / pack_size_at_entry` when it divides exactly, otherwise `entered_unit = 'piece'` and `entered_qty = packedQty` so the bill still prints an honest "2 cs + 3 pcs" (docs/17 A3). Never edit the order line.
6. **One invoice line per (order line × lot).** `postReservationAsSale` can return rows across several lots; each becomes its own `invoice_lines` row sharing the same `order_line_id`, with `lot_id`, `batch_no`, `expiry_date` and `mrp_paise` from the lot and the quantity/discount split by `allocate()`. `line_no` is 1-based and dense.
7. **Case size on the bill is sell-side** (docs/17 B): `invoice_lines.case_size = tenant_products.case_size_override ?? product_variants.default_case_size` at issue, frozen. Buy-side `supplier_pack_configs` is never consulted. `description = tenant_products.local_alias ?? product_variants.name`.
8. **Free goods** print as quantity with zero value: `free_qty_pcs` is excluded from `taxable_paise` and from the taxable base of every rule, but counts in the HSN-summary quantity.
9. **Totals.** Header `taxable_paise = Σ line taxable`, `subtotal_paise = Σ (rate × qty)` before discount, `discount_paise = Σ line discount`; `roundToRupee(taxable + cgst + sgst + igst + cess)` gives `total_paise` and `round_off_paise` (s.170, one rounding per invoice). The journal's ROUND_OFF line carries exactly that residue so the entry balances to the paisa.
10. **Numbering only at issue** (ADR 0001, docs/17 item 26): ≤ 16 chars of `[A-Za-z0-9/-]`, consecutive per `(tenant, series, fy)`, allocated inside the issuing transaction via `nextDocumentNumber`. A draft invoice has `invoice_no = NULL`. `nextDocumentNumber`'s parameter type is currently narrowed to the seeded `NUMBERING_SERIES` codes — widen it to `string` (keeping the prefix lookup with a `${seriesCode}/` fallback) so van series `V1`/`V2` work; that is the only platform change this slice makes.
11. **Invoice state machine.** `invoiceMachine` in `backend/libs/domain/src/state-machines/invoice.ts` currently ends in `void`, which is not a value of the `invoice_state` enum, and has no way out of `issued`. Extend it (shared-lib edit; update `state-machines.test.ts` and run `pnpm --filter @dos/domain build`): states become `draft | issued | partially_paid | paid | written_off | cancelled`; events gain `cancel` from `draft` and from `issued`; `void` is removed. Every state write goes through `invoiceMachine.next()`, never a literal.
12. **Immutability is a database guarantee.** The `invoices_immutable` trigger freezes number, series, fy, date, order, retailer, buyer, place of supply and every money column once `state <> 'draft'`; `invoice_lines_immutable` blocks UPDATE and DELETE of any non-draft invoice's lines. Write the whole invoice in one INSERT; the only later writes are `state`, `cancelled_at`, `cancel_reason`, `pdf_object_key`, `irn`, `ack_no`, `ack_date`, `signed_qr`, `eway_bill_no`, `eway_bill_valid_until`, `transport_mode`, `vehicle_no`. Map a Postgres `restrict_violation` to a 409 with the trigger's message (see `pgConstraint` in the inventory service for the pattern).
13. **Cancellation ≠ deletion.** The number survives (GSTR-1 Table 13), the goods come back by compensating ledger rows, the money comes back by a reversing journal entry, and the order returns to the billing queue. After dispatch, only a credit note.
14. **Credit notes reverse at the original rate** (ADR 0004). Never today's price list, never a re-quote. Cumulative credited quantity per invoice line is capped by a query over `credit_note_lines` joined to non-cancelled notes.
15. **Cash discount** follows `tenant_brands.cash_discount_mode` for the brands on the invoice: default `at_receipt_financial_cn` → print `cash_discount_bps` (= `retailers.cash_discount_bps`) and `cash_discount_until` (= invoice date + `retailers.cash_discount_days`), deduct **nothing**, and open a `cash_discount_conditions` row through receivables; `on_invoice` brands (Too Yumm) → no condition row. A mixed-brand invoice where any brand is `on_invoice` carries `cash_discount_bps = 0` and no condition (see §8).
16. **IST everywhere**: `businessDate()` for `invoice_date`/`note_date`, `financialYear()` for `fy`, `due_date = invoice_date + retailers.credit_days`. A pack at 23:40 IST on 31 March belongs to the old FY.
17. **Idempotency**: every mutation wrapped in `idempotent(tx, input.idempotencyKey, input, fn)`; ledger keys are deterministic and namespaced (`invoice:<id>`, `invoice-cancel:<id>:…`, `credit-note:<id>:<lineId>`, `journal:invoice:<id>`, `journal:credit-note:<id>`) so a retry, a replay or a device re-upload can never double-post (`UNIQUE(tenant_id, idempotency_key)` on `stock_ledger` and `journal_entries`).
18. **Bounded work** (docs/20): `lines ≤ 200` on any input array, `limit ≤ 200` on every list, PDF rendering always to the worker, registers computed by one grouped query with a date window — never by loading a tenant's history.
19. **Never**: a purchase cost, landed cost or margin in any billing output shape; a second legal invoice for a brand-DMS order; an edit or regeneration of an issued invoice; a number handed out at draft; a retailer-role write anywhere in this module (`staffWritePolicy` on all four tables plus `requireRole`); a policy or query that joins `retailer_identities` from a tenant table (42P17).

## 8. Founder questions this brief had to assume an answer for

1. **Invoice series after cut-over (docs/17 §C1).** Assumed a fresh `INV/` series starting at 1 per tenant per FY; continuing TradeEzee's `GL/1687` is a data decision expressible as `numbering_series.starting_no` + `prefix` with no code change, so nothing here blocks it.
2. **Van slips (§C2).** Assumed the recommended per-vehicle **tax invoice** series (`V1/`, `V2/`, `allocation_mode = 'device'`), not a consolidated daily B2C memo; `issueVanSale` therefore accepts a device-allocated number.
3. **Cash discount mode per brand (§C3).** Assumed `at_receipt_financial_cn` as the default (ADR 0004) and `on_invoice` only where `tenant_brands` says so. Additional assumption not in the docs: a **mixed-brand invoice carries no cash-discount offer** (`cash_discount_bps = 0`, no condition row) rather than a partial one — the alternative needs a per-brand split of the invoice total the founder has not asked for.
4. **Which retailers are GST-registered / composition (§C5).** Assumed `retailers.gst_reg_type` drives `supply_type` (`regular` → B2B with `buyer_gstin`, else B2C) and that **no tenant is composition**, so a "Bill of Supply" variant is not built. `supplyType` is on the contract, so adding it later is a print-template change.
5. **Who may cancel an invoice.** Assumed owner and manager only; the accountant may issue and raise credit notes but not cancel a numbered document. Easily widened in `permissions.ts` if the founder disagrees.
6. **Rounding.** Assumed one rupee rounding per invoice (s.170) with the residue to ROUND_OFF, matching `priceOrder()` and the existing seed — not per line.
7. **Receivables interface.** Assumed `modules/receivables` exports a `LedgerService` with `postEntry(tx, {entryDate, refType, refId, narration, idempotencyKey, lines:[{accountCode, amountPaise, partyType?, partyId?, memo?}]})`, `openCashDiscountCondition(tx, {id, invoiceId, discountBps, payBy})`, `allocateCreditNote(tx, {id, invoiceId, creditNoteId, amountPaise})` and `invoiceOutstandingPaise(tx, invoiceId)`, and that billing posts **synchronously in the same transaction** (so AR is right the instant the bill prints) rather than waiting for the outbox relay. If that module does not yet export it, create the minimal `modules/receivables/{ledger.service.ts,receivables.module.ts,index.ts}` with exactly that surface — receivables owns those tables and its own slice will build on it.
8. **Order state at billing.** Assumed billing may issue from `confirmed`/`picking`/`packed` and advances the order itself through a new `OrdersService.markPacked(tx, order, deviceId)` (walking `start_picking` → `pack` with `orderMachine`, recording transitions and the outbox event), because the warehouse pick/pack module does not exist yet. When it lands, it moves the order first and `markPacked` becomes a no-op for already-packed orders.
9. **Invoice state machine shape.** Assumed the domain machine should match the database enum (`cancelled`, not `void`) and gain `cancel` from `issued`, per docs/17 item 26 ("never regenerated" means "never edited", cancellation before dispatch is lawful). This edits `backend/libs/domain`, a shared library — flagged because it changes a file outside the module.
10. **IRN.** Assumed a deterministic local stub behind the `e_invoicing` feature flag (off for Tarsun), with no external call and no GSP credentials, so print layouts and the integrations module can be finished before the GSP contract exists.
