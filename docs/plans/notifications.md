## 1. Purpose and boundaries

Notifications is the distributor's and the shopkeeper's only view of "did the message go out": every WhatsApp template, SMS and in-app/push notice the platform ever sends is one row in `messages`, dispatched by the worker (never inline in a request), retried with backoff, and metered by cost. It owns `templates`, `messages`, `whatsapp_windows`, `inbound_messages`, `push_tokens` (schema file `backend/libs/database/src/schema/notifications.ts`) — no other module writes them — plus one new table, `broadcasts` (the header row for an owner/manager's ad-hoc send to a beat).

It **calls out** to: `RetailersService` (new export, see §3) for a retailer's contact phone, `preferred_lang` and `whatsapp_optin_at`; nothing else — pricing, orders, billing, delivery and receivables never receive a call from this module, they only ever produce the `outbox_events` it consumes.

It **is called by nobody's write path** — every trigger arrives as an `outbox_events` row (order confirmed, invoice issued, delivery today, payment received, dues reminder) or as an explicit staff action (an ad-hoc broadcast, a manual resend). It never reads `sales_orders`, `invoices`, `deliveries`, `receipts`, `journal_lines` or any other module's tables directly; every fact it prints into a template comes from the event's own JSON payload, not a fresh query (docs/17 A1-style discipline: the event is the interface).

**Explicitly out of scope for this slice** (flagged so nobody assumes it is silently covered):
- Parsing a retailer's free-text WhatsApp order ("bhai 2 case campa 1L kal") into a draft order (docs/06 §13). This module only captures the raw inbound text (`inbound_messages`, `handled = false`) for a human or a future LLM-parsing slice to act on; it never creates a `sales_orders` row.
- OTP delivery for sign-in (docs/10 "Better Auth send hook → WhatsApp authentication → MSG91 SMS") is the identity/auth module's own call path. It may end up sharing the SMS adapter's HTTP client, but that is an implementation detail of the auth module, not a procedure of this contract.
- Enforcing a hard per-tenant WhatsApp spend cap (docs/10 "per-tenant quota... logged"). This slice records `cost_paise` on every send for later reporting; a circuit-breaker that refuses further sends once a monthly budget is exhausted is a follow-up (§8 item 8).

## 2. Endpoints

Reuse `common.ts`: `IdSchema`, `MutationBase`, `QueryBoolSchema`/`QueryIntSchema`, `LocaleSchema` (`en-IN | hi-IN | mr-IN`). New contract-local enums mirror the DB enums verbatim: `NotificationChannelSchema = z.enum(['whatsapp','sms','push','email','in_app'])` (mirrors `notification_channel`), `MessageStatusSchema = z.enum(['queued','sent','delivered','read','failed','skipped'])` (mirrors `message_status`). ## 3. Schema changes needed

Everything the module needs already exists in `backend/libs/database/src/schema/notifications.ts` (`templates`, `messages`, `whatsapp_windows`, `inbound_messages`, `push_tokens`) and `retailers.ts` (`retailer_links.preferred_lang`, `retailer_links.whatsapp_optin_at`, already populated for 6 of the 36 demo retailers — see §6). One new hand-written, expand-only migration `backend/libs/database/migrations/0006_notifications_guards.sql`, with the matching Drizzle edits to `schema/notifications.ts`:

1. **`messages.attempts integer NOT NULL DEFAULT 0`** and **`messages.next_attempt_at timestamptz`** — the schema has `status`/`error`/`cost_paise` but nothing to drive retry backoff (§4.5); the worker's dispatch sweep needs both.
2. **RLS tightening — `messages` today carries plain `tenantPolicy`, which lets a retailer-role actor read every shop's invoice/POD/receipt notification history in the tenant (the same class of leak the delivery brief fixed on `deliveries`):**
   - Drop `messages_tenant`.
   - Add `tenantOrOwnRetailerPolicy('messages_read', 'recipient_retailer_id')` (a `NULL` `recipient_retailer_id` — a staff-only in-app/push row — is invisible to the retailer role, matching the `IN (...)` predicate's normal behaviour) + `...staffWritePolicy('messages_write')`.
3. **RLS tightening — `inbound_messages` and `whatsapp_windows` also carry plain `tenantPolicy` (any tenant member, retailer included) for data that is staff-only operational state:** drop each `tenantPolicy` and add `tenantRolePolicy(name, STAFF_ROLES)` (STAFF_ROLES from `columns.ts`, which already includes `warehouse`, unlike `platform/authz.ts`'s narrower `STAFF` — see the same footnote billing's item 20 raised).
4. **RLS narrowing on `push_tokens` writes** (read stays tenant-wide for admin visibility): keep a `pgPolicy('push_tokens_read', {for:'select', using: tenantMatches('tenant_id')})`, and replace the current all-purpose `tenantPolicy('push_tokens_tenant')` with a write policy scoped to the owning user (`user_id = current_setting('app.actor_id') OR actor_role = 'system'`) — a staff member should not be able to silently overwrite or delete a co-worker's device token.
5. **New table `broadcasts`** (owner/manager's ad-hoc send to a beat): `id text PK`, `tenant_id` (`tenantRef()`), `beat_id text references beats(id)` (nullable — an explicit `retailerIds` broadcast has no beat), `channel notification_channel NOT NULL`, `template_key text NOT NULL`, `locale text`, `created_by text NOT NULL references users(id)`, `total_recipients integer NOT NULL`, `queued_count/sent_count/delivered_count/failed_count integer NOT NULL DEFAULT 0` (denormalised counters refreshed by the dispatch sweep so `broadcasts.list` never has to re-aggregate `messages` on every read once a tenant's broadcast history grows — the live grouped query in §2 is the fallback for `get`'s per-recipient drill-down only), `...timestamps`. RLS: `tenantRolePolicy('broadcasts_owner_manager', ['owner','manager','system'])` — an accountant reads broadcast history through `messages`/the register query, never this header table directly, matching the role split in §2.
6. **New index `messages_dispatch_idx` on `(tenant_id, status, next_attempt_at)` WHERE `status IN ('queued','failed')`** — the worker's dispatch sweep query; the existing `messages_status_idx` on `(tenant_id, status, created_at)` doesn't sort by due time.
7. **New index `messages_recipient_retailer_idx` on `(tenant_id, recipient_retailer_id, created_at)`** — the retailer inbox list and the new `messages_read` RLS predicate's join both filter on this column, which had no index of its own before.

No changes to `templates_key_idx`, `templates_read`/`templates_write` (already correctly curator/owner-scoped), `pushTokens.push_tokens_device_idx`, `inboundMessages.inbound_messages_provider_idx` — those are already right.

**Not a migration, but required platform edits** (call these out in the PR, same as billing's `nextDocumentNumber` widening and delivery's `ensureVehicleLocation`):

- **`backend/worker/src/jobs/outbox-relay.ts` currently only counts unpublished events and logs a stub message — nothing consumes them yet.** It needs a small per-`eventType` handler registry (the file's own comment already anticipates this: *"Handlers per event type are registered here as modules grow"*) so that when notifications registers a handler for `OrderConfirmed`, the relay actually calls it, and marks `published_at = now()` only after every registered handler for that event type has run (a fan-out list per event type, not a per-consumer flag — `outbox_events` has one `published_at` column, so "published" means "every current handler saw it," matching how billing's brief lists five different consumers for one `InvoiceIssued` event with no per-consumer state anywhere in the schema).
- **`backend/worker/package.json` gains `@dos/core` as a dependency** (today it depends only on `@dos/db`/`@dos/domain` — confirmed by reading the file). The worker imports the plain, DI-free functions this module exports from `notifications.internals.ts` (event→message translation, the dispatch loop, the adapters) directly — not the `@Injectable` `*.service.ts` classes, so the worker process needs no Nest bootstrap.
- **`modules/retailers` gains one small read export**: `RetailersService.contactPreferences(tx, retailerId): Promise<{ phone: string, preferredLang: string | null, whatsappOptinAt: Date | null } | null>` (reads the retailer's `role = 'owner', status = 'active'` `retailer_links` row, falling back to `{ phone: retailers.phone, preferredLang: null, whatsappOptinAt: null }` when no link exists). This module calls that export rather than querying `retailer_links` directly — unlike `orders/credit.ts`'s precedent (a direct read because "neither module exists yet"), `retailers` already ships, so the "talk only through exported services" rule applies in full here. Flagged because it is a one-method edit outside this slice's own files.

## 4. Domain rules and edge cases

1. **Queue, then dispatch — never inline.** Every send is a `messages` row (`status = 'queued'`) written in the same transaction as its trigger (an outbox-consuming worker tick, or a `broadcasts.create` call); the actual provider HTTP call happens later, in the worker's dispatch sweep, off the request path (docs/20 rule 3).
2. **WhatsApp needs opt-in; SMS is the fallback, never a silent drop.** A recipient is resolved to `whatsapp` only when `retailer_links.whatsapp_optin_at IS NOT NULL` for their active `owner`-role link; otherwise the same event/broadcast is sent by `sms` instead (docs/17 A6). A recipient with no phone at all is `skipped` (reported, §2's `broadcasts.create.skipped`), never silently absent from the count.
3. **Meta's 24-hour session window is not this module's send gate.** `whatsapp_windows` records when a retailer's own inbound message opened a free-form reply window (docs/10 "'Reply 1 to confirm' keeps replies in the free 24-hour window"); every outbound send in §2/§7 is a pre-approved **template** message, which Meta allows any time regardless of the window. This slice writes `whatsapp_windows` rows on inbound receipt (for a future free-form-reply feature) but never reads the table to gate a template send.
4. **Locale resolution chain.** Per recipient: the retailer's `retailer_links.preferred_lang` (a free-text column — `'mr'`/`'hi'`/`'en'` today, per the existing seed; normalise short codes to `LocaleSchema` — `mr→mr-IN`, `hi→hi-IN`, `en→en-IN`, unrecognised → fall through) → `tenant_settings['notifications.default_locale']` (default `hi-IN`) → `hi-IN`. If no `templates` row exists for `(key, channel, resolvedLocale)` in either the tenant's own rows or the platform defaults, fall back to the `hi-IN` template for that key/channel rather than failing the send — a missing Marathi translation must never block a bill from going out.
5. **Retry with backoff, then terminate.** `attempts` caps at 5; `next_attempt_at` schedule is `1m, 5m, 30m, 2h, 12h` after each failure. After the 5th failed attempt `status` stays `failed` permanently — the dispatch sweep's `WHERE next_attempt_at <= now()` predicate excludes it once `attempts >= 5` regardless of `next_attempt_at`. A human `messages.resend` (§2) resets `next_attempt_at = now()` but **not** `attempts`, so a number that is simply wrong (typo, disconnected) still terminates rather than retrying forever.
6. **Cost is recorded on every send that leaves `queued`.** The adapter's response sets `cost_paise` (stub adapters return a fixed realistic figure — ₹0.136 WhatsApp per docs/10, a flat MSG91 SMS rate — never `null` once `status` moves past `queued`). This feeds a future per-tenant spend dashboard; no cap is enforced yet (§8 item 8).
7. **Cost and provider internals never reach a non-back-office role.** `costPaise`, `providerMessageId`, `error` are stripped by the mapper for every role except `owner`/`manager`/`accountant` — messaging spend is a back-office figure exactly like purchase cost, even though it lives in a different module.
8. **Bounded work everywhere** (docs/20 rule 3): `broadcasts.create` recipients ≤ 500; every list `limit` ≤ 200; `template.variables` ≤ 20 entries; `template.body` ≤ 1024 characters; the dispatch sweep pulls ≤ 200 due messages per tick, cross-tenant, and never loops a tenant's whole message history.
9. **A template's variables are a contract.** `templates.upsert` refuses (400) a `body` containing a `{{token}}` not present in `variables`. The translator/dispatcher refuses (and marks the message `failed` with a descriptive `error`, never sends a literal `{{orderNo}}` to a shopkeeper) when an event's payload is missing a variable the resolved template declares.
10. **A retailer never sees another shop's message** (RLS `messages_read`, §3.2) and never writes to `messages`/`templates`/`push_tokens`/`inbound_messages` (`staffWritePolicy` on all four; `broadcasts` excludes the role entirely).
11. **In-app "read" is explicit, never inferred.** `read_at` is set only by `messages.markRead`; opening the `messages.list` inbox screen does not mark anything read — the client calls `markRead` per item on open/tap, so `unreadCount` stays accurate across devices.
12. **`whatsapp`/`sms` "read" comes only from the provider.** `messages.markRead` refuses those channels (400) — `delivered_at`/`read_at` for WhatsApp arrive through the status webhook (§7), never a client call, and SMS has no read receipt at all (only `delivered`).
13. **Push tokens are per tenant-membership, not per device globally.** `UNIQUE(tenant_id, user_id, device_id)` — a user with memberships in two tenants (e.g., an owner who also delivers for a friend's business) registers one row per tenant on the same physical device, mirroring PowerSync's per-tenant bucket scoping (docs/20 rule 14).
14. **Provider adapters are a small typed interface**, not a hard dependency: `send(to, providerTemplateName, variables, locale): Promise<{ providerMessageId: string, costPaise: number, status: 'sent' | 'failed', error?: string }>`. `WhatsAppAdapter`/`SmsAdapter` stub implementations (dev/test) return deterministic fake ids and `status: 'sent'`; the real Meta Cloud API / MSG91 HTTP clients are gated behind `tenant_settings['whatsapp.phone_number_id']` / an MSG91 auth key env var and are not built in this slice (same "stub until credentials exist" posture as billing's IRN stub, §8 item 5).
15. **IST everywhere.** The delivery-today and dues-reminder sweeps (§7) key their "today"/cooldown window off `businessDate()`, never UTC midnight — a sweep that runs at 00:15 UTC (5:45 AM IST) must not treat it as "yesterday."
16. **DPDP / no binary through the API.** `inbound_messages.media_object_key` is an object-storage key only (docs/20 rule 15); a retailer's phone is always read from the tenant's own `retailers.phone`, never from the global `retailer_identities.phone` — a message must never leak which other tenants share this shopkeeper's identity.
17. **A message row is immutable in spirit once created.** After insert, only `status`, `provider_message_id`, `cost_paise`, `error`, `attempts`, `next_attempt_at`, `sent_at`, `delivered_at`, `read_at` ever change — `channel`, `to`, `template_key`, `payload` never do. A correction (wrong number, wrong template) is a fresh message, never an edit of what was already queued or sent.
18. **Idempotency keys are deterministic and namespaced**, exactly like billing's ledger keys: an outbox-triggered send is `'<eventType>:<aggregateId>'` (or `'<eventType>:<aggregateId>:<n>'` when one event fans out to several recipients); a broadcast recipient is `'<broadcastId>:<retailerId>'`. `UNIQUE(tenant_id, idempotency_key)` on `messages` (already in the schema) is the guarantee — a re-run of the outbox relay after a worker crash can never double-send.
19. **Never**: a provider call before the `messages` row exists; a WhatsApp send to a number that has never opted in (falls back to SMS, §4.2, rather than being skipped or sent anyway); a broadcast without an explicit, bounded recipient set; cost/provider fields in a salesperson/warehouse/delivery/retailer response; the outbox relay marking an event published before every currently-registered handler has run; this module writing `retailer_links`, `sales_orders`, `invoices`, `deliveries` or any other module's table.

## 5. DB-backed spec list

`backend/libs/core/src/modules/notifications/notifications.spec.ts`, wrapped in `describeDb`, booting `[NotificationsModule, RetailersModule, OrdersModule]` with `bootTestApp`; fixtures built directly with `@dos/db` + `bootstrapTenant`, keyed by a unique `run` suffix (one tenant, owner/manager/accountant/salesperson/warehouse/delivery users, one retailer with an active `owner`-role `retailer_links` row and `whatsapp_optin_at` set, a second retailer with no link at all, one beat with both retailers on it).

1. `translates an OrderConfirmed event into a queued WhatsApp message for an opted-in retailer` → `templateKey = 'order_confirmed'`, `channel = 'whatsapp'`, `refType = 'order'`/`refId = orderId`, `idempotencyKey = 'OrderConfirmed:<orderId>'`.
2. `falls back to SMS for a retailer who never opted into WhatsApp` → same event against the unlinked retailer → `channel = 'sms'`.
3. `replays the same outbox event without creating a second message` → running the translator twice for the same event leaves exactly one `messages` row (`onConflictDoNothing` on `messages_idempotency_idx`).
4. `messages.list scopes a retailer to its own shop and strips cost/provider fields` → the retailer actor sees only its own rows with `costPaise`/`providerMessageId`/`error` absent; the owner sees the same rows with those fields populated.
5. `messages.resend requeues a failed message without resetting attempts` → `status: 'failed', attempts: 3` → resend → `status: 'queued', attempts: 3, nextAttemptAt: now`; resending a `delivered` message is 409.
6. `dispatch sweep sends a queued message through the stub adapter` → after one sweep tick, `status: 'sent'`, `providerMessageId` set, `costPaise > 0`, `sentAt` set.
7. `dispatch sweep backs off a failing send and terminates at the attempt cap` → a stub adapter forced to fail five times in a row leaves `status: 'failed', attempts: 5`; a sixth sweep tick touches nothing (`messages_dispatch_idx`'s predicate excludes it).
8. `templates.upsert creates a tenant override that templates.list prefers over the platform default` → insert an override for `(key, channel, locale)`, list returns `isOverride: true` for that row and does not also return the platform-default row for the same key/channel/locale.
9. `a tenant cannot address a platform-default template row` → the service always forces `tenantId = ctx.tenantId`; a raw `withTenant` `UPDATE templates SET body = ... WHERE tenant_id IS NULL` as `actor_role = 'manager'` is rejected by `templates_write` (RLS, the backstop).
10. `broadcasts.create fans out to a beat, resolving channel per recipient's opt-in` → 2 recipients on the beat → 2 `messages` rows, one `whatsapp` (opted in) and one `sms` (not), a `broadcasts` header row with `totalRecipients: 2`.
11. `broadcasts.create refuses an oversized recipient list` → 501 explicit `retailerIds` → 400, no rows written.
12. `push token registration upserts by device, never duplicates` → registering the same `(tenantId, userId, deviceId)` twice updates `token`/`lastSeenAt` in place; still one row.
13. `push token registration never lets a caller name another user` → `userId` in the response is always `ctx.actorId` regardless of any client-supplied value (the input schema has no `userId` field at all — the test asserts the contract, not just the handler).
14. `inbound.markHandled sets handled without touching the raw text` → `body`/`mediaObjectKey`/`from` unchanged, `handled: true`.
15. `401 without tenant context` → any procedure called with no actor headers is 401.
16. **RLS/role refusal, one per role:**
    - `retailer` → `messages.list` never returns another shop's rows even without a `retailerId` filter (RLS, not app-level filtering); `templates.upsert`, `broadcasts.create`, `inbound.list` are all 403.
    - `salesperson` → `templates.upsert` and `broadcasts.create` are 403, while `messages.list` and `inbound.list` are 200.
    - `warehouse` → `broadcasts.create` and `templates.upsert` are 403.
    - `delivery` → `inbound.markHandled` is 403 (support triage is back-office/rep, not crew).
    - `accountant` → `broadcasts.create` is 403 (owner/manager only), while `broadcasts.list` and `templates.list` are 200.
    - `manager` → cannot write a `tenant_id IS NULL` template row even via a raw `withTenant` statement (spec #9) — the one thing even a back-office role cannot do in this module.
    - `owner` → cannot read or resend a message belonging to a different tenant → `NOT_FOUND` (tenant isolation, mirrors billing spec #14).
17. Extend `backend/libs/database/src/rls.test.ts` with: a retailer-role session can `SELECT` its own `messages` rows and zero of another shop's, and its `INSERT`/`UPDATE` on `messages`, `templates`, `push_tokens` and `inbound_messages` is rejected by the write policies.

## 7. Worker jobs / outbox events

**Outbox events consumed** (`outbox_events`, relayed by the extended `outbox-relay.ts`, §3's platform edit):

| event | source module (status) | consumer action |
| --- | --- | --- |
| `OrderConfirmed` | orders (live — `orders.internals.ts`) | `order_confirmed` template to the retailer. |
| `OrderSubmitted` | orders (live) | When the event's `approvalFlags` is non-empty: an `in_app`/`push` "needs approval" notice to the submitting salesperson and the tenant's back-office roles. |
| `OrderCancelled` | orders (live) | `order_cancelled` template to the retailer. |
| `retailer.identity_linked` | retailers (live — `retailers.service.ts`) | A one-time `in_app` welcome/opt-in-prompt to the newly linked login. |
| `InvoiceIssued` | billing (planned, docs/plans/billing.md) | `invoice_issued` (bill + UPI link) to the retailer. Registered as a no-op handler until billing ships, using the exact `eventType`/payload shape billing's brief already specifies, so no rename is needed later. |
| `InvoiceCancelled` | billing (planned) | Logged only; no retailer-facing message by default (§8 does not need to decide this — cancellation-before-dispatch means the shop was never billed anything final). |
| `DeliveryRecorded` | delivery (planned, docs/plans/delivery.md) | `pod_delivered` (outcome `delivered`/`partial`) to the retailer; a short-delivery credit note reference is included in the payload when `creditNoteId` is present. |
| `CollectionRecorded` | delivery (planned) | `payment_received` template to the retailer. |

**pg-boss jobs** (registered in `backend/worker`, alongside the existing `outbox-relay`/`retention` schedule):

- `notifications.dispatch` — every minute, `withSystem()` (cross-tenant, BYPASSRLS): pulls ≤ 200 rows from `messages` via `messages_dispatch_idx` (`status IN ('queued','failed') AND attempts < 5 AND (next_attempt_at IS NULL OR next_attempt_at <= now())`), calls the matching adapter (`WhatsAppAdapter`/`SmsAdapter`/an in-process push send/a no-op for `in_app`), and writes back `status`/`providerMessageId`/`costPaise`/`error`/`attempts`/`nextAttemptAt`/`sentAt` per §4.5. Also refreshes the parent `broadcasts` counters for any message whose `ref_type = 'broadcast'`.
- `notifications.deliveryToday` — daily at 07:00 IST: once delivery ships, scans today's `trip_stops` and enqueues one `delivery_today` message per stop's retailer (`idempotencyKey = 'DeliveryToday:<stopId>'`); until then, a documented no-op (delivery's tables don't exist).
- `notifications.duesReminder` — daily at 09:00 IST: once billing/receivables ship, scans overdue invoices past their `due_date`, enqueues `dues_reminder` at most once per retailer per 7 days (cooldown checked against the latest `dues_reminder`-templateKey message for that retailer); until then, a documented no-op.

**WhatsApp status webhook** (Meta Cloud API delivery/read receipts) is deliberately **not** a contract procedure — it carries no tenant headers at all (Meta calls one platform-wide callback URL, not a per-service one), so it cannot go through `TenantGuard`. It is a small dedicated, unauthenticated-by-header Fastify route (verifying Meta's `X-Hub-Signature-256` instead) that resolves the tenant by looking up the inbound `phone_number_id` against `tenant_settings['whatsapp.phone_number_id']`, then updates the matching `messages` row's `status`/`delivered_at`/`read_at` directly (plain DB write, the same posture as the worker jobs above). See §8 item 1 for where this route lives.

**Sync handlers**: none. Notifications' apps are all online-first for this module (a device reads its message log/inbox live; nothing here queues through PowerSync), matching the retailer app's own online-first posture (docs/17 D "Retailer on PowerSync: still online-first").

## 8. Founder questions this brief had to assume an answer for

1. **Multi-tenant WhatsApp webhook routing.** Meta's Cloud API gives one callback URL per WhatsApp Business Account, not one per distributor. Assumed a **single shared platform WABA for the pilot** (Tarsun is the only tenant), with the webhook resolving tenant via `tenant_settings['whatsapp.phone_number_id']` on a small unauthenticated route outside the oRPC contract (§7); a genuinely multi-tenant deployment would need either per-tenant Meta phone numbers or an embedded-signup flow, which is out of scope until a second real tenant exists.
2. **Who writes `retailer_links.preferred_lang`/`whatsapp_optin_at`.** Assumed the `retailers` module owns the write path (a small future addition there, e.g. alongside `retailers.upsert` or the retailer app's own "shop-detail self-edit" per docs/06 §13); this module only ever **reads** them via the new `RetailersService.contactPreferences()` export (§3) and never writes `retailer_links` itself, keeping single-table-ownership intact.
3. **Scheme announcements: automatic or operator-initiated.** The task text lists "scheme announcement" both as an outbox-triggered event and as the worked example for the ad-hoc broadcast feature. Assumed **always operator-initiated** via `broadcasts.create` for this slice — matching a scheme's `applicability` dimensions (docs/17 B) to the right retailer set automatically is real logic the founder hasn't asked for yet; the owner picks the beat/retailers by hand instead.
4. **Retry/backoff numbers.** Assumed 5 attempts, backoff `1m, 5m, 30m, 2h, 12h`, matching typical WhatsApp/SMS provider guidance; easily tuned as constants in `notifications.internals.ts` without a schema change.
5. **Provider choice and credentials.** Assumed **Meta Cloud API direct** for WhatsApp (docs/10: "no BSP fee") and **MSG91** for SMS (per the task), both stubbed in dev/test with deterministic fake responses (§4.14) — no GSP/BSP contract exists yet, same "stub until credentials exist" posture as billing's IRN stub.
6. **Dues-reminder cadence and threshold.** Assumed triggered once an invoice is overdue by any amount past its `due_date`, sent at most once per retailer per 7 days (§7); the founder may want a minimum overdue amount or a longer cooldown once real collections data exists.
7. **Retailer push notifications.** Assumed the retailer app does **not** register push tokens in this slice (docs/06: "Retailer (WhatsApp → PWA → native)" — WhatsApp/PWA-deep-link first); `pushTokens.register` is staff-only. If/when the retailer app gets native push, this is a one-line role-group widening, not a schema change.
8. **Spend cap enforcement.** Assumed this slice only **records** `cost_paise` per send for later reporting (docs/10's "per-tenant quota... logged"); a hard circuit-breaker that refuses further sends once a monthly WhatsApp budget is exhausted is a follow-up once real billing from Meta is flowing, not built here.
