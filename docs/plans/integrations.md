## 1. Purpose and boundaries

Integrations is the file-based bridge to Tarsun's existing systems and the outbound files its CA and the government eventually need (docs/10, ADR 0014, docs/17 A1/A5/A7/A11). Its own schema header says it plainly: "the integration bus is files, not APIs." It owns `tally_mappings`, `tally_sync_ledger`, `export_jobs`, `import_jobs`, `import_rows` — no other module writes them. It never calls a manufacturer's, a brand's or a GSP's server: every `import_rows` row starts life as a report the operator downloaded from TradeEzee or FieldAssist and uploaded here, and every `export_jobs` file is a download the operator hands to the CA or a GSP tool later. The post-pilot Node-SEA Tally Connector that actually polls a live TallyPrime instance (docs/10, D21) is out of scope for this slice.

It **calls out** to (never another module's tables, only its exported service, per docs/16):

- `RetailersService` (retailers module, built) — `upsert()` for party-master rows, plus two new methods this slice needs added there: `linkExternalCode(tx, {id, system, code, retailerId})` writing `external_party_codes` (docs/17 A7 — currently unwritten by any module) and `recordPurchaseHistory(tx, rows[])` writing `retailer_purchase_history` (docs/17 A11 — also currently unwritten). Both tables already exist in `retailers.ts`; nothing in this module inserts into them directly.
- `CatalogService` (catalog module, built) — `search()` to find candidate global variants for an item-master or brand-invoice row; **never** `propose()` (§4.12).
- `TenantCatalogService` (tenant-catalog module, built) — `upsertListing()` to list a matched variant for the tenant from an item-master row; `suppliers()` and `tenant_brands` (read) for the Tally/GST export filters.
- `BillingService` (billing module, not yet built — `docs/plans/billing.md`) — `invoices.importBrandDms` exactly as billing.md §2 already defines it, called once per matched FieldAssist row with `orderId` omitted (§4.7); `registers.salesRegister` / `registers.gstSummary`, billing.md's own words: "integrations reads it through this procedure, never through the tables" — the Tally sales-voucher and GSTR-1 source; a new method this slice needs billing to add, **not covered by billing.md today**: `invoices.recordOpeningInvoice(tx, {id, retailerId, amountPaise, asOfDate, importJobId})` — a bare header-only invoice, `source = 'import'`, `series_code = 'OPEN'`, numbered at issue exactly like every other series, no lines, no stock (§8.4).
- `ReceivablesService` (receivables module, not yet built — `docs/plans/receivables.md`) — `postOpeningBalance(tx, {retailerId, invoiceId, amountPaise, asOfDate, importJobId})` exactly as receivables.md §1/§2 already defines and names it; `accounts.list` / `journal.list` / `receipts.list` as the Tally receipts-voucher and chart-of-accounts source.
- `ProcurementService` (procurement module, built) — `SupplierInvoiceService.list()` as the Tally purchase-voucher source.

It is **called in** by:

- the console's imports wizard and Tally/exports screens (owner, manager, accountant only — no salesperson, warehouse, delivery or retailer screen in any of the six apps ever touches this module, so it mounts only in `owner-service` and `manager-service`, never the other four);
- `ClaimsService` (`docs/plans/claims.md` §1/§7, already committed): `IntegrationsService.enqueueExport({kind, params, requestedBy})` gets it an `export_jobs` row for a claim sheet without duplicating that insert. The claim sheet's own **rendering** stays claims' worker job (`claims.statement.render`); this module's own export-render worker only ever renders `kind IN ('tally_xml','gstr1_json','sales_register_xlsx','outstanding_xlsx','eway_bill_json','einvoice_json')` (§7).

It emits `ImportCommitted` / `ExportReady` outbox events (notifications, reporting). It never writes `invoices`, `invoice_lines`, `credit_notes`, `receipts`, `journal_entries`, `journal_lines`, `retailers`, `retailer_links`, `tenant_products`, `product_variants`, `sales_orders` or `sales_order_lines` — every one of those goes through the owning module's service, inside the same per-row transaction the commit worker opens for that row (§4.4).

## 3. Schema changes needed

Everything else the module needs already exists in `backend/libs/database/src/schema/integrations.ts` (`tally_mappings`, `tally_sync_ledger`, `export_jobs`, `import_jobs`, `import_rows`, all already FORCE RLS + `tenantRolePolicy(..., BACK_OFFICE_ROLES)` from migration 0003 — §2's role table needs no RLS change at all), `retailers.ts` (`external_party_codes`, `retailer_purchase_history`, both fully defined and, per a repo-wide grep, written by nothing yet — this module is their first writer, through `RetailersService`), `billing.ts` (`invoices.source` already has the `'import'` value this brief needs) and `tenant-catalog.ts` (`tenant_brands.tally_export_source`). Four small, expand-only additions in `backend/libs/database/migrations/0006_integrations_guards.sql`, appended to `migrations/meta/_journal.json`:

1. `ALTER TYPE job_status ADD VALUE 'staged';` — **its own statement, outside any transaction block** (Postgres rule for `ADD VALUE`, same note claims.md makes for `claim_status`). The existing five values (`queued, running, succeeded, failed, cancelled`) cannot tell "parsed and waiting for a human to review" apart from "actively committing" or "fully committed" — `staged` is that missing state, shared with `export_jobs` (unused there; an export never pauses for review).
2. `import_jobs.started_at timestamptz`, `import_jobs.finished_at timestamptz` (both nullable) — `export_jobs` already has this pair; `import_jobs` was missing it, and the wizard's progress screen needs it for both phases (staging and committing).
3. `import_rows.reviewed_by text references users(id)`, `import_rows.reviewed_at timestamptz` (both nullable) — set by `imports.rows.override` (§2); without it there is no record of who resolved a row before an opening-balance or brand-DMS commit.
4. `CREATE INDEX tally_sync_ledger_export_idx ON tally_sync_ledger (tenant_id, export_job_id);` — the export-detail screen's "what did this job actually push" list (today only the `(tenant, docType, docId)` unique index exists, which is the dedupe key, not a query path).

No new tables, no new RLS policy anywhere in this module — every role edge case (salesperson/warehouse/delivery/retailer must see and touch nothing) is already the effect of `tenantRolePolicy(..., BACK_OFFICE_ROLES)` on all five tables since migration 0003.

## 4. Domain rules and edge cases

1. **Files are the integration surface, not APIs** (docs/10, ADR 0014). This module never calls FieldAssist's or TradeEzee's servers, and never calls a GSP. Every row starts as a file the operator downloaded from that system's own report/export screen.
2. **Nothing binary through the service** (docs/20 rule 15). `imports.create` accepts only an already-uploaded `sourceObjectKey`; `exports.get` returns a pre-signed URL, never bytes.
3. **Long work never runs on the request path** (docs/20 rule 3). Staging, matching, committing and rendering are all pg-boss jobs; every endpoint that starts one returns a job id and `queued`/`running`/`staged`, never blocks for the work itself.
4. **Per-row commit, not one all-or-nothing transaction.** Each `import_rows` row commits in its **own** transaction, keyed `import:<jobId>:<rowNo>`, so one bad row of 5,000 never rolls back the other 4,999 — mirrors billing's "one invoice line per lot" grain. `import_jobs.okRows`/`errorRows` are always recomputed from `import_rows`, never incremented in memory (docs/20 rule 1).
5. **Idempotent by construction** (docs/20 rule 4). `imports.create`/`commit`, `exports.create`, `tally.mappings.upsert` all wrap in `idempotent()`. Each row-commit step is **individually** idempotent (the target service's own `idempotencyKey`, derived from the same `import:<jobId>:<rowNo>` key, e.g. suffixed `:invoice` / `:journal`), so a worker crash between, say, `BillingService.recordOpeningInvoice` and `ReceivablesService.postOpeningBalance` for the same row is healed by simply re-running `commit` on that row — never a rollback of the invoice already created, never a duplicate.
6. **`retailers` target.** Matching: exact `external_party_codes` hit → exact `phone`/`gstin` → fuzzy name (`pg_trgm`, already an installed extension per D12) with a similarity floor. A confident match calls `RetailersService.upsert` with only name/phone/address/gstin/pan/beat/code from the mapped columns — `creditLimitPaise`/`creditDays`/`tier`/`creditMode` are **never** set by an import (those stay `retailers.setCredit`'s job, back office one row at a time, with its own approval trail); a row below the confidence floor or with more than one close candidate is `needs_review`, never auto-picked.
7. **`products` target.** Matching: exact `product_variants.ean` → fuzzy `tenant_products.local_alias`/`product_variants.name` via `CatalogService.search`. A match calls `TenantCatalogService.upsertListing` (local alias, case-size override from the row). **No new global product is ever created from a bulk import** — a TradeEzee export lacks the structured fields (`manufacturerId`, `netQty`, `netUnit`, `defaultCaseSize`) `catalog.propose` requires, so an unmatched row stays `needs_review`; the operator either picks an existing variant (`imports.rows.override`) or proposes the product properly on the catalog screen first and re-runs `preview`.
8. **`opening_balances` target — per bill, not a lump sum** (receivables.md's own recommendation, §8.4). One row = one `BillingService.recordOpeningInvoice` (source `'import'`, series `OPEN`) **then** one `ReceivablesService.postOpeningBalance` against that invoice's id — never an aggregated per-retailer credit, so bill-to-bill allocation and ageing buckets work from day one. Refused outside the owner sign-off gate (§2, §4.10). No stock, no `sales_orders` row, ever.
9. **`sales_history` target has no ledger effect** (docs/17 A11 verbatim). A matched row becomes one `RetailersService.recordPurchaseHistory` row (`retailer_purchase_history`, `source = 'migration'`, `importJobId` set) — read later by the suggested-order median-gap engine. Never a journal entry, invoice or stock row.
10. **`brand_dms_invoices` target — never a second legal invoice** (ADR 0014). One matched row = one `BillingService.invoices.importBrandDms` call, `orderId` omitted (a Too Yumm invoice never rides on a DOS-tracked trip — Too Yumm's own field force delivers it; the day-end **photograph** path that does need a trip stop is `docint`'s job and is explicitly refused there today per `docs/plans/docint.md` §8.3, so this bulk file path is the only committed brand-DMS entry point right now, §8.9). Retailer matched via `external_party_codes(system='fieldassist')` (docs/17 A7). A row whose `externalInvoiceNo` already exists on an `invoices` row (billing's `invoices_external_no_idx`) commits as `skipped` with an error, **never** a job-level failure — a bulk import must tolerate an overlapping monthly export exactly like the sync endpoint tolerates a replay (docs/20 rule 6, extended by analogy here even though this is not literally `/sync/upload`). Posts no stock (billing.md §2 `importBrandDms` already says so).
11. **Matching is best-effort and always reviewable, never silently wrong.** No row commits on a guess: below-floor or ambiguous matches are `needs_review`, and `commit` refuses them unless `skipErrors: true` explicitly leaves them uncommitted.
12. **No entity is ever created that the operator did not confirm existed.** §4.6/§4.7 already say this for retailers/products; it applies module-wide — this is a reconciliation tool, not an onboarding one (echoes docs/17 item 27's "never probe/create implicitly" spirit even though the identity-leak concern itself doesn't apply to a back-office actor).
13. **Column mapping is per-`kind`, remembered, never assumed** (the brief's "saved column mappings"). No mapping is hardcoded; `imports.create` without an explicit `mapping` defaults to the most recently used mapping for that exact `kind` **in this tenant** (RLS already scopes it; the query is scoped by `tenant_id` explicitly too for clarity, since a wrong default here would misfile real money).
14. **Tally export never double-posts** (docs/10 acceptance: "the Sales Register matches to the paisa"). Every voucher gets a stable GUID (`sha256(tenantId:docType:docId)`, truncated) written to `tally_sync_ledger`; re-running an overlapping date range compares `contentHash` of the voucher's own field values — unchanged → the **same** GUID re-emitted so Tally's own GUID-keyed import updates instead of duplicating; changed (e.g. a credit note landed on an already-exported invoice) → same GUID, new content, since it is still the same underlying document.
15. **Tally export respects `tenant_brands.tally_export_source` at the invoice-line level, not the whole invoice.** A line whose variant's brand is `tally_export_source = 'brand_dms'` or `'none'` is excluded from the voucher's amount and counted in the job's skip log; an invoice with zero eligible lines emits no voucher at all; a mixed-brand invoice emits a voucher for the eligible subset only — a genuine, undocumented assumption, flagged in §8.6.
16. **GST/e-way/e-invoice exports are read-only snapshots, never a GSP call.** `billing.invoices.requestIrn` (billing.md §2) is the only place an IRN/ack is ever stubbed; `eway_bill_json`/`einvoice_json` here just bundle N invoices' already-stubbed-or-still-null fields into one file for a human to hand to a GSP tool or paste into the government portal later.
17. **Row-level errors are always human-readable and bilingual-ready** (docs/17 B Hindi UX groundwork): every `import_rows.error` and `ImportJob.error` is a short plain-English sentence naming the row/column, never a raw exception string or a Postgres error code — mirrors `SyncRejection`'s messages elsewhere in the codebase.
18. **Bounded work** (docs/20): every list `limit ≤ 200`; `commit`/`preview`/the stage job process rows in batches of 500 so one huge file never starves another tenant's job (per-tenant fairness, docs/20 rule 5); `exports.create`'s date window is capped at 366 days.
19. **IST everywhere a date is matched or minted**: `asOfDate`/`invoiceDate`/`noteDate` fields inside a row are validated as IST business dates at matching time (a garbled date is a row-level error, never a job-level failure); the synthetic `OPEN/nnnn` opening-invoice number is ≤ 16 chars like every other document number (ADR 0001).
20. **Worker jobs run tenant-scoped, not cross-tenant.** The staging/commit/render jobs open `withTenant(db, {tenantId: job.tenantId, actorId: job.requestedBy, actorRole: 'system'})` — **not** the `app_worker`/BYPASSRLS role, which stays reserved for genuinely cross-tenant jobs (outbox relay, retention, per CLAUDE.md). `BACK_OFFICE` already includes `'system'`, so every RLS policy and `requireRole` check in this module passes for the worker unchanged.

## 5. DB-backed spec list

`backend/libs/core/src/modules/integrations/integrations.spec.ts`, wrapped in `describeDb`, booting `[IntegrationsModule, RetailersModule, CatalogModule, TenantCatalogModule, BillingModule?, ReceivablesModule?, ProcurementModule]` with `bootTestApp`; fixtures built directly with `@dos/db` + `bootstrapTenant`, keyed by a unique `run` suffix (one tenant, an owner/manager/accountant/salesperson/warehouse/delivery/retailer user each, a handful of seeded retailers and variants, one Too-Yumm-like brand with `tally_export_source = 'brand_dms'` alongside an ordinary `'dos'` brand, a supplier invoice and a receipt already posted for the Tally purchases/receipts voucher tests).

1. `stages a TradeEzee party-master CSV and matches retailers by phone` → `status = 'staged'` after `create`, `import_rows` count = source row count, phone-matched rows `matched`, the rest `needs_review`.
2. `preview re-scores rows when the mapping changes, without writing any real entity` → a second `preview` call with a different `mapping` changes `normalized`/`status` on existing rows; zero new `retailers`/`tenant_products` rows exist anywhere.
3. `commit creates and updates retailers idempotently` → matched rows call through to real `retailers` rows; replaying `commit` on an already-`succeeded` job is a no-op, no duplicate retailer.
4. `row override forces a match and remembers the external code` → `imports.rows.override` with `retailerId` on a `fieldassist_invoices` row writes an `external_party_codes(system='fieldassist')` row; a second job whose raw data carries the same source code auto-matches with no review needed.
5. `item-master rows never auto-propose a product` → an unmatched row stays `needs_review` through `commit` (with `skipErrors: true`, `status → skipped`); no `product_variants` or `tenant_products` row appears for it.
6. `FieldAssist invoice import commits a brand-DMS invoice with no stock movement` → `invoices.source = 'brand_dms_import'`, `external_invoice_no` set, `order_id IS NULL`, zero new `stock_ledger` rows.
7. `duplicate external invoice number is skipped, not a job failure` → importing the same FieldAssist row twice (replayed job, or two overlapping files) leaves the second occurrence `skipped` with an error; the job still `succeeded`; exactly one `invoices` row exists.
8. `opening-balance commit is refused without the owner sign-off` → manager `commit` on a `target='opening_balances'` job → 403; owner without `confirmOpeningBalances` → 403; owner with it → `succeeded`, one `invoices(source='import', series_code='OPEN')` row and one balanced journal entry per committed row.
9. `sales-register rows have no ledger effect` → after commit, `retailer_purchase_history` rows exist; zero new `journal_entries`/`invoices` rows.
10. `Tally export excludes brand_dms-sourced lines` → a mixed-brand invoice's rendered voucher amount equals only its `tally_export_source='dos'` lines; a Too-Yumm-only invoice's voucher is skipped entirely and counted in the job's skip log.
11. `Tally export is safe to re-run` → exporting the same date range twice writes the same GUID into `tally_sync_ledger` for an unchanged voucher — one row, not two, on `(tenant, doc_type, doc_id)`.
12. `Tally mapping upsert is idempotent` → same `idempotencyKey` twice → one `tally_mappings` row; `tally.mappings.list` reflects the new `tallyName` immediately.
13. `export job renders asynchronously and returns a signed URL only once ready` → `exports.create` returns `status='queued'`, `objectKey=null`; after the render job runs, `exports.get` returns a non-null `url`.
14. `import rows paginate and filter by status` → `imports.rows.list` with `status='needs_review'` returns only those rows; `limit`/`cursor` behave like every other list in the codebase.
15. `401 without tenant context` → any procedure called with no actor headers is 401.
16. **RLS/role tests, one per role that must be refused:**
    - `salesperson` → `GET /integrations/imports` and `POST /integrations/imports` both 403; a direct `withTenant` select as `salesperson` on `import_jobs`, `tally_mappings` and `export_jobs` returns 0 rows.
    - `warehouse` → same as salesperson (this module has no warehouse carve-out, unlike billing's issuer role).
    - `delivery` → same as salesperson.
    - `retailer` → same as salesperson, plus `GET /integrations/exports/{id}` for another tenant's export is `NOT_FOUND`, never a leak.
17. `tenant isolation` → an import job created in tenant A is invisible to an owner of tenant B on every list and 404s on `imports.get`; a Tally mapping in tenant A never appears in tenant B's `tally.mappings.list`.

## 7. Worker jobs / outbox events

**pg-boss jobs** (registered in `backend/worker`):

- `integrations.imports.stage` — parses the file at `source_object_key`, inserts `import_rows`, runs the matcher (§4.6–§4.10), sets `status='staged'|'failed'`, `total_rows`, `started_at`/`finished_at`. Triggered by `imports.create`.
- `integrations.imports.commit` — walks `matched` rows in batches of 500, calls the one target-specific service method per row (§4.4), updates each row and the job's counts, sets `status='succeeded'|'failed'`, `committed_at`. Triggered by `imports.commit`.
- `integrations.exports.render` — renders `kind IN ('tally_xml','gstr1_json','sales_register_xlsx','outstanding_xlsx','eway_bill_json','einvoice_json')` by calling the owning module's register-read method (`BillingService`, `ReceivablesService`, `ProcurementService`), uploads the file to object storage, sets `object_key`/`row_count`/`finished_at`/`status`; for `tally_xml` additionally writes `tally_sync_ledger` rows (§4.14). `claim_sheet` export jobs are **not** consumed here — `claims.statement.render` (docs/plans/claims.md §7) owns that one kind.

**Outbox events** (written in the same transaction as the state change, relayed by the existing worker relay):

| event             | aggregate             | payload                                          | consumers                                                          |
| ----------------- | --------------------- | ------------------------------------------------ | ------------------------------------------------------------------ |
| `ImportCommitted` | `import_job` / job id | `{importJobId, kind, target, okRows, errorRows}` | notifications ("import finished: 42 ok, 3 need review"), reporting |
| `ExportReady`     | `export_job` / job id | `{exportJobId, kind, objectKey, rowCount}`       | notifications ("your Tally export is ready")                       |

**Consumed**: none, in this slice. `receivables.md` and `delivery.md` both list `integrations` as a future consumer of `ReceiptRecorded`/`InvoiceIssued`-shaped events for an _incremental_ Tally push — that is the post-pilot Node-SEA Connector (docs/10, D21), explicitly month 2, not this slice; this module's Tally export is a manual date-range pull.

## 8. Founder questions this brief had to assume an answer for

1. **Does the CA already key Too Yumm invoices into Tally? (docs/17 §C8.)** Assumed **yes** — the exact assumption `docs/plans/docint.md` §8.3 already makes for the same open question — so `tenant_brands.tally_export_source` seeds Too Yumm as `'brand_dms'` and this module's Tally export excludes its lines (§4.15) rather than risk a double-post the founder would have to notice and undo by hand.
2. **No real TradeEzee/FieldAssist sample export exists yet (docs/17 §C6).** Assumed column layouts based only on the report **names** (party master, item master, outstanding, sales register; Too Yumm's invoice export); the saved-mapping screen (§4.13) exists precisely so the real columns can be wired up with zero code change once Tarsun supplies one export of each, per docs/17 §C6's own open item.
3. **Persistent SKU/party code mapping across imports.** Assumed **no new table** this slice: `external_party_codes` persists retailer matches (explicitly required by the brief), but product/SKU matches are re-scored fresh on every import except where `product_variants.ean` gives an exact hit (§4.7). If a monthly FieldAssist import keeps asking the operator to re-resolve the same ambiguous SKUs, the fix is an `external_product_codes` table shaped exactly like `external_party_codes` — deferred until that pain is real.
4. **Opening-balance shape.** Assumed receivables.md's own recommendation (per-bill, not a lump sum) and its `postOpeningBalance` signature verbatim. The genuine gap this brief surfaces: `billing.md` never covers `invoices.source = 'import'` at all, so this slice needs a small new `BillingService.invoices.recordOpeningInvoice` method (§1) that billing.md's author did not anticipate — flagged for the founder/whoever builds billing first, since two sibling briefs now depend on it.
5. **Per-retailer variance screen for the outstanding import (docs/17 B).** Assumed **out of scope** for `commit` itself — the owner+flag gate (§4.10) is the sign-off this brief builds; a richer side-by-side comparison against `retailer_outstanding_summary` before that click is a reporting/receivables-console concern reading this module's `import_rows.normalized`, not a new procedure here.
6. **Mixed-brand Tally voucher splitting.** No doc resolves this. Assumed a **partial-amount voucher** over excluding the whole invoice (§4.15) — the same kind of call `billing.md` §8.3 made for mixed-brand cash discount, flagged the same way here rather than silently picked.
7. **Who may run the generic imports.** Assumed **owner/manager/accountant uniformly** for everything except the opening-balance sign-off (owner only, §4.10) — a bulk version of `retailers.upsert`/`tenantCatalog.upsertListing` needs no narrower gate than the one-row version already has; only money entering the books without an invoice behind it (opening balances) gets the extra owner-only lock.
8. **Tally XML _masters_ import and FieldAssist _order_ (SFA) import.** Both are anticipated by the existing `import_jobs.kind` column comment (`tally_xml`, `fieldassist_orders`) but are **explicitly out of this slice's scope** per the brief's own bullet list — Tally is export-only here, FieldAssist is invoices only. Not a gap; a deliberately smaller cut.
9. **`ALTER TYPE job_status ADD VALUE 'staged'` vs. a separate `reviewed`/`phase` column (§3.1).** Assumed extending the existing shared enum is simpler than a second status axis or a new table, since only one module (`import_jobs`) ever needs the value and it costs `export_jobs` nothing. A stricter reviewer might prefer a boolean `import_jobs.staged boolean` instead — flagged since it is a real, if small, design choice.
