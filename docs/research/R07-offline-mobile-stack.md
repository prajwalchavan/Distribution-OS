## 1. Executive recommendation

**Build on Expo SDK 57 (React Native 0.86, New Architecture only) + TypeScript, with PowerSync as the sync engine over Postgres, op-sqlite on device, EAS Build/Update for delivery, expo-location + expo-task-manager for trip-scoped GPS, react-native-maps (Google Maps mobile SDK, which is free/unlimited on native) for display with URL-scheme hand-off to Google Maps for navigation, expo-camera (ML Kit) for barcodes, a document-scanner plugin for invoice photos, i18next for Hindi/English, Supabase Auth phone-OTP routed through the Send-SMS hook to MSG91 (SMS) and WhatsApp authentication templates, Expo Push (free) for staff, and WhatsApp Cloud API utility templates for retailers.**

### 2.2 Flutter (verified)

Flutter 3.47.2 stable (2026-08-12), 3.44 (2026-05-18), 3.41 (2026-02-11); full iOS 26 / Xcode 26 support; Apple-mandated UIScene migration ([docs.flutter.dev/release/whats-new](https://docs.flutter.dev/release/whats-new)). ### 2.3 Decision

For a **solo TypeScript developer** who must also write the backend, shared Zod/TS domain types (pricing engine, order state machines, invoice schema) across server and five app surfaces are worth more than Flutter's rendering consistency. Expo additionally gives OTA fixes (EAS Update) for the inevitable field-bug-of-the-day without a store round-trip, and one config-plugin-driven native project. Flutter's code push equivalent (Shorebird) exists but was **[unverified]** in this session.

**Recommended layout:** one monorepo (pnpm workspaces) with `apps/team` (Distributor + Salesperson + Manager + Delivery as role-gated routes in ONE binary) and `apps/retailer` (separate binary), plus `packages/domain`, `packages/sync-schema`, `packages/ui`. Two binaries, not five: the team app is the only one that needs background location, camera-for-invoices and foreground-service permissions, which keeps the retailer app's Play/App Store review trivial and its permission list short. (This is a recommended refinement of the "five apps" decision — five products, two binaries — flagged here as a change with reasons: store review scope, permission declarations, and solo-dev release load.)

### 3.2 PowerSync — the details that shape your schema and backend

1. **Every synced table needs a primary key column named `id` of type `text`.** Use UUIDs generated on the client (v7 for time-ordering is fine) everywhere — orders, order lines, visits, GPS points, attachments.
2. **Stream queries cannot use `GROUP BY`, `ORDER BY`, `LIMIT`.** Pre-aggregate dashboard numbers server-side into small per-tenant/per-role summary tables (PowerSync's national-scale showcase moved from one 2M-row summary table to per-administrative-level tables and cut wire traffic ~1000×).
3. **Per-beat partial sync pattern** (Sync Streams): a `rep_beat_assignments` parameter query yields `beat_id`s for `auth.user_id()`; data queries select `retailers WHERE beat_id IN …`, `price_lists WHERE tenant_id = auth.parameter('tenant_id')`, `orders WHERE rep_id = auth.user_id() AND created_at > …`. Reassigning a rep to another beat changes the parameter query result and the device re-syncs. Global masters (Manufacturer, Product) go in an `auto_subscribe: true` reference stream.
4. **Salesperson-must-never-see-purchase-price** (the Vyapar failure) is enforced at the _stream_ level: the rep's stream selects a `sell_price` view/columns only; cost/margin columns never leave Postgres. Do not rely on UI hiding.
5. **Write path**: `uploadData()` posts each local transaction to your endpoint. PowerSync says process writes _immediately_ (no deferred queue), return 5xx only for transient failures, **never 4xx** (it blocks the queue forever), and report validation/business rejections with 2xx plus an error row in a synced `sync_errors` table. Include the per-client op ID as the idempotency key.
6. **Consistency**: client shows local writes immediately but "does not advance to a new checkpoint while mutations remain unacknowledged"; clients only ever see complete checkpoints (no half-applied transactions).
7. **Attachments** (invoice photos, POD photos): built into SDK ≥1.16; metadata rows sync through PowerSync, bytes go straight to Supabase Storage/S3 via signed URLs with a local queue and retry. Supports the "full-quality images, never compress" decision.
8. **Supabase specifics**: PowerSync reads WAL via a `powersync_role`; JWKS auto-configured for new projects; "Sync Streams generally mirror your RLS setup"; writes through supabase-js still respect RLS. Watch `max_wal_size`/`max_slot_wal_keep_size` on idle instances and avoid `FOR ALL TABLES` publications.
9. **Licensing**: the service is FSL-1.1 with an Apache-2.0 future license; Open Edition self-host has no dashboard and no custom write checkpoints. Start on Cloud Free (2 GB/mo, 50 concurrent clients is enough for the Tarsun pilot), move to Pro $49/mo at roughly 10+ distributors.

### 3.3 What the custom-outbox alternative would cost you

Even with PowerSync you still write: the upload endpoint, idempotency table, domain validation, and the `sync_errors` feedback loop. What you _avoid_ writing: change feeds with tombstones, per-user cursors, bucket-level partial sync that re-evaluates on reassignment, checkpoint atomicity, attachment queues, and reconnect logic. For a solo dev, that is months of work and the highest-risk code in the product.

## 4. Background GPS tracking (delivery teams, owner-required)

### 4.1 Expo capabilities (verified from docs.expo.dev)

- `Location.startLocationUpdatesAsync(taskName, options)` with `TaskManager.defineTask` **at module top level** (never inside React lifecycle). Options: `accuracy` (Lowest…BestForNavigation), `deferredUpdatesDistance` (m), `deferredUpdatesInterval` (ms), iOS `pausesUpdatesAutomatically`, `activityType` (`AutomotiveNavigation` for vans), `showsBackgroundLocationIndicator`, Android foreground-service notification (title/body/96×96 white icon).
- Config plugin flags: `isAndroidBackgroundLocationEnabled`, `isAndroidForegroundServiceEnabled` (defaults true when background enabled), `isIosBackgroundLocationEnabled` (adds `UIBackgroundModes: location`), `locationAlwaysAndWhenInUsePermission` string.
- `requestBackgroundPermissionsAsync()` maps to iOS _Always_. Caveat: if the user chose "Allow Once", a later background request "will silently fail" with `denied`; the user must go to Settings.
- Termination: background location stops if the app is force-killed; "Android won't auto-restart after termination for location events (unlike iOS)"; behaviour on removal from recents varies by vendor (relevant for Indian OEM skins — Xiaomi/Vivo/Oppo battery killers).
- Geofencing: `startGeofencingAsync` — iOS max 20 regions, Android max 100 per app.
- Not available in Expo Go (iOS needs dev build; Android TaskManager absent entirely).
- `expo-background-task` (WorkManager / BGTaskScheduler): ≥15-minute, inexact scheduling; fine for flushing an outbox, useless for continuous tracking.

### 4.2 Platform policy (verified)

**Android** ([permissions/background](https://developer.android.com/develop/sensors-and-location/location/permissions/background), [fg-service-types](https://developer.android.com/develop/background-work/services/fg-service-types), [Play policy 9799150](https://support.google.com/googleplay/android-developer/answer/9799150), [Play FGS 13392821](https://support.google.com/googleplay/android-developer/answer/13392821)):

- Android 11+: system dialog has no "Allow all the time"; the user must go to Settings; show an educational screen first, using `getBackgroundPermissionOptionLabel()`.
- API 34+: foreground service must declare `foregroundServiceType="location"` and hold `FOREGROUND_SERVICE_LOCATION`; you cannot _start_ a location FGS from the background unless you hold `ACCESS_BACKGROUND_LOCATION`.
- Play Console requires a **Permissions Declaration Form** (exactly one background-location feature), an in-app **prominent disclosure** dialog before the runtime prompt using the wording pattern "This app collects location data to enable [feature] … even when the app is closed or not in use", and a ≤30 s video showing the disclosure, prompt and feature. "Delivery/ride tracking (driver perspective)" is an explicitly acceptable use case. FGS types (location) also need their own Play Console declaration with a video.

**iOS** ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)): 2.5.4 background modes only for intended purposes (location is listed); 5.1.1 accurate purpose strings; 5.1.2 explicit disclosure that location is shared with the employer; 5.1.5 "notify and obtain consent before collecting, transmitting, or using location data". 4.8 (Sign in with Apple) is **not** triggered by phone-OTP login — only by third-party social logins.

### 4.3 Design that passes review and saves battery

1. **Trip-scoped tracking, not shift-long tracking.** Start updates when the driver taps "Start trip", stop at "End trip". This satisfies "user-initiated", is the acceptable Play use case verbatim, and halves battery cost.
2. Foreground-service notification on Android ("Trip in progress — location shared with Tarsun Enterprises"), `showsBackgroundLocationIndicator: true` on iOS. Both double as the transparency Apple 5.1.2 wants.
3. `accuracy: Balanced` in motion + `deferredUpdatesDistance: 50` m / `deferredUpdatesInterval: 30 s`, `activityType: AutomotiveNavigation`. Write points into a local `trip_points` table (PowerSync-synced, rep-scoped) so tracking works with no signal and the owner's live map catches up on reconnect.
4. Separate consent record in Postgres (`location_consents`) captured with the disclosure dialog, because Apple 5.1.2 and Indian labour practice both want it and the owner will ask for it later.
5. If Indian OEM battery managers kill the service, the paid Transistorsoft `react-native-background-geolocation` (5.5.0, Expo config plugin, motion-state machine, durable SQLite HTTP queue; perpetual license **$399 for 1 app**, $599 for 5, debug builds free) is the escape hatch. Start with expo-location; budget the $399 as a known option.

## 6. Barcode / QR scanning and invoice capture

Verified: `expo-camera@57` supports 13 symbologies (`qr, ean13, ean8, code128, code39, code93, itf14, codabar, upc_a, upc_e, pdf417, datamatrix, aztec`) via `onBarcodeScanned`; `launchScanner` uses Google Code Scanner on Android and `DataScannerViewController` on iOS 16+; `scanFromURLAsync` is QR-only on iOS; barcode support can be compiled out (`barcodeScannerEnabled: false`) to shrink the retailer app. ML Kit on Android: bundled model +2.4 MB works without Play Services; unbundled +200 KB needs Play Services (present on essentially all Indian retail phones, but bundled is safer for the team app). Alternative `react-native-vision-camera@5.2.3` + ML Kit plugin for frame-processor throughput if EAN scanning in a dim godown proves slow ([expo-camera](https://docs.expo.dev/versions/latest/sdk/camera/), [ML Kit](https://developers.google.com/ml-kit/vision/barcode-scanning/android), [VisionCamera](https://visioncamera.margelo.com/docs/guides/code-scanning)).

Invoice capture (Document Intelligence pipeline): use `react-native-document-scanner-plugin@2.0.4` (ML Kit Document Scanner on Android / VisionKit on iOS — edge detection, perspective correction, multi-page) and keep `quality: 1`, `skipProcessing: false`, largest `pictureSize`; upload the original via the PowerSync attachment queue to object storage and never downscale (this is the anti-Vyapar requirement). Also read the e-invoice IRN QR (`qr` type) on Reliance/Guiltfree invoices — it carries the signed JSON with IRN, seller/buyer GSTIN, total and item count, a free cross-check for the LLM extraction.

## 7. Hindi + English localisation

- `expo-localization` (`getLocales()[0].languageCode`) + **`i18next@26.4.2` / `react-i18next`** (Expo docs call it "stable, well-maintained"); Lingui 6.6 is the alternative if you want compile-time extraction. Declare `supportedLocales: { ios: ["en","hi"], android: ["en","hi"] }` in the config plugin so per-app language settings work; set `CFBundleAllowMixedLocalizations` for iOS metadata ([docs.expo.dev/guides/localization](https://docs.expo.dev/guides/localization/)).
- Fonts: both OSes ship Devanagari system fonts; for consistent rendering across cheap Android skins bundle `@expo-google-fonts/noto-sans-devanagari@0.4.1`.
- Numbers/currency: use `Intl.NumberFormat('en-IN', {style:'currency', currency:'INR'})` for lakh/crore grouping (₹1,23,456.00). Hermes Intl coverage on iOS vs Android differs historically — test on both; **[unverified this session]**; fall back to a hand-written Indian grouping formatter in `packages/domain` if any device misgroups.
- Product names stay in English/brand form ("Campa 1L"); localise UI chrome, statuses, error strings, WhatsApp templates (Meta templates need per-language approval).

## 9. Push notifications

Expo push service: **no cost**, 600 notifications/s/project, at-least-once hand-off to FCM/APNs with push receipts; requires FCM v1 service-account credentials (Android) and an APNs key (iOS); removed from Expo Go in SDK 53+; you can bypass it with `getDevicePushTokenAsync` and hit FCM/APNs directly ([overview](https://docs.expo.dev/push-notifications/overview/), [FAQ](https://docs.expo.dev/push-notifications/faq/)). Use it for staff-facing events (approval requests, picklist ready, trip assigned). Retailers get WhatsApp/SMS per the existing decision; push in the retailer app is a nice-to-have because kirana owners rarely enable it.

## 12. Top 10 pitfalls (ranked by how likely they are to bite a solo dev)

1. **Choosing a sync engine that is quietly dying.** ElectricSQL Cloud is winding down after the Databricks deal (2026-08-11); WatermelonDB has had no release since April 2025 and an open "abandoned?" issue; Replicache is in maintenance mode. Only PowerSync, RxDB and Zero are actively shipping — and Zero rejects offline writes.
2. **Returning 4xx from the upload endpoint.** PowerSync's queue is blocking FIFO; a 4xx wedges that device forever. Validation failures must return 2xx plus an error row; only transient failures return 5xx.
3. **Syncing too much per device.** A distributor's full order history to every rep's phone blows the 2 GB/mo free tier and phone storage. Scope streams to the rep's beats and a rolling 60–90-day window; pre-aggregate dashboard numbers into per-role summary tables.
4. **Leaking purchase price through a sync stream.** The Vyapar failure repeats itself if `products` syncs the cost column to the rep role. Put cost/margin in a separate table or view that only the owner stream selects, and test it with a "rep device dump" in CI.
5. **Background location without the paperwork.** Missing prominent-disclosure dialog, Play declaration form, FGS type declaration or demo video gets the team app rejected; "Allow Once" on iOS silently denies background permission later; Indian OEM battery killers stop the service. Trip-scoped tracking with a persistent notification is the fix; Transistorsoft is the escape hatch.
6. **Testing in Expo Go and shipping surprises.** Background location, TaskManager on Android, push (SDK 53+), SQLCipher, op-sqlite and Ditto/MapLibre native modules all need development builds. Set up EAS dev builds on day one.
7. **Using Firebase phone auth or Twilio Verify for Indian OTPs.** $0.07/SMS (Firebase) or ~$0.13 (Twilio) vs ₹0.115 on WhatsApp / ₹0.2 on MSG91 — a 30–60× cost gap that shows up the moment retailers start logging in.
8. **Assuming Ola/Google map pricing is static.** Ola moved to mandatory prepaid credits on 2026-09-01; Google's India card is a separate schedule from global. Wrap maps behind a provider interface and pin lat/lng at first visit instead of geocoding addresses.
9. **Non-`text id` primary keys or server-generated IDs.** PowerSync needs `id text` on every synced table; server serials break offline creation. Generate UUIDs on the client; keep human-facing numbers (invoice no. GL/1686 style) as a separate server-assigned column allocated on commit.
10. **Treating OTA updates as a free pass.** EAS Update cannot change native modules/permissions; a runtime-version mismatch strands users on old binaries; Expo SDK moves three times a year and SDK 55+ dropped the Legacy Architecture and requires Xcode 26. Plan one native release per quarter and keep every native dependency New-Architecture-only (which rules WatermelonDB out again).
