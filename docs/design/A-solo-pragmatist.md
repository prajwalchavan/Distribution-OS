# Distribution OS — Architecture Proposal A ("solo pragmatist")

Author stance: one developer, production-grade pilot for Tarsun Enterprises in ~20 weeks, then scale without rewrites. Boring, documented tech; the fewest stateful systems possible; buy managed services where they are cheap; never compromise ledgers, idempotency or tenant isolation. Evidence base: CONTEXT.md and research reports R01–R10 (cited inline as R0x §y). Anything that changes a decision in CONTEXT.md is marked **[CHANGE]** with the reason.

## 1. Verdict on the five-apps plan

### 1.1 Keep five products; ship three deliverables

CONTEXT is explicit that five apps were confirmed twice. Nothing below removes a product or a screen. What changes is the number of **binaries and store listings**, because that is what costs a solo developer time and store-review risk, not the number of role experiences.

| Product (CONTEXT)       | Deliverable                                                                                           | Surface                                                                                                                                                                               | Why                                                                                                                                                                                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Distributor (owner) app | **Team app** (Owner module) + **Owner web console**                                                   | Mobile for live dashboard, approvals, live delivery map, price control quick-edits; web for price lists, scheme setup, Tally mapping, imports, reports/exports, billing desk printing | Owners approve on the phone and configure on a PC. Bulk config screens are miserable on mobile and cost 2–3× to build there.                                                                                                               |
| Salesperson app         | Team app (Sales module)                                                                               | Mobile, offline-first                                                                                                                                                                 | Field, patchy network (R01 §5 sync complaints).                                                                                                                                                                                            |
| Manager (warehouse) app | Team app (Warehouse module) + web Billing desk                                                        | Mobile for invoice photo capture/review, GRN, picklist, packing; web for A4/thermal print, bulk invoicing, day-end                                                                    | The Marg-shaped invoice (R02 §7) prints from a PC in every distributor office today.                                                                                                                                                       |
| Delivery app            | Team app (Delivery module)                                                                            | Mobile, offline-first, trip-scoped GPS                                                                                                                                                | Same permissions bundle as the sales module (camera, location).                                                                                                                                                                            |
| Retailer app            | **WhatsApp intake** (week 13) → **Retailer PWA** (week 18+) → **Retailer native binary** (post-pilot) | Online-first                                                                                                                                                                          | R10 §2.14 and §3: install friction is the adoption killer; R04 §5.2: no adoption data exists for an independent distributor's own app, so measure before investing in a store binary. **[CHANGE]** to sequencing only, not to the product. |

Why one Team binary (R07 §2.3): the Team app is the only artefact that needs background location, a location-typed foreground service, camera-for-documents and the Play Console permission declaration + video (R07 §4.2). Putting the Owner, Sales, Warehouse and Delivery roles in one binary means that paperwork is done once, one EAS pipeline, one OTA channel, one quarterly native release. Role gating is a route group selected from the membership role in the session; a person with two roles (Tarsun's owner will also bill for a while) simply sees two tabs. The Retailer surface stays a separate binary because its permission list must be minimal and its user base will eventually be 100× larger.

### 1.2 Sequencing by dependency (the founder wants everything; here is the order in which "everything" can be built without rework)

Every screen reads from ledgers that another screen writes. The dependency graph is:

```
tenancy/identity ─► catalog (global + tenant) ─► retailers/beats ─► pricing engine
      │                                                                   │
      └──────────────► inventory ledger ◄── procurement/GRN ◄── docint     ▼
                            │                                          orders (rep)
                            ▼                                              │
                    warehouse (picklist/pack) ─► billing ─► receivables ◄───┘
                            │                        │
                            ▼                        ▼
                     delivery/trips/GPS ─────► settlement ─► owner dashboard/reporting
                                                             │
                                          notifications ◄────┴──► exports (Tally/Excel)
```

Concretely: the Warehouse module's GRN-by-photo and the Sales module's order-taking are built first because they populate stock and orders, which every other screen reads (R08 §10). Delivery follows billing because a delivery stop needs an invoice to collect against. The Owner dashboard is built last of the core because it is an aggregate over everything else, and it should be built as CQRS-light read models (§3.6) rather than as ad-hoc queries.

### 3.3 Data model highlights

**Tenancy.** Shared schema + `tenant_id uuid NOT NULL` on every tenant table + RLS with `ENABLE` and `FORCE ROW LEVEL SECURITY`; API/worker connect as `app_rw` (not owner, no BYPASSRLS); every unit of work runs inside a transaction that starts with `SELECT set_config('app.tenant_id', $1, true), set_config('app.actor_role', $2, true), set_config('app.actor_id', $3, true)`; policies use `(SELECT current_setting('app.tenant_id', true)::uuid)`; every index leads with `tenant_id`; the repository layer still adds `WHERE tenant_id = ?` (R08 §2.2). Global tables (`manufacturers`, `brands`, `products`, `product_packs`, `product_external_codes`, `product_aliases`, `hsn_rates`, `suppliers`, `supplier_aliases`, `retailer_identities`) have no `tenant_id`; writes go through `app_curator` or through a promotion workflow.

**IDs.** All synced/domain tables use `id text` primary keys holding UUIDv7 generated on the client (offline creation) or server; PowerSync requires `id text` (R07 §3.2). Human-facing numbers (`GL/1686`, GRN-0042, TRIP-2026-09-04-01) are separate server-assigned columns allocated at commit from `document_sequences` under a row lock, never client-side. Invoice numbers are ≤16 chars and unique per series per FY (IRN-ready, R05 §4).

**Stock ledger (append-only).**

```sql
stock_ledger(id, tenant_id, occurred_at, product_id, lot_id, location_id,
             qty_delta int, reason stock_reason, ref_type, ref_id, actor_id,
             idempotency_key, created_at)            -- pieces, signed, never updated
stock_balance(tenant_id, product_id, lot_id, location_id,
              on_hand int CHECK (on_hand >= 0 OR negative_allowed), reserved int, version int)
stock_reservations(id, tenant_id, order_id, product_id, location_id, qty, state pending|posted|voided)
```

Same-transaction balance update with `RETURNING`; nightly job re-derives balances from the ledger and alarms on drift. Vehicles are `locations` of kind `vehicle`; load/unload are `transfer_out/transfer_in` rows; van sales fulfil from the vehicle location (R03 §7, R08 §3.1). Available-to-promise = `on_hand - reserved` per location.

**Money ledger (double-entry).** `journal_entries` + `journal_lines` (`SUM(debit)=SUM(credit)` enforced by a deferred constraint trigger), `receipts` + `allocations` (never mutate invoices to track payment), credit notes as reversing entries at the original invoice's tax rate (R09 §5). Cash discount is a conditional rule realised at receipt time within the window, else not applied (R09 §12.20).

**Shared product master.** `products` (global, curated), `product_packs` (piece → inner → case with `case_size`, `supplier_id` nullable for supplier-specific conversions), `product_external_codes` (manufacturer article codes: Reliance 494607257, Guiltfree product code, DMS Item ERP Id), `product_aliases` (learned names), `tenant_products` overlay (listed, sell UoM rules, case override, max per order), `tenant_product_costs` (purchase price, PTD, margin basis; RLS predicate requires actor_role in owner/manager). Proposals: a tenant creating "MOM Makhana 12g Himalayan Salt x 90" inserts a `product_proposals` row usable immediately in that tenant and queued for curator merge into the global table.

**Retailer identity across distributors.** `retailer_identities` (global, keyed on E.164 phone, optional GSTIN/FSSAI, DPDP consent record) ↔ `retailers` (tenant row with code, tier, credit, beat). A retailer user's Better Auth memberships list the tenants they are linked to; the Retailer surface shows one card per distributor. New relationships via the directory are created as `credit_mode = prepaid`.

**Pricing data (synced to devices).** `price_lists`, `price_list_items`, `retailer_price_overrides`, `schemes` are versioned (`version int`, `valid_from`, `valid_to`) so a device can price an order with the version effective at `priced_at` and the server can recompute the same result.

### 3.4 API style

- **oRPC** procedures defined in `backend/libs/contracts` (Zod 4 input/output), implemented in each module's `http/` folder, mounted once in Nest. The apps use the oRPC client + TanStack Query for online reads/writes that do not go through PowerSync (retailer surface, owner web console, docint review, approvals).
- The same router is served as **OpenAPI/REST** for the Windows Tally Connector, brand exports and, later, ONDC/partner adapters.
- Every mutating procedure declares `idempotencyKey: string` (UUID) in its input; `IdempotencyInterceptor` stores `(tenant_id, key) → request_hash, status, body` inside the transaction and replays on retry; a different hash under the same key returns 409 (Stripe semantics, R08 §3.3).
- **PowerSync upload endpoint** `POST /sync/upload` (§5).
- **Webhooks**: `/webhooks/whatsapp` (Meta), later `/webhooks/gsp`.
- No GraphQL (no consumer needs ad-hoc graphs) and no tRPC (no OpenAPI without extra tooling).

### 3.6 Realtime

- **SSE** from the API (`@Sse()`) for the owner web console and mobile Owner module: dashboard tiles, approvals queue, order status; payloads are ids, fan-out via `LISTEN/NOTIFY` (R08 §5.2).

### 3.7 Auth

Better Auth self-hosted in the `identity` module (R08 §7): phone OTP (via MSG91 SMS with a WhatsApp authentication template tried first, R07 §8), email/passkey for owners, `organization` plugin = tenants + memberships + roles (`owner`, `manager`, `salesperson`, `delivery`, `retailer`; platform roles `curator`, `support`), `jwt` plugin issuing short-lived RS256 JWTs with claims `{sub, tenant_id, role, beats[]}` verified by PowerSync through the JWKS endpoint. ### 3.8 RBAC: three layers, one hard test

1. **Membership role → transaction settings** (`app.actor_role`, `app.actor_id`).
2. **CASL** abilities in `backend/libs/domain/authz` (isomorphic): e.g. `cannot('read', 'TenantProductCost')` for salesperson/delivery; `cannot('update', 'Retailer', ['creditLimit','tier'])` for retailer.
3. **RLS**: `tenant_product_costs` policy requires `app.actor_role IN ('owner','manager')`; PowerSync sync streams for the salesperson role select from a `products_for_sales` view that has no cost columns.

The Vyapar hard test ("a salesperson must never see purchase price / margin") becomes a CI test: log in as a salesperson, dump the device SQLite after a full sync, dump every oRPC response for that role, assert no cost/margin column or value appears (R07 §12.4).

## 4. Inbound invoice pipeline (photo/PDF → GRN)

Principle (R05 §7, R06 §6): **QR first, structured pull where a session exists, vision extraction always, human commit always.** "Zero manual entry" means zero manual **typing**; the one deliberate manual number is the blind box count at the gate **[CHANGE]** (R06 §9.3).

## 5. Offline-first sync design (Team app)

### 5.1 Engine: PowerSync

PowerSync Cloud over Postgres logical replication (R07 §3): server-authoritative, per-user partial sync via Sync Streams keyed on JWT claims, offline writes with a FIFO upload queue, per-field LWW with backend veto, built-in attachment queue, `@powersync/react-native` 2.2 with op-sqlite. ElectricSQL (no write path, cloud winding down), WatermelonDB (dormant), Replicache (maintenance), Zero (rejects offline writes) are ruled out by evidence. Cost: Free tier (2 GB/month, 50 clients) for the pilot; Pro $49 at ~10 distributors. RDS: enable `rds.logical_replication`, a `powersync` publication limited to the synced tables, a replication role, TLS, security group restricted to PowerSync's egress IPs. Only the Team app uses PowerSync; the retailer surface and the web console are online-first with TanStack Query persistence, which keeps synced client counts small.

### 5.2 Partial sync scope

### 5.3 Write path: command-shaped upload

The client writes domain rows locally (`sales_orders`, `sales_order_lines`, `visits`, `receipts`, `deliveries`, `delivery_lines`, `pod_evidence`, `trip_points`, `trip_expenses`, `bargain_requests`, `retailer_edits`). PowerSync groups local writes into CRUD transactions; `POST /sync/upload` receives them in order. The handler:

1. Derives `idempotency_key = sha256(client_id + transaction_id)`; if seen, returns 2xx with the stored outcome.
2. Maps the transaction's table set to a **command** (`PlaceOrder`, `RecordVisit`, `RecordReceipt`, `CompleteDelivery`, `AppendTripPoints`, `RequestBargain`, `EditRetailerProfile`) and dispatches to the module's application service inside one DB transaction with tenant/actor settings from the JWT.
3. On business rejection (credit hold, invalid transition, unknown product), commits nothing for that command, writes a `sync_errors` row (synced back to that device: entity id, code, message in hi/en) and returns **2xx** — never 4xx, which would wedge the queue (R07 §3.2 rule 5). The device shows the rejection on the entity and reverts or lets the user fix it.
4. Returns 5xx only for transient faults (DB unavailable) so PowerSync retries.

Server-owned fields (invoice number, allocated receipt number, recomputed prices, statuses) flow back through the download stream and overwrite the optimistic local values.

### 5.4 Conflict rules by entity

| Entity                       | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sales order (create)         | Client stores `quoted_unit_price`, `scheme_ids`, `price_version`, `priced_at`. Server recomputes with the same pure engine at the same version. Equal → accept. Different (version no longer valid, retailer override changed) → accept with `price_variance` flag; if variance > owner tolerance (default ₹0) the order goes to the approvals queue; the retailer-facing confirmation is sent only after approval. Credit hold and per-SKU max are server-enforced; rejection → `sync_errors`. |
| Sales order (edit/cancel)    | Allowed only while `placed                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | confirmed`; state machine guard on server; concurrent manager edit wins over rep edit (server order), rep sees `sync_errors` "order already picking". |
| Visit / geo-tag              | Append-only; geofence result stored as evidence flag, never blocks.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Receipt / collection         | Append-only, never edited; correction = reversal receipt. Allocation: client may pick invoices; else server FIFO oldest-first. Duplicate protection: idempotency key + `(tenant_id, device_id, client_receipt_no)` unique. Cash receipts count toward the trip's expected cash.                                                                                                                                                                                                                 |
| Delivery state               | Monotonic transitions `assigned → started → arrived → delivered                                                                                                                                                                                                                                                                                                                                                                                                                                 | partial                                                                                                                                               | failed`; server rejects regressions; `delivered` requires the ePOD bundle per tenant policy; delivered quantities regenerate the invoice (derived artifact) and post stock from the vehicle location. |

### 5.5 Idempotency and ordering guarantees

- Client UUIDv7 ids everywhere; human numbers server-assigned at commit.
- Idempotency table checked inside the write transaction; 24-hour retention (Stripe semantics).
- PowerSync guarantees clients only see complete checkpoints and does not advance while local mutations are unacknowledged (R07 §3.2 rule 6), so a rep never sees half an order.
- A CI test replays a recorded upload log twice and asserts identical ledger state.

### 6.4 Design system rules (cheap, enforced)
